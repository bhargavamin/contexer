# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Install dependencies
uv sync

# Run the server (stdio transport — for manual testing)
uv run python server.py

# Smoke-test the server responds to MCP initialize
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"test","version":"0"}}}' | uv run python server.py

# Test the commit-time guard against currently staged changes (see Commit-time guard below)
uv run contexer guard --explain

# Preview the assisted anchor backfill (read-only; see Anchor accrual below)
uv run contexer guard anchors --list
```

## Architecture

A small package (`contexer/`), intentionally minimal:

- **`contexer/revisions.py`** - pure decision-revision lifecycle and derived metadata: normalization, title derivation, confidence scoring, immutable revision creation, HEAD resolution, cache synchronization, and append transitions.
  It mutates an already-loaded decision only; persistence, migration, approval, and locking remain in `store.py`.
  Callers reach these functions on the owner (`revisions.current_content(entry)`), never through a private alias on `store`: the six aliases `store.py` carried at extraction time (`_derive_title`, `_new_revision`, `_current_revision`, `_current_content`, `_sync_decision_cache`, `_append_revision`) plus three more (`_normalize_title`, `_normalize_content`, `_compute_confidence`) are gone, per the third module-boundary rule below.
- **`contexer/reconciliation.py`** — pure team-reconciliation state transitions: proposal-slot protection, remote-head deduplication, convergence clearing, and approved/dismissed outcome receipts. It mutates an already-loaded decision only; persistence and public compatibility entry points remain in `store.py`, and the dependency stays one-way (`store.py` imports this leaf, never the reverse).
- **`contexer/review.py`** - pure proposal-slot policy: the trust order for the single unreviewed `proposed_revision` slot (`PROPOSAL_TRUST`/`outranks_proposal`), the displace-and-archive claim (`claim_proposal_slot`), the model-facing refusal ack, and proposal construction (`build_proposal`). Same one-way rule as the two leaves above. **Promotion is deliberately NOT here:** `store._promote_proposal` and `store._apply_approval` anchor source files, which shells out to git and mutates the entry, so approval transitions stay with the store's I/O. `store._route_containment` stays too - it saves mid-branch - and reaches this policy on the owner (`review.build_proposal`, `review.claim_proposal_slot`), the five aliases it used to go through having been removed.
- **`contexer/retrieval.py`** - pure lexical retrieval primitives: `index_tokens` (the one index/query tokenization, distinct from the novelty filter's `store._tokenize`), `derive_topics` + `_TOPIC_ALIASES`, `bm25_rank` + BM25 tuning, and `extract_artifacts` + the artifact regexes. Same one-way rule. **The index sidecar stays in `store.py`:** `_index_path`/`_read_retrieval_index`/`_write_retrieval_index`/`ensure_retrieval_index` are file I/O *and* the suite monkeypatches the reader/writer **through the store module**, which only works while those calls resolve in store's namespace. `_build_retrieval_index` stays too - it assembles docs from a loaded store (entry status, current content) and calls `guard_engine`/`conflicts` via function-level imports. `guard_engine` no longer reaches the artifact regexes at all: it calls **`retrieval.raw_path_artifacts`**, the one definition of "what a path or dotted module looks like", which `extract_artifacts` also builds on (it segments the spans for BM25; the guard needs them intact to compare against a staged path). That replaced a three-hop read (`guard_engine` -> a private alias copied onto `store` -> `retrieval`'s compiled regex), and with it the other twelve retrieval aliases `store.py` carried, seven of which had no reader in `store.py` at all and existed purely so other modules could address this leaf through `store`.
- **`contexer/server.py`** - MCP server entry point. Defines tools (`capture_user_constraint`, `update_context`, `approve_decision`, `resolve_conflict`, `retire_decision`, `restore_decision`, `dismiss_lifecycle`, `reconsider_decision`, `record_agent_conclusion`, `review_pending`, `reconcile_session`, `evaluate_policy`, `get_context`, `get_context_for_prompt`, `bootstrap_context`, `list_shareable`, `share_decision`, `update_global_context`, `get_global_context`) using `FastMCP`. Generates a `SESSION_ID` (UUID) at process start shared across all tool calls in a session. Delegates all logic to `store.py`. **Pending-review UX is non-blocking:** `update_context` capturing an AI-inferred constraint / L3 architecture decision returns a *"pending review - not yet trusted, does not block your work"* notice (never a "wait for the developer" prompt); the identified list with content is pulled on demand via `review_pending` (the in-session twin of `contexer review`), and SessionStart injects only a **count** (not per-decision content) to keep startup light. **`share_decision` is confirmed-by-default:** an outward push previews what would leave the machine (`confirm=false`, a pure local read, only when a team endpoint is configured) and requires `confirm=true` to send; a developer can opt out with `skip_confirm = true` in `config.toml`. When the developer hasn't named a decision, `list_shareable` returns an identified list to pick from, and `share_decision` accepts a comma-separated **multi-select** (`"id1,id2"`) so a whole selection previews + pushes in one call. The CLI mirror is `contexer share` with no args → a numbered interactive multi-select picker.
- **`contexer/store.py`** - All read/write and filtering logic. `_passes_filter` is the core gate: content is stored only if it is novel (token-overlap check - >70% overlap with existing decisions = duplicate). In front of it, at the two server write tools only (`update_context`/`update_global_context`), sits **`capture_lint`**: a long (>400 chars) ai/plan-sourced capture whose first sentence reads as investigation narrative ("Investigated…", "Bug fix…", a date stamp) or runs 45+ words without stating a decision is BOUNCED with same-turn restate instructions instead of stored - a deliberate, model-facing exception to silent filtering (same in-band-ack precedent as `constraint_ack`), because a silent discard would lose the capture the lint exists to reshape. Human/scan/bootstrap/memory sources, `replace_id` corrections, and short content never bounce. **A second bounce, same gate, different defect: the multi-claim split (`_LINT_SPLIT_BOUNCE`).** A capture carrying ≥`_LINT_MIN_SECTIONS`=3 distinct ALL-CAPS section labels is a DOCUMENT, not a decision - independent claims sharing one record, which then ages at the rate of its fastest-rotting part: one anchored file changes and the whole entry renders "may be stale", tarring the durable subsystem understanding inside it by association with the implementation detail beside it. The bounce says SPLIT (one `update_context` per claim), not restate - a model handed the narrative bounce here would fix the wrong thing. What counts as a label is measured, not guessed, against the 193 real long captures across every store on one machine: a run of ≥2 whitespace-separated tokens of which ≥2 are **digit-free** ALL-CAPS words, followed **directly** by a `:` (an intervening parenthetical allowed), counted only **outside code and URLs**, and counted **distinctly**. Every qualifier was earned by a false positive rather than reasoned into existence - digit-free drops ticket noise (`PRT-54 Q5`, `FE SA-108/109`) that otherwise scored as high as a real header; blanking code (fenced blocks **including an unterminated one** - a routine LLM output shape a close-fence-only pattern let leak its contents straight back to the scanner - plus inline spans) with the `:` rule eliminates the SQL class outright (`UUID PRIMARY KEY` / `TEXT NOT NULL` / `ORDER BY` / `ON CONFLICT … DO UPDATE` scored **7** labels on one schema-quoting decision without it, **0** with it); blanking URLs stops "the HTTP API docs live at `https://…`" reading as a label off the scheme's own colon; requiring the `:` to follow **directly** (bare parenthetical allowed, because real headers look like `KNOWN GAP (pre-existing, untouched):`) stops a comma-joined header being double-counted - `WHY CHECKOUT, NOT THE PORTAL:` scored 2, which inflated the very corpus the threshold was set against; distinct counting stops a thrice-repeated `DO NOT:` reading as three sections. Measured with all of it applied, the corpus is 183 captures at 0 labels, 7 at 1, and one each at 2, 3 and 4 - `_LINT_MIN_SECTIONS`=3 catches exactly the 3 and the 4, both genuine multi-section documents, one of them the record this gate was built from. **That is a one-count margin, not a wide gap**, stated plainly because the earlier looser matcher made the gap look bigger than it was. Known residual shape, accepted rather than tuned away on a single example: a one-claim decision that uses three `LABEL:` constructs of its own (`the API GATEWAY: … the DB LAYER: … the CI PIPELINE: …`) does bounce; every tightening that would exclude it (three-word runs, sentence-initial position) also drops the real headers the gate exists to catch. Same narrow scope as the narrative bounce: ai/plan only, >400 chars, no `replace_id`. **Refused corrections ack in band (#202):** an entry has ONE `proposed_revision` slot, trust-ordered by `_claim_proposal_slot` (`_PROPOSAL_TRUST` = human > plan > ai > scan, #200) - when a `replace_id` correction's source is strictly outranked by the sitting proposal, the slot keeps the higher-trust version and the caller still returns success (failing toward review of the better proposal), so the refusal is reported through `update_decision_with_meta`'s `meta["refusal_ack"]` (the 3-tuple variant `update_decision` wraps, house pattern: `get_context_for_prompt_with_meta`) and `update_context` returns that ack instead of the pending-approval prompt: the model is told its correction was refused, not queued, must not retry, and must surface BOTH versions to the developer that turn. Same in-band-ack precedent as `capture_lint`/`constraint_ack`. **Evidence receipts are BOUNDED, and the drop is recorded.** `record_evidence_summary` keeps at most `MAX_EVIDENCE_SUMMARIES`=50 rows and stamps `evidence_summary_dropped` when it actually evicts, the same "truncation is recorded, not silent" rule `_anchor_sources` follows with `source_files_total`. Unbounded, it grew for as long as a rule kept being restated (measured: 31 rows for 31 repetitions, beside a `recurrences` list correctly capped at 20 on the same entry), because every settled candidate files one. The cap is deliberately NOT `MAX_RECURRENCES`: a recurrence row COLLAPSES (one per session + match kind, with a count) while a summary row does not - it is one settled candidate carrying the ids of the events it accounts for, so each eviction loses a distinct receipt runbook invariant 3 leans on. Known interaction, stated rather than guarded: `reconcile._recorded_summaries` builds its idempotency set from this list, so a receipt evicted before its held events were deleted is filed a second time; reaching that needs 50 other candidates to settle on the SAME decision between one candidate's summary write and its delete, and the cost is one duplicated receipt row, never a wrong disposition. **Recurrence is RECORDED, never silent (hardening Task 03).** `_record_recurrence` still bumps `occurrence_count` and the distinct `session_ids` with exactly their existing meanings, and still touches neither confidence nor approval status - a rule repeated a hundred times is still a rule a human has or has not approved. It now also appends one bounded history row (`recurrences`, at most `MAX_RECURRENCES`=20) saying WHEN, in WHICH session, from WHICH source, and HOW the match was made (`overlap` | `containment`, plus the ratio). **One row per (decision, session, match kind) with an in-session `count`**, because the constraint hook fires on every prompt and a developer restating a rule six times in one session must not evict five other sessions from the window; the counts above it stay exact, so the cap loses detail and never a hit. The write lands in the same save under the same store lock. **`capture_user_constraint`'s plain-duplicate branch used to record NOTHING** (no bump, no write, no return value distinguishing "not a directive" from "the developer said this again"), which is outstanding issue 3: the second statement of a rule left no trace anywhere. It now records the recurrence and reports it through `capture_user_constraint_with_meta`'s `meta["recurrence"]` (the house `_with_meta` variant - `capture_user_constraint` is a 3-tuple wrapper over it, so no existing caller changed), which is what lets `evidence.capture_directive` spool the repetition. Still no second entry, no status change, no `.pending_review` arming. **An INACTIVE match never records a normal recurrence:** `update_decision_with_meta`'s dedup is status-blind, so a restatement of an `ignored` decision used to bump its count - ranking a discarded decision as increasingly corroborated. It now stores nothing and REPORTS the match as `meta["inactive_match"]` for the reconsideration lane, the only thing allowed to bring an inactive decision back. **Human review surfaces clip:** `format_pending_review` and `format_shareable_list` render bodies through `clip_body` (public since Task 07 gave it a second reader module, per boundary Rule 2) (400 chars, word boundary, `… [+N chars]`, one footer line pointing at the full text when anything clipped); model-facing renders (`get_context`, `_render_prompt_decisions`, session-start payloads), the CLI edit path, and the wire-accurate `format_share_preview` stay full. **`contexer review` renders bodies IN FULL too** (`cli._print_wrapped`), deliberately: it is the one-decision-at-a-time surface whose entire purpose is judging an approval without running a second command - it previously clipped at 400 chars with no footer saying so, so the only way to read a long decision was to enter `[E]` edit mode and submit empty. Alongside the body it renders the metadata that makes an approval accurate (`cli._review_metadata`): capture time + origin (`created_by`, humanised via `_ORIGIN_LABELS`), corroboration (`occurrence_count`/`session_ids`, shown only when >1), `source_files` plus a `_staleness_note` warning when that code moved since capture, `anchor_candidates` as `Would anchor`, the anchor commit via `store.review_anchor_note`, and a warning when `repo_source == "pointer"` - the one resolution branch that can silently target the WRONG repo. `review_anchor_note` reads the PR number off the anchor commit's own SUBJECT (`(#211)` / `Merge pull request #211`); no PR number is stored in the schema, so this costs one `git log -1` and works retroactively. Both git lookups are fail-soft - a hiccup drops a row, never the review - and both route through `cli._budgeted`, a per-run memo + **time** budget (`_REVIEW_GIT_BUDGET` = 3s, built once per invocation by `_review_git_budget`). Deliberately a time budget, not the call-count cap the batch renders use (`_STALENESS_MAX_CHECKS` = 3): that cap protects a prompt's critical path where the developer is blocked and never asked for the work, whereas here they explicitly ran `contexer review`, so a 3-call cap would blank the accuracy rows from the 4th decision onward even on a warm repo where each call costs ~10ms. Memoising is what actually pays: a review queue is normally decisions captured in one session, which share an `anchor_commit`, so the whole queue collapses to one lookup. On exhaustion the row SAYS `(git is slow - anchor/staleness checks skipped this run)` rather than rendering bare and reading as "nothing to report" - the same honest-on-exhaustion rule `anchors.py` enforces with `_BudgetExceeded`. `[Q]` quits the loop leaving the remainder pending. **Legacy stamping:** `_migrate_decision` stamps missing `status`→`approved` / `created_by`→`ai` on pre-provenance entries (schema v4; behavior-neutral - readers already default through `entry_status`). **Scan-convention re-verification:** `verify_scan_conventions` runs at non-resume/compact session start (24h TTL stamp written before scanning; fast-path exit before any mining when the store has no scan-sourced stats-bearing participants): a still-measured rule refreshes its evidence sentence in place (including fuzzy wording-drift matches against stat-bearing fresh sentences only), a disappeared rule attaches a rule-shaped withdrawal `proposed_revision` ("… (evidence withdrawn on re-scan: …)") through the normal review flow, a reappearing rule retracts its stale scan-sourced proposal, an empty fresh scan flags nothing (silence over noise), and the session-start payload re-reads the store when verification reports a change so the new session renders verified state. Storage is capped at `MAX_ENTRIES = 500` per repo. Display is separately capped: `_UNFILTERED_DISPLAY = 10` for overview calls, `_FILTERED_DISPLAY = 25` for query/type-filtered calls. Bootstrap is insight-aware: `_detect_insight(repo_path)` infers the user's familiarity (`high`/`medium`/`low` + decisive flag) from git signals - commit authorship by `user.email`, first-commit authorship, fresh-clone reflog entries. Detection order is load-bearing: the empty-email check must run before any `--author` query (an empty author pattern matches every commit). Detection is TTL-cached by `_cached_insight` (24h, `~/.contexer/.insight_<slug>`, fail-soft), validated on read against the current `user.email` + `HEAD` - a cache hit costs 2 git subprocesses instead of ~6, and a changed identity or re-cloned/rewound repo invalidates immediately rather than after the TTL; `_detect_insight` stays pure for tests. `bootstrap_scan(repo_path, insight, mined=None)` filters gap questions by each gap's `min_insight` AND suppresses questions the miner already measured (tests-in-scope, CI, team conventions when ≥3 conventions mined); empty `insight` auto-detects. **`bootstrap_apply(repo_path, session_id, insight)` is the self-storing bootstrap** (what the `bootstrap_context` tool runs by default, `apply=True`): scan + `miner.mine_conventions` + persist under one store lock with one save - exactly ONE consolidated `"Stack: ..."` architecture entry (never ~15 per-fact entries), each mined convention as its own decision tier-gated by evidence (≥90% dominance → born `approved` via `created_by="scan"`; 60–89% → `pending_approval` - deliberately NOT `suggested`, which would inject at session start and never surface in `review_pending` - arming the `.pending_review` nudge). Idempotent: skip-don't-bump `_find_match` dedup, so re-calls store 0 and never touch `occurrence_count`. The model's only remaining bootstrap jobs are reporting the returned `stored`/`pending` counts and asking the residual author-only gap questions. Non-decisive detection makes the offer ask the user directly. **The offer is a numbered menu of at most FOUR options in every variant**, and the injected block tells the model to render it as one interactive multiple-choice question where the host has that tool (Claude Code: `AskUserQuestion`), else as the numbered text list - a number and its own row's keyword mean the same thing, but **which** keyword sits at a given number is variant-dependent (`2` is `full` in the high/ambiguous menus and `quick` in the low one), so never hardcode a number→mode map. Four is the picker's option cap (plus its own free-text "Other"), which is why `some` has no row in the ambiguous variant: it stays a documented typed reply mapping to `insight='medium'`, and `scan` absorbs its "didn't build it" meaning - **so in the ambiguous variant `scan` routes to `insight='medium'`, not `'low'`**: `'low'` returns only the goal gap, silently dropping the purpose question (`min_insight='medium'`) for the one user class `some` existed to serve; the low-decisive variant, where the evidence says no commits, still routes `scan → 'low'`. For the same reason the affirmative is variant-relative: a bare "yes" means **option 1 of the variant on screen** (`quick` in high, `scan` in low), never a fixed keyword, since a blanket `yes → quick` would start the author interview precisely where the evidence says the user cannot answer - and in the **ambiguous** variant it resolves to nothing at all, because that question is "how well do you know this repo?" whose option 1 asserts authorship a bare "yes" never claims; there the model must ask which option instead of inferring. The offer rows are also emitted **unquoted**: the block used to be wrapped in script quotes, invisible in verbatim text mode but rendered into the picker's own labels (`not now"`). Gap questions are asked the same way, but that ask shape lives in **`store.GAP_ASK_GUIDE`**, attached by `server.bootstrap_context` as a `how_to_ask` field **only when the result carries gaps** - never inlined into `_build_bootstrap_context`, which is injected at every context-less session start, again at the first `UserPromptSubmit`, and post-compact, including the skip and STEP 0 paths where no gap is ever asked (~470 tokens per injection, ×2-3 per first turn). `/bootstrap` and the docs point at that field instead of restating it, so the rule cannot drift across copies - it had already drifted in `bootstrap_command.md` within one commit. The shape itself: ONE question at a time, never batched (batching would skip the between-answer re-evaluation that drops tests/CI/deploy gaps for a docs-only repo); last option = "Skip this one"; a "Correct" option (description = the gap's `assumption`) ONLY when that assumption actually answers the gap's question - **and `assumption` is an OPTIONAL key, omitted (never `""`) when no repo signal predicts the answer**, so no assumption means no Correct option and the question is asked openly. The goal gap is the one such gap: it asks what the USER intends to do here, which nothing in the repo forecasts. It used to carry `_infer_purpose(...)` - the repo's purpose, answering a different question - and the guide spent a paragraph teaching the model to discard it; deleting the field deleted the workaround, and an empty string was rejected as worse than absent because it renders as a blank Correct option. `_gap`'s signature moved `assumption` last with a default; every call site was already keyword-only (verified, zero positional). Up to two candidate options in between ONLY when the `hint` names distinct candidate answers (half the hints are one comma-list belonging to a single answer, or a restatement of the question); and the stored sentence must ANSWER THE QUESTION, never echo the assumption's wording. **Rule docs are EVIDENCE FOR A QUESTION, never a decision.** `GAP_ASK_GUIDE` opens by telling the model to read the files named in the result's `existing_context_files` before asking anything, and to convert a gap those files already answer into confirm-or-correct (quote the line, ask the developer) - storing the *confirmed answer*, never the quote, so provenance stays `human` and no unratified prose reaches the store. This is the safe direction of the import idea rejected in #19e5a6cb: docs → better question → human answer → store, never docs → store. Two disciplines make it survivable: rule docs may only reshape or drop existing gaps, **never add** one (a thirty-line rules file would otherwise become a thirty-question interview), and a rule doc contradicting a *measured* convention in the same result (a doc demanding full type hints beside a mined "61% of 556 functions") becomes the highest-value question in the interview, since both sides are evidence and only the developer can settle it. **Exactly ONE addition is carved out**, because the two rules collided in the first cut: a doc contradicting a sentence in the result's `measured_conventions` earns its own question even though it is not one of the returned `gaps` - the answer is stored as a `convention` that SAYS it supersedes the measurement, so the developer can retire the stale one from `contexer review` instead of both standing as equals. That check is only executable because `bootstrap_scan` now RETURNS `measured_conventions`: `bootstrap_apply` already mined them for gap suppression and then discarded them, so an earlier draft told the model to compare against measurements that were nowhere in the payload. The enumeration is the whole mechanism - the model can read only what the scan names - so `bootstrap_scan` also lists `AGENTS.md`, `CONTRIBUTING.md`, `GEMINI.md`, `.github/copilot-instructions.md` and `.claude/rules/*.md` (capped at `_MAX_RULE_DOCS`=5, with an explicit `(showing 5 of N)` row rather than a silent truncation), all previously invisible to bootstrap. **The model is pointed at `context_docs`, NOT `existing_context_files`:** the latter is every file the scan touched - `uv.lock`, `.github/workflows/`, and literal glob strings like `.eslintrc*` that are not readable paths at all - so aiming a "read these" instruction at it buys failed reads and wasted tokens. **A generated doc is skipped by its own BANNER** (`_is_generated_doc`: a marker - `auto-generated`/`autogenerated`/`@generated`/`do not edit` - on a SHORT line, ≤`_GENERATED_BANNER_CHARS`=80 chars once comment leaders are stripped, within the first `_GENERATED_BANNER_LINES`=5 lines; fail-soft toward *keeping* the file). The shape test is the whole point, and matching the marker anywhere in the header was wrong (caught in review on #220): a human rules file *discussing* generated code uses the same words - "the files under `src/proto` are auto-generated; do not edit them manually" - so a header-wide substring match silently dropped exactly the "never hand-edit the protos" rule that most deserves a confirm-or-correct question. The two failure modes are not symmetric, which is what sets the direction: enumerating a generated doc costs one skipped read, while excluding a human-authored one loses evidence with no signal. Residual and accepted: a rules file whose opening lines hold a short standalone sentence like "Protos are auto-generated." still reads as generated - separating a banner from a terse rule beyond that needs meaning, not shape: an earlier Contexer version wrote its own auto-generated mirror into `.claude/rules/` (36KB and months stale on this very repo until it was deleted; nothing in the current source regenerates it, but an install of that vintage still leaves one behind), and enumerating it would have the model quote Contexer's own output back to the developer to "confirm" - a decision round-tripping in as if human-authored, the exact loop this design exists to prevent. Enumeration and keyword-scanning are one table (`_CONTEXT_DOC_FILES`, second element = scan budget in chars, `0` = enumerate-only) so the invariant lives in data rather than in a comment beside a second loop. The four scanned entries (README/CLAUDE.md/.cursorrules/.windsurfrules) are **grandfathered, not endorsed** - a `CLAUDE.md` opening "For example, run `make deploy`" trips the same unanchored substring test and silently suppresses the tests/CI/deploy/exclusions gaps; narrowing `_SIMPLE_REPO_SIGNALS` is a separate behaviour-changing decision, deliberately not folded in here. **`readme_summary` was deleted outright**: the README's first non-heading line is as often markup as a tagline - on contexer's own README it evaluated to `'<p align="center">'`, which shipped as the purpose the developer was asked to confirm - and a length filter cannot rescue it (badge lines run 60–70 chars). **`_infer_purpose(name)` returns `""` rather than a placeholder**, and matches NAME TOKENS rather than substrings; both were fixed on review, and both were caused by deleting the README fallback that used to mask them. A truthy non-answer ("Purpose not yet documented", `'"x" - type not obvious from name alone'`) survives `_gap`'s omit-when-empty rule and renders as the "Correct" option for "What does this repo do?", so clicking it stored a non-answer as the ratified purpose; and `"api" in "rapid-sync"` is true (r-**api**d), so a sync tool was labelled a backend API, `webhook-processor` a frontend. With no README second opinion left, either mistake now reaches the developer unchallenged. What survives at the read sites is only the `_SIMPLE_REPO_SIGNALS` keyword scan; the `docs/*.md` three-file cap still needs its deterministic sort, since **which** three still decides `is_simple_repo` - what changed is that no ordering heuristic can improve the sample, because nothing is extracted from those files any more. No host plumbing: the capability line is host-neutral text in `_build_bootstrap_context`, so a host without the tool simply falls through to the text list and a new adapter inherits both for free. **The offer fires at most once per session per repo**, gated by `~/.contexer/.bootstrap_offered_<slug>` (`_arm_offer` / `_offer_already_made`): skipping stores no decision, so the `if decisions` guard never trips and every later prompt - plus every `/compact` - used to rebuild the block and re-open the picker the developer had just dismissed, one modal per prompt. A non-resume, non-`compact` session start clears the flag (a genuinely new session offers again); `compact` deliberately does not, since it continues the session in which the developer already answered. The STEP 0 newcomer-answer path is NOT gated - it shows no menu, and gating it would swallow the answer. Fail-soft (a flag error degrades to the old always-offer behaviour) and swept by `_gc_stale_session_files` for repos never reopened. Known limitation: commit count is repo-wide, so a few commits in one corner of a monorepo read as insight into the whole repo. **Retrieval V1 (topic router).** `get_context_for_prompt(repo_path, prompt, session_id="")` (called by `claude.rationale` - Codex reuses it verbatim - and Gemini's `before_agent`) is BM25-backed by a disposable index sidecar (`STORE_DIR/.retrieval_index_<slug>.json`, indexing every non-`ignored` decision - `approved`/`suggested`/`pending_approval` - since `pending_approval` entries ARE retrievable (`get_context` renders them with a `[pending]` tag) and the index must surface exactly what `get_context` can hand back; only `ignored` is excluded, permanently, so a stale index can never advertise a topic `get_context` would refuse to return) written ONLY at the tail of `save` (every writer already holds the store lock, so no extra locking) and read-only per prompt via `_read_retrieval_index` - a missing/corrupt/wrong-version index falls back verbatim to the pre-V1 keyword lookup (`_legacy_prompt_context`), never rebuilt inline. **Session-start self-heal (`ensure_retrieval_index`).** The per-prompt reader stays strictly read-only, but "the repo's next `save` rebuilds it" is only an adequate self-heal for a repo somebody is still writing to: an index *version* bump (v1→v2 at #187 fix round 1) rejects every already-indexed repo at once and silently demotes it to `_legacy_prompt_context`, whose keyword pick is `sorted(set(keywords), key=len, reverse=True)[:3]` - literally the three LONGEST words of the prompt, so a long prose word ("verification", "deliberately") outranks the short domain identifier that matters ("Clerk", "orgId"), and a repo nobody captures into never recovers at all. So `_local_session_start_payload` calls `ensure_retrieval_index(repo_path)` once per session start, positioned BEFORE the `resume` early-return and unconditional on `source` (a resumed/compacted session injects nothing there, but its later prompts still route through BM25). It rebuilds only when `_read_retrieval_index` returns None AND the store holds an indexable entry (the identical `decision`-minus-`ignored` filter `_build_retrieval_index` participates on - matching it exactly is what stops an all-ignored store from writing the zero-doc sidecar the guard exists to avoid; an empty sidecar buys nothing the legacy path doesn't already answer with the same silence). **Both bail-outs are tested UNLOCKED first and re-tested under the lock**, which is taken only around the write: `store_lock` is `flock(LOCK_EX)` with no timeout and the other session-start passes hold that same per-store lock across genuinely long work (`verify_scan_conventions` across a whole-repo mine, `anchors.verify_anchors` across up to `_ANCHOR_GIT_BUDGET` git subprocesses, `bootstrap_apply` across another mine), so locking *before* the bail-outs would make a second session on the repo - and, on `resume`/`compact`, a session start that previously took no store lock at all - queue behind that work on every start, forever for a repo that can never satisfy the condition. The unlocked pass is therefore pure contention avoidance; the locked re-check stays the authority (and is what stops two sessions both rebuilding). The result is verified by reading it back rather than assuming the fail-soft `_write_retrieval_index` succeeded, then an `index_rebuild` event goes to the retrieval log - log-only, never user-facing, so silent operation holds. - **`contexer/guard_engine.py`** - the commit-time guard engine (staged-file plumbing, Tier-1 advisory pairing, Tier-2 armed blocking rules), extracted out of `store.py`. `store.py` stays the public facade: it re-exports the five public entrypoints (`guard_staged`, `guard_candidates`, `arm_guard`, `disarm_guard`, `dismiss_guard`) *lazily*, via a PEP 562 module `__getattr__` at the bottom of its file, not an eager `from contexer.guard_engine import ...` - `guard_engine.py` imports `store` at its own top (the module object, not `from`-imports, so store-owned values tests monkeypatch on `contexer.store` are still seen here at call time) for the store-owned helpers it needs (`STORE_DIR`, `load`, `save`, ...), so an eager import in `store.py` would make `store.py`'s own load depend on `guard_engine`, which depends on `store.py` having already finished loading - a cycle that only resolves if `store.py` happens to be the module that starts loading first. Resolving lazily means `store.py` finishes loading without ever needing `guard_engine`, so `guard_engine.py`'s own `from contexer import store` is safe in any import order, including `import contexer.guard_engine` as the very first touch of the package. Approval-time anchoring (`approve_decision`, `_apply_approval`, `_anchor_sources`) is approval machinery, not guard engine, and stays in `store.py`. **`decisions_for_files(repo_path, files, decisions=None)`** (Task 1 of #174) is the retrieval surface built on the same Tier-1 pairing signals (`source_files` membership, path-like content artifacts extracted from a decision's content) but is pure retrieval, not advisory noise control: no guard-trust filter (a `pending_approval`/`suggested` decision can still govern a file - the caller decides what to do with its status) and no throttle/dismissal state, since nothing here is ever surfaced repeatedly at commit time. Every non-`ignored` entry of both the repo and global store participates; `files_matched` on each hit lists, in the caller's input order, which queried files matched that decision (the reverse-tracing property), and `reason` is the single strongest signal across those files (`source_files match` beats any artifact reason). - **`contexer/anchors.py`** - anchor lifecycle verification (Task 2 of #174), extracted out of `store.py` (user directive: don't crowd store.py with a second verification family) so `store.py` carries only the session-start call site (`anchors.verify_anchors`, wired in immediately after `verify_scan_conventions`, same re-read-on-change convention: a rename correction or a fresh retirement proposal makes the session re-`load` so it renders the verified state). `verify_anchors(repo_path, force=False)` re-checks every anchored, active-status (`approved`/`suggested`) decision's `source_files` against the working tree, gated by a 24h TTL stamp (`.anchor_verify_<slug>`, mtime-based, written BEFORE any git work so a crash mid-run can't retry-storm the next session start), with a fast-path exit - before the stamp is even touched, before any git call - when no entry in the store carries `source_files` at all. Per participant, **rename detection runs first**: git-budgeted (`_ANCHOR_GIT_BUDGET` = `2 * MAX_SOURCE_FILES + 1` = 21 calls/run - derived, not picked: one entry's worst case is every anchored path missing at 2 calls each plus one `rev-parse`, so the budget guarantees the first entry of every run always completes and the run makes forward progress; a smaller budget let one fat entry exhaust it inside its own file loop, silently starving that entry and every entry after it on every run forever, `store.GIT_FAST_TIMEOUT`-second timeouts, fail-soft) `git log --follow` + `git show --name-status` finds a confident single rename target for each vanished path; a target that's found and still exists on disk corrects the entry's `source_files`/`anchor_commit` in place - NOT a review event, since the decision's content is unchanged, only its address moved. No confident rename -> the file is `missing`; partial loss (something survives, as-is or renamed) is still a silent address-list refresh. Total loss (every anchored file gone, none renamed) attaches a `proposed_lifecycle` retirement (`lifecycle.attach_lifecycle_proposal`, source `scan`, reason "anchors withdrawn on re-verification: `<files>` no longer exist") and arms the `.pending_review` nudge. The decision's CONTENT is never touched: a retirement is a state transition, not a rewording, and encoding it as new decision text is exactly what the plan's C2 lane exists to stop. Approving it (`lifecycle.retire_decision`) tombstones the decision with its lifecycle history; dismissing it (`lifecycle.dismiss_lifecycle`) leaves the entry, `source_files` included, untouched, so the next TTL cycle re-proposes - dismiss means "not now", not "never ask again", until the developer retires the decision or ignores it. **Dedupe is structural rather than a text comparison**: an entry already carrying either proposal is not a participant at all. The older content-marker guard stays for the one case it still answers - a LEGACY entry whose live content already carries the withdrawal clause a pre-lane `proposed_revision` wrote. That pre-lane shape is no longer CREATED, but `store._promote_proposal`/`_apply_approval` keep their `clear_anchors` branches (drop `source_files`/`anchor_commit`, drop `anchor_candidates`, skip the candidate-blessing branch) for stores that still hold one pending, marked as legacy in both docstrings. **Budget exhaustion is honest, not degraded**: once `_ANCHOR_GIT_BUDGET` is spent, `_call` raises `_BudgetExceeded` instead of returning a value indistinguishable from "git found nothing" (which previously could misclassify a cut-off entry as a total loss or a wrong partial refresh); the entries loop catches it and breaks immediately, leaving the in-progress entry and every entry after it completely UNVERIFIED this run - no proposal, no refresh, no re-anchor, no mutation - deferred to the next TTL window rather than guessed at. `anchor_candidates` (unconfirmed, human-not-yet-blessed anchor guesses) are never by themselves a reason to participate - participation requires a real `source_files` anchor - but they CAN ride along on a participant (candidates survive the pending-twin promote path and `_route_containment`, neither of which pops them), and under the lifecycle lane a retired decision leaves the live store entirely, taking any leftover guess with it. Fail-soft throughout: any unexpected failure degrades to a no-op `{"reanchored": 0, "proposed": 0}` rather than raising out of session start.
- **`contexer/lifecycle.py`** - the decision-lifecycle lane (plan C1 + C2): the `proposed_lifecycle` slot, retirement, and restoration. Extracted out of store.py on the same directive that produced `anchors.py`/`conflicts.py`/`console_api.py`, with the identical discipline - `from contexer import store` at its top, store-owned helpers read through the module OBJECT at call time, and store.py needing it only at call time (two function-level imports). **A decision's one `proposed_revision` slot answers "this should READ differently"; a `proposed_lifecycle` answers "this should stop being live".** Different state transitions, so sharing one slot would let either silently drop the other: the two lanes COEXIST and never displace one another, and resolving one leaves the other exactly where it was. Within the lifecycle lane the order is only human-over-automated (`ai` and `scan` are both machine guesses at the same transition, and ranking them against each other would let one quietly overwrite the other's reason); a displaced proposal is archived to `superseded_lifecycle`, the shape `superseded_proposals` already has. **A proposal is bound to `basis_revision_id`** = the target's `current_revision_id` at proposal time: if HEAD moves the proposal is STALE, rendered with an explicit marker, and `retire_decision` REFUSES it rather than applying a verdict passed on text nobody read in this form - `dismiss_lifecycle` stays available, since dropping a proposal needs no basis. `retire_decision(repo, id, reason, replacement_id=None)` is the only thing that moves a decision out of active context, and it doubles as the APPROVAL path for an ai/scan-proposed retirement - a human calling it IS the explicit human action, so the recorded actor is `human` either way. It shares ONE transition (`tombstone_entry`) with store's console-facing `delete_decision`, so tombstone history is uniform however a decision left the live store: a versioned `lifecycle` record (`{event_id, kind, occurred_at, actor, reason, revision_id, replacement_decision_id}`, kind `superseded` when a replacement is named else `retired`; `restored` on the way back; `replacement_linked` stays reserved vocabulary with no writer). **That kind vocabulary has ONE owner here** - `RECORD_KINDS`/`RETIRED_KINDS`, enforced by `lifecycle_record` itself, with `reconcile` DERIVING its retired set rather than respelling it, so a rename cannot leave a reader matching on a spelling nothing writes while its own tests still pass. `remote._WIRE_LIFECYCLE_KINDS` deliberately stays SEPARATE even though the three spellings agree today: it is a GUESS at the server's enum, and coupling it to the local vocabulary would let a local rename silently change what goes over the wire - the `source="plan"` failure exactly. **`revision_id` is captured AT the transition, never re-derived**: `revisions.append_revision` pops the entry-level `approved_by` stamp whenever a non-human revision lands, so history that trusted entry-level state would misreport which version was retired. An unresolved `proposed_revision` is ARCHIVED onto the tombstone as `unreviewed_proposal_at_retirement` rather than dropped - nobody ever ruled on it, and a retirement is not a ruling on it - and `restore_decision` APPENDS a `restored` record rather than rewinding history. Schema is additive: an old store loads unchanged, and the tombstone's raw readers (`scope_audit`, `console_api.list_tombstones`) ignore the new keys. Two store privates were promoted to public because this module made them a SECOND reader - `touch_pending_review` (also `anchors`) and `read_deleted` (also `console_api`) - while `_deleted_path`/`_save_deleted`/`_keep_recent_tombstones`/`_clip_body` stay private with this as their one reader, the coupling the boundary rules allow. **The facade re-exports exactly ONE name**, `store.restore_decision`, and only because that spelling WAS public on store before the extraction; every other lifecycle name is new, so `anchors`/`reconcile`/`cli`/`server`/`ui/api` all import this module directly. **A THIRD slot lives here too, `proposed_reconsideration` (OUTSTANDING-ISSUES item 7):** a decision the developer already switched off, restated out loud in a later session, is neither a live duplicate nor a fresh decision beside it - it is the question "should this come back?", and its subject is not live at all (an ignored decision sits in the store with an inactive status; a retired one is in the tombstone sidecar, which is why `propose_reconsideration`/`reconsider_decision` locate through `_locate_inactive` and save whichever file actually holds the entry). Reusing `proposed_revision` was refused for the reason the retirement lane refuses it - different questions, and one slot lets either silently drop the other - so all three lanes coexist. Only `candidates._classify`'s `reconsider` kind opens one, and only from an explicit `user_directive` (`_has_directive`, read across the group so a directive that merged into a conclusion's group still counts): an agent conclusion, edit, test or repetition may corroborate an open question but may never raise one, and for agent-only evidence the aggregator deliberately emits a note that NAMES no decision, because a pointer at the inactive decision would be the reopening itself. The inactive match must also be STRICTLY closer than any live one, so a simultaneous live match stays an ordinary duplicate or update. Identity binds the basis: `candidates._candidate_id` appends `basis_revision_id` for this kind ONLY (appended, never joined as an empty fourth component, so every id already in a ledger keeps its spelling), because reconsidering revision 3 is a different question from reconsidering revision 5. `reconsider_decision(repo, id, action, content)` takes the four answers `restore` / `restore_edit` / `skip` / `dismiss`; `restore` returns a decision with NO historical active status as `pending_approval` (`_fail_toward_review`) rather than guessing it was approved, since guessing there arms the commit-time guard, and `restore_edit` appends the developer's own wording as a human revision and is the only path that comes back approved. Staleness covers both ways the record can move - HEAD advanced, or the decision left the state it was judged in (restored elsewhere) - and refuses restoration while leaving `dismiss` available. Every outcome leaves a durable receipt on the decision itself (`reconsideration_history`, capped at `_MAX_RECONSIDER_HISTORY`=20), which is what lets a later directive raise the question again while the review surfaces say "asked before: dismissed N time(s)". `reconcile._materialize` routes the kind ONLY here (never through `update_decision_with_meta`, whose dedup is status-blind and would absorb the restatement onto the dead entry), holds the evidence under lane `reconsideration`, and settles it on observed state alone: `approved` only for a completed `restored` record carrying the basis revision - never on the decision merely being live again - and `dismissed` only for a durable receipt naming that candidate.

- **`contexer/evidence.py`** - the evidence event SCHEMA, the host-hook emission surface, the ONE `agent_conclusion` emitter, and the host-coverage vocabulary: every filesystem concern lives in `spool.py`. `validate_event` is a PURE function and the ONE gate, so storage validates once and writes what it gets rather than re-asserting flatness, path shape or caps a second time. The schema is FROZEN per version: an unknown top-level key is an error rather than being preserved, and a `schema_version` other than `SCHEMA_VERSION` is rejected in BOTH directions, since a forward version means a newer writer whose semantics this reader cannot assume. **Three kinds are RESERVED - schema-valid with no emitter anywhere.** `diff_observed` and `test_result` because their CONSUMER shipped first (`candidates.SUPPORT_KINDS` scores both, so the day an adapter emits one the validator must already accept it); `session_reconcile` because ruling R34 moved the pass receipt OUT of the spool into `.reconcile_<slug>.jsonl`, and it stays valid so a spool that already holds one reads back and is filtered out by `reconcile._EVIDENCE_KINDS` rather than being quarantined as malformed. **`candidate_disposition` was REMOVED on the opposite test:** a settled candidate's disposition lives in the decision's own `evidence_summary` history, so that kind has neither a producer nor a reader, and a spooled file claiming it is schema drift the validator SHOULD catch. A leaf: it imports `redact` and reaches `store` through the module OBJECT at call time, and `emit_hook_event` reaches `spool` through a FUNCTION-LEVEL import placed inside the never-raises `try` (so even the import failing is caught) - which is what keeps the dependency one-way at import time while `spool` imports this module for `validate_event`. `repo_key` is the repo the CALLER already resolved, never re-resolved here: an event keyed through a different chain than the spool it lands in is the writer/reader split this repo has shipped twice already (`post_write`'s slug, the team-poll session id). `capture_directive` is the one definition every host's per-prompt constraint hook shares - `store.capture_user_constraint` plus the `user_directive` event for it, returning and RAISING exactly what the store call does so no hook's behaviour changes; it emits when the store reports it stored or updated an entry AND when the store reports a RECURRENCE (`meta["recurrence"]` - the developer restating a rule the store already holds, which used to emit nothing at all: outstanding issue 3). The repetition goes out as an ordinary `user_directive` carrying the sanitized content, so the aggregator matches it onto the decision it duplicates and settles it there rather than opening a second pending decision; `decision_repeated` deliberately stays a valid kind with NO emitter, since a lone repetition scores below the review bar and would open a group nothing can settle. When the store raises (the loss this ledger exists to record) it emits an `unverified` event only if the store's own public detector says the prompt was a directive, that emission suppressed separately so a failure while RECORDING the loss never replaces the exception the caller's error path is about to see. **`record_agent_conclusion` is the ONE production emitter of `agent_conclusion`** (surfaced as the MCP tool of the same name, closing OUTSTANDING-ISSUES item 2): it spools ONE event carrying `reported_by="agent"` plus whether a rationale was supplied, and writes nothing else - never a decision, never an approval, anchor, retirement, restoration or armed policy. Two gates run in front of the spool, both reusing rules that already exist: a blank conclusion is refused rather than spooled (an event with no statement can never seed a candidate), and **`store.capture_lint` runs on the same text `update_context` would lint**, because without it this door is a LINT BYPASS - reconciliation materializes through `store.update_decision`, which is NOT the linted server tool, so a bounced narrative re-submitted as a conclusion would land pending review in exactly the shape the lint exists to reshape. An append failure REPORTS the loss and never reads as capture. **The scoring bar bounds what QUALIFIES, not how much arrives**, and the distinction was measured rather than assumed: a bare conclusion scores 15 against a review bar of 25, so it needs either its own rationale (25) or an independently observed file change (15 + 10) to reach review - but candidate identity is a uuid5 over the sorted event ids, which by design gives every DISTINCT event set its own candidate, so 20 distinct explained conclusions in one session produce 20 `pending_approval` entries, 20 review-queue rows and 20 `[pending]` rows in `get_context`. Task 03's merge (`_MERGE_OVERLAP` 0.7) plus the store's own >70% novelty filter catch a model REPEATING itself (30 near-identical variants collapse to one proposal); nothing catches a model writing a fresh conclusion every turn, and `MAX_ENTRIES`=500 is the only ceiling. The cost is review-queue and retrieval noise rather than safety - every such entry is `pending_approval`, never trusted, never injected at session start, never anchored or armed - and it is recorded as OUTSTANDING-ISSUES item 10 rather than throttled here. **Host coverage** (`host_coverage`/`format_coverage`, `COVERAGE_FIELDS`/`CAPTURE_STATES`/`RECONCILIATION_STATES`) is the honesty surface for what a host can actually see: each adapter owns its own static `EVIDENCE_COVERAGE` map (Claude/Codex/Gemini capture directives and file changes, Cursor captures prompt directives only, `test_result`/`diff_observed` stay `unavailable` while they have no emitter) and this module owns the vocabulary, the `manual` fallback for an unnamed host, and the rendering. The rule is one-directional: a runtime status may DOWNGRADE a field, never raise one - a value outside `CAPTURE_STATES` degrades to `error`, evidence evicted during a pass makes the pass `partial`, and a caller-supplied state is never improved. **`assistant_conclusions` is `model_reported`, never `captured`, on every host**: no host hands a hook the assistant's own response, and `unavailable` is not the same fact as captured-zero, which is why the rendering states a capability and never a count. `reconcile.reconcile_session(..., host=...)` carries the block in its receipt (and its `.reconcile_<slug>.jsonl` line) and `contexer status` prints one `coverage:` line per host.

- **`contexer/spool.py`** - the evidence spool: ONE atomic JSON file per event under `STORE_DIR/evidence/<repo-slug>/` (`pending/`, `held/<candidate-id>/`, `quarantine/`, `.gap`), and **NO LOCKS ANYWHERE**. The property that makes a per-prompt, per-tool-use hook affordable is that the cost of event N does not depend on events 1..N-1: `append_evidence` writes exactly one file and never lists, reads, parses, counts or rewrites the spool. A uuid event id in the filename is what removes writer CONTENTION - two concurrent writers cannot name the same target, so there is nothing to serialize and nothing to lose - and a unique temp file in the same directory plus `os.replace` buys atomicity without a lock. Everything that SCANS (retention, the orphan-hold sweep, temp-debris removal, quarantine moves) runs ONLY from reconciliation or from `maintain_spool`, which is session start, TTL-gated at 24h, and is the sweep that runs INDEPENDENTLY of whether a reconciliation pass happens (it landed as the retention path for an emit-only host, back when Codex and Cursor never reconciled; now that every host does, it still covers the pass skipping on lock contention or returning early, and `_sweep_orphan_holds` has no other caller at all); a hook never scans. That TTL is not only about cost: `_sweep_orphan_holds` judges a held candidate against the LIVE store, where a retired decision is absent - which reconciliation reads as its lifecycle candidate being APPROVED and this sweep would settle as dismissed - so keeping it to once a day is what leaves it a safety net rather than a racing second judge. **Retention ages by the file's MTIME, never by the timestamp in its own filename** (ruling R29): the filename comes from the event's `occurred_at`, which the WRITER supplies, so ordering evictions by it would let content decide retention - a clock-skewed host stamping 2030 would sit at the end of filename order and outlive every honestly-stamped event beside it, while a backdated one would always go first however recently it arrived. The trade-off this accepts is that eviction order (arrival) and listing order (event time) can disagree, so a full spool can drop from the MIDDLE of what a reader consumes; that is the right way round, because listing order is consume ergonomics while retention is about which evidence is genuinely stalest, and only one of the two can be decided by the writer. **Documented residual, named rather than glossed:** the eviction sort is stable, so two files with the SAME mtime keep listing order, which IS `occurred_at` - the very content influence the distinct-mtime case removes. At equal mtimes the spool has no arrival fact left to decide with and a tie-break invented here would be arbitrary; the upgrade path is a monotonic arrival counter stamped at write time, not a cleverer sort. **`.gap` is a CUMULATIVE ledger, not a resettable alarm** (ruling R28): it records what left the spool unconsumed, nothing in this module ever clears it - a successful run does not un-lose an event - and `_read_gap` answers three ways (absent, the mapping, `{"unreadable": True}`) so "no loss ever recorded" can never collapse into "the record of the loss is damaged". A damaged marker is never overwritten with a fresh count of one: the count restarts, but `prior_drops_unknown` is stamped and carried forward for good, which keeps the figure honest as a lower bound instead of quietly reporting `drops: 1` over a marker that had said 47. That ledger is where evidence EVICTION becomes visible to a human: `run_retention` bumps it with the drop count and `contexer status` renders it through `cli._gap_phrase`. **It keeps TWO counts, because "we failed to record this" and "this aged out unconsumed" are different news and only the first is a bug.** `drops` is genuine loss (a failed write; a quarantined event, which is one nothing could read, ageing out); `expired` is a PENDING event ageing out unreconciled, which is not a failure to RECORD anything and so is not a `drop`. Reporting both as `drops` made `contexer status` say "N events lost" about a healthy spool and buried the real failures in the same number, in the one surface built to be honest about loss. **What `expired` MEANS changed when every host gained a session-start reconciliation, and the split outlived its original reason:** it was introduced when Codex reached no reconciliation entrypoint and Cursor emitted directives only, so ageing out genuinely was the queue's designed end on those hosts. Now an `expired` count on ANY host means an event outlived a month of session starts, so it is an anomaly to look into (reconciliation skipping, failing, or never reached) rather than an explanation that settles the question. `spool._bump_gap` and `cli._gap_phrase` both say so; the rendered wording ("aged out unreconciled", never "lost") already carried it. Which counter is bumped is decided by WHICH DIRECTORY was swept, never by anything inside the events - retention must not parse content (ruling R29). `DISPOSITIONS` is likewise only what something actually writes (`approved`/`dismissed`): `edited`/`ignored` were declared with no writer anywhere, which read as exercised code and gave `reconcile._dispositions` two statuses it could accept off a hand-edited `candidate.json` and never produce. A listing includes any file whose name is odd rather than skipping it - in-flight temp files are the only thing passed over: silently ignoring junk would leave it invisible to quarantine AND to retention both, which is how a stray file becomes permanent. **`candidate.json` is deliberately NOT special-cased in the listing itself**, because the name is a held directory's legitimate bookkeeping and a stray one in `pending/` is junk like any other - so it is read, fails validation, and is quarantined, and the held-directory callers that care filter it themselves. `evidence_diagnostics` reports zeros with `readable=False` rather than the partial counts it had gathered when a listing fails - a half-count beside a "could not read" flag is the same unreadable-versus-empty collapse `load_diagnostics` and `_read_global` exist to prevent - and counts `held_unattributed` separately, because a held candidate whose `candidate.json` is missing or unreadable names no `entry_id`, so nothing will ever judge it and it would otherwise accumulate silently. **The manifest is also the candidate STATE MACHINE's durable half:** this module owns manifest persistence (`update_candidate_state` - same-directory temp write plus `os.replace` at 0600, and it REFUSES a manifest that is missing, unreadable or carries an unknown state rather than inventing a phase for it), the read-time legacy migration (`_with_state`), the resume reader (`held_events`), and `discard_empty_hold`, the one removal here that files no receipt - safe only because it refuses the moment a single event file is present. A manifest carrying an unrecognized state is counted as `held_invalid_state` and is exempt from the orphan sweep, for the same reason a missing `entry_id` is: this sweep can only ever say `dismissed`, and a phase nothing understands may be mid-materialization. `spool_slugs()` exists for the one reader with no repo path to resolve: `contexer status` built its repo set from STORE files plus the current-repo pointer, so a repo whose evidence never produced a store entry (every candidate insufficient, or duplicates before any entry existed) had its pending count and its `.gap` invisible in the surface meant to report them. Such a spool is listed by SLUG, which is all there is - a slug does not reverse into a path - and by path as soon as anything knows one.

- **`contexer/candidates.py`** - pure, deterministic grouping and scoring of validated evidence events into decision CANDIDATES. A candidate is a PROPOSAL: the group of events that, taken together, look like one engineering decision worth a developer's attention. It reads events plus a read-only projection of the existing decisions and returns dicts; it writes nothing, imports nothing that does, and its only in-package import is `retrieval`, for the ONE tokenizer this repo has. **The load-bearing property is IDEMPOTENCY, and it comes from IDENTITY:** `candidate_id` is a uuid5 over the candidate's kind, the decision it targets when it names one, and the SORTED contributing event ids, with events read in (occurred_at, event_id) order and candidates returned sorted by (-score, candidate_id) - so the same event set in ANY input order produces byte-identical output, which is what lets `held/<candidate-id>/` BE the "already pending" record and lets repeated reconciliation be a no-op. A `uuid4` in this module is a defect. Kind and target join the event ids in the hash because they are what the candidate PROPOSES: the same events read as "update the auth decision" and as "retire it" are two different proposals, and one directory could only ever hold one of them. **`score` is an AGGREGATION-RANKING INPUT, never a confidence that a statement is TRUE** - 50 for a user directive means "a developer said this out loud, put it near the top of the review queue", not "50% likely correct" - and nothing here approves, enforces, retires or materializes anything: the review flow is the only gate. Every event in a group gets a signal row, weight 0 included, because the row is the audit trail for why the candidate exists and dropping the zero-weight ones would make a corroborating event that scored nothing indistinguishable from one that was never seen. A red test run scores 0 rather than corroborating, since a failing run is evidence the behaviour is NOT settled. `_subtype_for`, `_has_rationale` and the negation regex are documented PROXIES, not classifiers: they pick a retrieval bucket and a rank, and the developer rules. **Three linear scans are INDEXED, with output frozen exactly as it was.** Seed merging counts token overlaps through per-token postings over the groups (`_shared_counts`) instead of re-tokenizing both sides of every pair; support attachment is handed the event's own session bucket instead of the whole run (the cross-session-attachment ban expressed as a lookup rather than as a test repeated per pair); and the stored decisions are tokenized ONCE per call (`_decision_index`) instead of once per candidate that asks. Each surviving pair is judged by the same expression against the same constants - `|A∩B| / |smaller|` against `_MERGE_OVERLAP` / `_CONTRADICTION_OVERLAP` - with one exact algebraic short-circuit (`2 * shared <= smaller` cannot clear the lower bar). **First-match-in-group-order survived by being restated as a MINIMUM**, which is what makes it computable from an order-free scan: the old loop returned the first group above the merge bar and fell back to the first polarity-flipped group above the contradiction bar only when NO group anywhere cleared the higher one, so the answer was always the lowest qualifying index of each kind. Tracking the two minima is order-independent, and it has to be: the postings are walked in set-iteration order and `str` hashing is randomized per process, so a version that took the first hit would answer differently between runs of the same corpus (pinned by `test_the_answer_does_not_depend_on_the_order_the_postings_scan_yields`). Equivalence is proven rather than asserted - `tests/test_candidates.py` keeps a running copy of all three replaced scans and compares the COMPLETE returned dict over randomized event permutations, and the frozen goldens in `tests/test_evidence_hardening_replays.py` are unchanged. Measured at the spool's `_MAX_PENDING_EVENTS` bound (aggregation alone, three-run median after warm-up): 1,000 mutually distinct statements 2667.67ms → 106.45ms, 1,000 boilerplate ones 8.65ms → 8.26ms, a realistic session 30.57ms → 5.68ms. **This is still O(N^2) in the worst case** and the bullet says so on purpose: the 1,000 distinct statements share four ordinary words, so every pair IS counted - what fell by ~25x is the price of a pair, not the pair count. A pair sharing no token now costs nothing at all. **Every signal row carries a TYPED relationship** (`relation` from the closed `RELATIONS` vocabulary, plus a `certainty`), because a weight of 0 alone cannot tell a corroborating event that scored nothing from one that merely happened nearby. Grouping runs in TWO passes - all seed groups first, then support - so a link no longer depends on which of a statement and its edit the developer did first: an edit is `structural` when it touches a file the group carries OR one the SEED NAMES IN ITS OWN TEXT (both directions in time), `causal_forward` when a fileless seed was followed inside `_PROXIMITY_SECONDS`, and `temporal_backward` when only that window connects them. **A `temporal_backward` link is always `uncertain`, always worth zero, and never consumes its event**: its path lands in `possible_source_files` (never `source_files`, never an anchor, never a policy or guard input) and the event ALSO stays in the leftover set, so the "files changed with no stated decision" gap it failed to explain is still reported. Cross-session temporal attachment is forbidden outright. When several groups qualify the pick is deterministic - strongest relation, shortest absolute time distance, lowest seed event id. **A merged seed is a `contradiction` only when its negation POLARITY differs from the group's** (ledger ruling D1): `_negates` matches a bare negation word, so a prohibition restated verbatim used to be charged -30 for contradicting ITSELF and sank below the review bar, while the same rule phrased affirmatively was corroborated; a near-verbatim REVERSAL still flips polarity and is still charged. One consequence of the two passes, stated because it is visible: a group's `signals` read statements-first then support rather than in strict wall-clock order. Nothing scores off that order. **The aggregator refusing to anchor a path is not by itself enough, because the store has a SECOND route to the anchor pipeline.** `store.update_decision_with_meta` stashes the recently-edited-files sidecar as `anchor_candidates` on a new pending entry, and `store._EDITED_FILES_WINDOW` is the same 1800 seconds as `_PROXIMITY_SECONDS`, written by the same `post_write` call that emits the `file_changed` event - so on Claude and Codex every `temporal_backward` path was guaranteed to be a fresh sidecar entry when reconciliation materialized the decision, and landed on it as an anchor guess a developer could bless (caught in review; invariant 6 survived only on the human gate). `reconcile._materialize` therefore passes `anchor_candidates=` the candidate's own CONFIRMED `source_files`, and that argument REPLACES the sidecar read, empty list included - a caller that knows which files its capture is about can say so more truthfully than a time window can. Every other caller passes nothing and keeps the sidecar accrual exactly as it was.

- **`contexer/reconcile.py`** - the one coordinator in the evidence pipeline: it reads the spool, scores what it finds through `candidates` (pure), and materializes the result through the store's ORDINARY capture path, so novelty filtering, revision construction, capacity limits and the pending-review flow all still apply. Above store rather than beside it - `store.py` never imports it, and store-owned helpers are read through the store module OBJECT at call time. **Everything it creates is REVIEWABLE by construction.** A new candidate lands `pending_approval` via `force_pending` and NEVER the `suggested` tier an `ai` capture would otherwise get, because `suggested` injects at session start yet never appears in `review_pending`: trusted without ever having been offered for review. An update lands as a `proposed_revision` on its target with HEAD unmoved; a retirement or replacement lands as a `proposed_lifecycle`, which retires nothing - only an explicit human `lifecycle.retire_decision` moves a decision out of active context. **The same discipline governs the way back out:** a held candidate is settled `approved` ONLY against real review evidence - a human ratification stamp (`approved_by == "human"`, which is what covers a brand-new pending entry, since approving one blesses revision 1 in place and no revision advance is visible), a content proposal whose revision actually advanced, or a decision genuinely retired into the tombstone sidecar CARRYING a retirement record (presence in the sidecar is not enough: a legacy tombstone records nothing about why the decision left). **For the LIFECYCLE lane a revision advance is never an approval signal** (ruling R25): retirement is a MOVE, so an unrelated content edit that happened to advance HEAD would otherwise record a retirement that never occurred - the same fabricated-approval class, polluting the very disposition signal this pipeline exists to measure - which is also why a lifecycle hold stores no `revision_id` at all rather than storing one a reader might use. A candidate that was already settled when it was held keeps the status its `candidate.json` recorded, never one the rules below it would infer; a hold naming no `entry_id` is left alone rather than guessed at, surfaced instead through `evidence_diagnostics`' `held_unattributed`. **Idempotency is the HOLD, not the store's novelty filter:** a materialized candidate's events are moved out of `pending/` into `held/<candidate-id>/`, so they never reach the aggregator again, and the directory itself is the record that the candidate awaits review; the novelty filter is only the backstop for a hold that failed to complete. **Candidate processing is an explicit STATE MACHINE, and the phase lives in the hold's own `candidate.json`** (`spool.CANDIDATE_STATES`), so every crash boundary is replayable rather than reconstructed by inference: (1) write the complete manifest in `held`, (2) move every named event, (3) VERIFY the move, (4) flip to `materializing`, (5) write through the ordinary store or lifecycle path, (6) re-read the store and persist `pending_review` or `settled` from what it OBSERVES rather than from the write's return value, (7) record the evidence summary after review, (8) persist `reviewed` with the disposition, (9) only then remove the directory. **HOLD FIRST, materialize second** - the reverse (shipped until the durable-state work) left a window nothing on disk covered: a crash after the store write and before the hold left a decision whose evidence was still in `pending/`, connected to it by nothing. Now a crash leaves the evidence either wholly pending (the next pass aggregates it again under the same deterministic id) or wholly held behind a manifest that names both what it claims and how far it got. `_resume_holds` carries each interrupted phase forward: a `reviewed` hold gets its raw cleanup finished with no second summary, a `held`/`materializing` one has its OWN held events re-classified against the CURRENT store and materialized under the SAME candidate id - so a decision the interrupted pass already created comes back as a `duplicate` of itself instead of being written twice - and a hold holding no events at all (its events claimed by a racing pass, or a manifest write that never landed) is discarded rather than occupying its candidate id forever. A partial move is still finished from the manifest's recorded `event_ids` (`_finish_interrupted_holds`, which runs BEFORE any resume) rather than re-aggregating the remainder into a SECOND candidate under a different id. The window is closed but its recovery stays, because the store's own dedup and legacy holds from the old order still produce a candidate duplicating a decision nobody has reviewed. **Legacy manifests migrate on READ, never stranded** (`spool._with_state`): no `state` means a recorded disposition reads as `settled`, a named `entry_id` as `pending_review`, anything else as `held`; only a manifest that is corrupt or carries an UNRECOGNIZED explicit state is the diagnostics-incomplete case, and such a candidate is never resumed, swept or deleted. **A candidate nothing can file a receipt against is never finalized either** (fix round 1): `_finalize` distinguishes an `entry_id` that never existed - the store's status-blind dedup absorbed the capture as a recurrence and returned no id - from one that no longer RESOLVES, because only the second means the receipt has nowhere to go and retrying is futile. The first keeps its evidence held and unattributed rather than deleting acknowledged evidence with no record anywhere (runbook invariant 3). **A lifecycle refusal is likewise not one fact**: `propose_lifecycle` returns the same `ok: False` whether the target is gone, is not live, or is already carrying a retirement proposal - and in the last case (routinely the candidate's OWN proposal, met by a resume replaying an interrupted pass) a review IS pending, so the evidence is held against it and `_dispositions` settles it on the real outcome. Reading them as one fact filed a `dismissed` receipt against a live proposal and deleted the evidence. **A hold that reports `missing` is never finalized.** `spool.hold_candidate_evidence` REPORTS a source gone with no target rather than raising and hands the decision to the caller; deciding means refusing, because finalizing writes an `evidence_summary` saying this event set settled, and a hold that could not account for its events has not earned that receipt. The recorded status stays on the hold, the receipt says `incomplete`, and a later pass settles it. **One pass at a time per repo** (`_reconcile_lock`): two overlapping passes each snapshot the live decisions before classifying, so a store write landing between one's snapshot and the other's classification changes the `kind`/`target` it computes for the same events, hence their `candidate_id` - and it then files a disposition under its own entry for a review that never happened. **EVERY host reconciles at session start**, and Claude and Gemini add their own compaction and session-end checkpoints on top, so two passes on one repo is ordinary rather than exotic. That session-start pass is ONE call on the store-side path all four hosts traverse (`store._local_session_start_payload`, immediately after `spool.maintain_spool` and BEFORE the store is read, so anything it proposes reaches the same session's pending-review count instead of the next one's) - which is what closed OUTSTANDING-ISSUES item 1 for Codex and Cursor, who had no reconciliation entrypoint at all, and for Gemini, which had none at session start. It passes `session_id=""` deliberately: the evidence worth recovering is precisely the evidence of a session that ENDED without a checkpoint, and scoping the pass to the starting session would skip it forever. Claude consequently reaches reconciliation TWICE per session start (`sync_memory`, then the shared path) and that duplicate is kept HARMLESS rather than suppressed - the first pass moves the events into their holds, so the second finds no work, returns before reading the store or taking any lock, and costs two directory listings (measured 0.04ms). No skip marker anywhere: a marker is exactly what would suppress work after a crash. The status line stays silent on a `complete` or `skipped` pass and carries one sentence on `partial`/`error` (`store._reconcile_note`), because acknowledged evidence that went unaccounted for is what runbook invariant 3 requires to stay visible - never candidate content, which reaches the developer through the review queue. The call site is UNGUARDED, on the strength of the never-raises contract and for a reason: a try/except there would swallow that very diagnostic. A NON-BLOCKING `flock` (never a marker file, which a crash would leave wedging the repo for good): a pass that finds it held SKIPS entirely and says so in its receipt, and the next checkpoint picks the work up. It is taken only AFTER the fast path finds work, the unlocked-then-locked shape `ensure_retrieval_index` uses - this runs at every session start on every repo, so locking first would create (and `mkdir` for) a lock file on repos that will never hold one evidence event, and the listing under the lock is the authoritative one anyway, since a pass that finished meanwhile may have consumed exactly what the fast path saw. **This is not the spool's "no locks anywhere" rule**, which governs evidence WRITES FROM EDITOR HOOKS - reconciliation is the scanning consumer, already takes the store lock to write, and can afford to skip. Failing to open the lock at all fails OPEN, since it is contention this answers and not I/O; a dry run is never gated by it, because it writes nothing and taking the lock would itself create a file. **`dry_run` writes NOTHING anywhere** - no store write, no hold, no manifest, no state update, no finalize, no retention, no receipt line, no disposition. With the hold moved in FRONT of the store write the gate is now ONE early return in `_materialize`, taken after the candidate is counted and before the first write of any kind, so every lane (content and lifecycle alike) is covered by the same check rather than by a wholesale discard plus a per-lane guard; `_run_pass` additionally skips `_resume_holds` outright, since resuming is a write. A future lane must sit BELOW that return, not beside it. The pass receipt is LOGGED, never spooled (ruling R34): a receipt spooled into `pending/` was never held, so it aged out through retention, which counts every drop in `.gap` and made `contexer status` report "N events lost" on a repo that lost nothing, in the one surface built to be honest about loss. It goes to `.reconcile_<slug>.jsonl` on the `.retrieval_<slug>.jsonl` precedent - tail-capped, fail-soft, never user-facing - and a pass that did nothing logs nothing, so a repo with one stuck held candidate does not write a line per SessionStart forever.

- **`contexer/policy.py`** - the policy-evaluation vocabularies, request validation, pure policy SELECTION and pure JUDGING. A LEAF: stdlib plus `redact` for the secret patterns, no store, no `guard_engine`, no filesystem, no subprocess, and **no clock** - it owns no time budget and no fail-open/fail-closed policy, it reports what it judged and what it could not and the CALLER decides what that means, because a commit gate and a read-only prompt hook want opposite answers from the same `partial`. Judging lives here and ONLY here: `guard_engine` owned it first, against staged git files, and now delegates (`policy.validate_check` at arm time, `policy.evaluate_policies` at run time) so the armed regex, the `i` flag, the glob and the secret scan each exist once. Two sharply separated paths, inherited from the guard: ARM TIME raises, because arming is a deliberate developer act that must fail loudly rather than degrade into a rule that silently never fires; RUN TIME never raises for bad DATA - an unparseable pattern or an unknown check type comes back as an `unchecked` reason. **Every `unchecked` row is a check that DID NOT HAPPEN and must never read as a check that found nothing**, which is why an armed policy facing a request with NO artifact is `omitted` rather than passing, why a caller's malformed gap row RAISES rather than being dropped, and why an internal failure lists the policy it broke on AND every one after it as `evaluator-error` instead of leaving an empty list beside a broken run. An ARMED policy is machine-checked and may `block`; an ADVISORY (prose) policy may only ever `warn`, enforced in `_match` through `MAX_VERDICT` rather than merely documented - a prose decision that could block would turn every approved opinion into a commit gate. `policy_set_version` names the exact set that answered so a logged verdict can be tied to the policies that produced it. Its request bounds MIRROR `evidence.py`'s path rules and 300-char caps rather than sharing them, and the copy is forced rather than lazy: `evidence.py` imports store and this module cannot, so hoisting the rules into a third module would be an interface with two callers and no behaviour of its own. Change one side's path rules, change the other. **Tier 1 gates on provenance TRUST while Tier 2 gates on the explicit ARMING gesture, and the two must NOT be unified.** `select_policies` gates on `is_trusted`, a MIRROR of `guard_engine._guard_trusted` restated rather than imported (that module imports store, this one cannot; a parity test pins the two equal) - that is Tier 1's rule. Tier 2 selects through `guard_engine._armed_rules`, approved AND explicitly armed, because arming is itself a more deliberate act than approval. Routing Tier 2 through the trust gate would silently stop firing rules a developer armed BY HAND, and such decisions arise through ORDINARY CAPTURE rather than only legacy migration (ruling R42): `store._classify_level` returns `auto` for content matching `_SCAN_FACT_PATTERNS` and `_level_to_status` maps `auto` to `approved`, so an `ai` capture whose text merely LOOKS like a scan fact is born approved with revision source `ai` and no `approved_by` stamp, and `arm_guard` gates on approved status alone and accepts it. Nothing in the suite seeds an armed untrusted entry, so unifying the two gates would have been a silent kill rather than a caught one - see `guard_engine._armed_policy`'s docstring, which is where a future reader will be standing when they consider it.

- **`contexer/policy_api.py`** - the repo-scoped facade: the ONE place an operation becomes a policy answer. `policy.py` judges a request against policies somebody else already loaded; the four steps in front of that (resolve the repo, load the participating decisions from the repo store PLUS the global one, select, evaluate) are identical for every general caller, and there are two - the `evaluate_policy` MCP tool and `contexer policy evaluate` - so they exist here once, on the `console_api.py` precedent: a thin layer ABOVE store, store-owned helpers read through the store module OBJECT at call time, one-way dependency (`server.py`/`cli.py` -> `policy_api` -> `store`/`policy`, never back). `policy.py` cannot host any of it, because a store import there is exactly what its purity buys. **`guard_engine` is deliberately NOT a caller:** it is the GIT adapter over the same evaluator and owns things this layer has no concept of - staged paths, throttle sidecars, a wall-clock budget - so routing it through here would mean teaching this module about git rather than sharing anything real. **BOUNDS** are `policy.validate_request`'s, applied HERE at the chokepoint every caller funnels through, the same shape `remote.bound_source_files` has: a surface schema only covers the callers that go through that surface. The one bound a surface applies for itself is the CLI's read of a diff file, which has to stop before the bytes are in memory, and it reads `policy.MAX_ARTIFACT_BYTES` rather than restating the number. **REDACTION IS EGRESS-ONLY, at the render boundary only:** `format_result` and `scrubbed_result` scrub because rendering is where a secret leaves, nothing scrubs the artifact on the way IN (a `secret` check that sees redacted bytes detects nothing, which is the whole point of `redact.py`'s egress-only rule), and nothing mutates the structured result the caller holds - the result is authoritative, the text is a rendering. **Scrub the leaves and THEN encode, never encode and then scrub the document:** JSON escaping rewrites `"` as `\"` and redact's keyword-gated generic pattern matches a QUOTED value (`password="s3cr3t"`), so scrubbing the encoded text silently stops detecting exactly that class while still looking like it works - the high-confidence provider patterns are quote-independent and keep matching, so a test written against an AWS key passes either way (caught in review; the earlier code dumped and then scrubbed).

- **`contexer/review_impact.py`** - the ONE interpretation the three review surfaces share: what approving a pending decision would actually do. `review_pending` (MCP), `contexer review` (CLI) and the console's `dashboard_summary` each used to decide for themselves what a decision's evidence, files, history and enforcement effect were, which is how one decision could read as `would anchor: src/a.py` in the terminal and as nothing at all in the console. `review_impact(repo, entry, context)` returns the structured block (identity, priority, evidence, files, coverage, related, history, revisions, policy, diagnostics) and `impact_lines(impact, seen_coverage=None)` renders it; both text surfaces print the SAME list and the console consumes the same dict, so agreement is the only code path they have rather than a convention they keep. A leaf: it imports `store` as a module object, reads `spool`/`evidence`/`adapters`/`guard_engine`/`lifecycle`/`conflicts` at call time, and nothing calls back into `store.py`, `cli.py` or `console_api.py`. **Nothing here writes.** The block exists to be read BEFORE a signature, so a surface that acted while describing would be describing its own side effects; `_armed_rule` REPORTS a rule through `guard_engine._armed_rules` (the selector the commit-time guard itself runs, so the preview cannot claim a rule is inert that the guard would fire) and there is no path from approval to arming - which is the sentence the default preview makes, pinned by `TestInvariants::test_approval_never_writes_an_armed_policy_rule`. **`possible_source_files` surface here and ONLY here** (Task 07's carve-out of the structural invariant in `tests/test_evidence_hardening_replays.py`): Task 04 keeps them off every proposal, so the candidate manifest in the spool is the last place they exist, and a reviewer who is never told a path was considered cannot catch a wrong one either. They render under `Possible files: ... - NOT anchored on approval; the link is uncertain`, they are filtered out the moment the same path is confirmed, and `anchor_confirmation` - the line the CLI prints immediately before it approves - names the CONFIRMED files only. **Costs are per RENDER, not per decision:** `review_context(repo, decisions=None)` does one store read, one `spool.held_candidates` listing and one `adapters.detect()` for a whole queue, and the console hands in the decisions it has already loaded on its 10-second poll. `seen_coverage` exists for the same reason: capture coverage is a property of the installed hosts, identical for every decision in one payload, so the MCP list prints each host's line once instead of 25 times while the interactive surfaces (one screen, one card) print it every time. **The displaced-candidate diagnostic** closes Task 04's ledgered residual: a held reconsideration candidate at a DIFFERENT `basis_revision_id` than the question on screen can never be settled by the answer being given, and it is invisible to `held_unattributed` (which counts holds naming no entry), so `_displaced` names the decision and the stale basis in the review block itself. `ORIGIN_LABELS` moved here from `cli._ORIGIN_LABELS` on the same rule - three surfaces render it now.

- **`contexer/conflicts.py`** - conflict rendering + resolution memos (issue #193), extracted out of store.py on the same directive that produced `anchors.py` (one module per cohesive concern; `store.py` stays a thin call-site facade). Owns `_CONFLICT_GUIDE`, `_conflict_pair_key`, `_has_open_conflict`, `_conflict_view`, and `record_conflict_memo`; store-owned helpers (`title_and_body`, `_current_revision`, `_current_content`, `_normalize_content`, `store_lock`, `repo_slug`, `load`, `save`, `entry_by_id`) are read through the `store` module OBJECT at call time - the identical load-order discipline `guard_engine.py` documents, so a test monkeypatching `contexer.store` is still seen here and store.py never needs this module at import time. **A live decision carrying a Suggested Update (`proposed_revision`) that is neither scan/`clear_anchors`-sourced (bookkeeping, not a conversational conflict - those keep the pre-existing flag-only `[update pending approval]` tag, since they re-propose on every 24h TTL cycle and "only the developer knows" is backwards for evidence-driven withdrawals) nor title-only (`_normalize_content`-equal to the current content) is an *open conflict*** (`_has_open_conflict`, the shared gate predicate) and renders BOTH the standing content and the labeled unreviewed update, with dates, at all four model-facing render sites - `get_context`, `_render_prompt_decisions`, the session-start project-rules loop, and `_rehydrate_working_set` (so the conflict survives post-compact rebuild) - via `_conflict_view` (replaces `title_and_body` at those sites only, proposal-side title read from the proposal's own `title`, never the standing entry's). `_CONFLICT_GUIDE` ("don't resolve via codebase exploration - only the developer knows; ask, then record with `resolve_conflict`") renders once per call whenever any shown entry has an open conflict, not once per entry. **`resolve_conflict(entry_id, choice)`** (the MCP tool → `store.record_conflict_memo`, reachable on the facade through store.py's SAME lazy PEP 562 `__getattr__` block that re-exports guard_engine's entrypoints - the private helpers are deliberately NOT re-exported, so `cli.py`'s review branch imports this module directly for `_conflict_pair_key`) records the developer's EXPLICIT in-session pick as an on-entry `conflict_memo` (`{pair, choice, session_id, created_at}`, precedent: `superseded_proposals`) keyed by `_conflict_pair_key` (sha1 of the resolved current revision id + the proposal's content/title/`created_at`) - the `created_at` component is what stops an identical-content proposal rebuilt after a non-revision-advancing pop (e.g. `verify_scan_conventions`) from reviving a dead memo. `record_conflict_memo` is lock-guarded like `approve_decision`, requires an 8-char-minimum id (renders always emit 8-char ids; prefix resolution is first-match-wins), requires a render-eligible (non-scan, non-title-only) proposal, and writes none of `status`/`approved_by`/`source_files`/`anchor_commit` - so a memo can never arm the commit-time guard. The memo is deliberately **asymmetric**: `choice="standing"` fully hides the update (unreviewed content may be hidden by anyone); `choice="update"` makes the proposal operative but keeps the standing version as one demoted continuation line, since reviewed (human-approved) content may only ever be fully hidden by a review action (`store._apply_approval`'s promote/dismiss are the only two sites that pop the memo - every other proposal-death site leaves it as an inert orphan, harmless because `_conflict_view` early-returns on no-proposal). `store.format_pending_review` and `contexer review`'s terminal proposal branch both render the memo as a per-choice steer note beneath the `detected:`/`Detected:` line, phrased in the same picked/declined vocabulary as the model-facing markers and naming BOTH actions' consequences, so `approve` can't be misread on a declined pick (`the update was picked with the developer on <d> - approve to formalize (dismiss drops it)` vs `the update was declined with the developer on <d> - dismiss to formalize (approve applies it instead)`). Retrieval reachability stays in store.py: proposal content folds into `matches_query` and the BM25 index's doc tokens (`_build_retrieval_index`), so a decision is findable by the update's own terms before anyone resolves the conflict.
- **`contexer/console_api.py`**: local-console read projections, every shape the `contexer ui` console renders for one repo, one store, or the global rules (`list_stores`, `resolve_store`, `resolve_store_slug`, `store_summary`, `dashboard_summary`, `list_decisions`, `get_decision_detail`, `list_tombstones`, `list_global_rules`, `delete_global_rule`, `team_snapshot`, `overlap_report`, plus the `_console_*` row/diff projections and `_read_store`). Extracted out of store.py on the same directive that produced `anchors.py` and `conflicts.py` (one module per cohesive concern), and **the boundary was measured rather than chosen**: `contexer/ui/api.py` is the only production caller and it reaches for exactly those names and nothing else, while the rest of store.py called into the cluster exactly ONCE. That single back-call (`file_mtime`) is store-owned and stayed, so store.py has **no call site into this module at all**; the dependency runs one way only (`ui/api.py` → `console_api` → `store`), which is what makes it a read/query layer for a web UI rather than part of the capture store. **That one-caller property is load-bearing, which is why `overlap_report` stayed in store.py** even though it sat inside the same line range: it has no console consumer at all (its only caller is `contexer review`'s terminal output via `cli._print_overlap_section`), it carries its own thresholds, and it reads store internals rather than projecting an entry for display. It was moved out and then moved back when review caught the claim, and the episode is the rule: adjacency in a file is not a boundary, and anything added to `console_api.py` must have a console consumer or the one-caller claim stops being checkable. The console must never open a store file itself (the same one-write-path rule the MCP surface follows), so when a shape the console needs does not exist yet the fix is a new public read HERE, not a file read in `ui/api.py`. Everything is a PURE READ except `delete_global_rule`. **Three things deliberately did NOT move**, each for a reason that would have been invisible after the fact: `load_diagnostics` is the third of a family with `global_diagnostics` and `deleted_diagnostics` (both store-owned, and `ui/api.py` calls `global_diagnostics` directly), so splitting one off would scatter the trio; `store_files`/`_is_repo_store_file` enumerate which files in `STORE_DIR` are repo stores, which is store-level knowledge `scope_audit.py` depends on by documented contract; and `file_mtime` is read by `store.verify_scan_conventions` and `anchors.py` as well as here. Store-owned helpers are read through the `store` module OBJECT, not `from`-imported, the identical load-order discipline `guard_engine.py` documents, so a value a test monkeypatches on `contexer.store` (the `tmp_repo` fixture patches `STORE_DIR`; `test_ui_cli.py` patches `GLOBAL_SLUG`) is still seen at call time and store.py never needs this module at import time. **The public reads stay reachable as `store.<name>`** through store.py's lazy PEP 562 `__getattr__` (`_CONSOLE_EXPORTS`), as **back-compat only**. They were re-exported wholesale on the argument that `store` is this package's published surface and that the suite reaching them that way keeps the facade exercised. **Measurement retired that argument**: across all three export sets, one name of seventeen had a production consumer through the facade (`server.py`'s `store.record_conflict_memo`, since repointed at `conflicts`), every other production caller already imported the owner, and `store.py` has no `__all__`, so nothing mechanically backs the published-surface claim. The facade is how the TEST SUITE addresses this code, and covering it proves only that the shim resolves. So it is frozen under the first module-boundary rule below, and `team_snapshot`, which had no consumer of any kind, was dropped from it. Production consumers still import the owner directly (`ui/api.py` calls `console_api.<name>`), which is what keeps the one-consumer boundary visible. **The projections' own tests deliberately stayed where they were**: the 14 blocks that call these reads are each testing store-level behaviour (sidecar corruption, slug addressing, poll cost) and merely OBSERVE it through a console read, so moving them would have separated, for one example, a global-store corruption test from the global-store test file. `tests/test_console_api.py` therefore pins the seam this extraction created instead: facade resolution and `dir()` parity, first-import-in-either-order (checked in a fresh interpreter, since an already-imported package hides an ordering bug completely), nothing left behind as a second definition in store.py, and call-time lookup of store-owned names. Those last two were mutation-checked (removing the facade branch, and binding the store globals at import time, each fails exactly the tests that claim to cover it).
- **`contexer/scope_audit.py`** - cross-store scope audit: finds decisions saved into the WRONG repo's store (see "Wrong-store writes" under Storage). The fingerprint needs no heuristic - **one session id appearing in more than one repo store**. A session belongs to one project, so decisions from it landing in two stores means at least one of those stores is wrong; that is exactly how the original case was found, and every entry already carries the field. Only the ORIGINATING `session_id` counts, never `session_ids` - the latter accumulates every session that has TOUCHED an entry, so a recurrence recorded from a second session is normal and would otherwise read as a misroute. Two exclusions keep it from crying wolf, both found by running it against real stores rather than reasoned about: **the store-file set comes from `store.store_files()`, never a local re-glob** - `<slug>.deleted.json` tombstones carry the same `{"repo_path", "entries"}` shape as a real store, so a hand-rolled "skip dotfiles and `_global`" filter reads a repo's deleted decisions as a SECOND store for that same repo and tells the developer to re-capture a decision they deliberately deleted; and **memory imports never participate** (`_is_memory_import`) - `memory_sync` stores an unattributed fact under the LITERAL id `"memory-sync"`, so every repo that ever imported one shares that id and pairs with every other such repo forever, and even a real `originSessionId` records where the FACT came from rather than which repo a writer targeted. That second exclusion is detected three ways (`created_by`, `memory_key`, the sentinel id) because entries are read RAW here, without `load`'s migration - which is also why the per-entry title derivation is individually guarded AND every rendered field goes through `_text()`: a raw field can be a JSON null (`.get(k, "")` returns `None` when the key EXISTS with a null value, which then blows up the timestamp sort and every slice in the report), a number, or a list, and a read-only command must never exit on a traceback. The global store never participates (cross-repo BY DESIGN), and a corrupt store contributes nothing rather than raising. **A store FILE is not the unit of identity** - `_repo_identity` groups by `os.path.realpath(_canonical_store_key(repo_path))`, because a pre-fix stray worktree store sits beside its canonical file until that repo's next session start folds it in (`migrate_worktree_strays`), and counting both would report a correctly-scoped session as split. The `realpath` on top is load-bearing rather than defensive: a main worktree fast-paths out of `_canonical_store_key` with its path unchanged while a linked worktree goes through `git rev-parse --path-format=absolute`, so under a symlinked root (`/tmp`→`/private/tmp`) the two canonical keys differ by that prefix alone and would not merge. A store whose own `repo_path` is unreadable stays keyed by its file rather than being merged blindly. **Known limit, labelled rather than papered over:** this can only merge a worktree that still EXISTS - once the directory is removed or pruned there is no `.git` file to read and `git worktree list` no longer enumerates it, so nothing on disk ties the stray back to its main worktree (`migrate_worktree_strays` cannot fold such a stray either, for the same reason) and merging would mean guessing from path shape, which worktrees do not constrain. That store is therefore rendered with a `(path no longer exists - a removed worktree or deleted checkout)` note so the row explains itself, and `_exists` is fail-soft so an unstattable path (dead mount, permission wall) is never accused of being gone. **The report states a question, not a verdict**: the fingerprint is a WRITE-SESSION id, and for MCP captures that is `server.SESSION_ID`, a uuid4 minted per server PROCESS - so a developer who deliberately captured into a second repo by naming it, or a host reusing one server process across workspaces, produces this exact shape with nothing wrong (`[via argument]` is the tell). It caps at `_MAX_ENTRIES_SHOWN`=10 per store with a `showing N of M` note, like every other human-facing surface here, and its remediation names `approve_decision(action="ignore")` or the console - deliberately NOT `contexer review`, which lists only decisions still PENDING in the CURRENT repo while a misrouted decision is normally already approved and in another one. Each reported entry carries its stamped `repo_source`, so a deliberate cross-repo write (`argument` - a developer named the repo) is distinguishable at a glance from a misrouted one. **Read-only, and staying that way:** moving an entry rewrites where a decision is recorded as having been made, and this module can tell only that two stores disagree, never which one is wrong - so it reports, names the files, and stops, per the same informed-signature rule the anchor backfill already established. Surface: `contexer scope-audit` (no arguments; anything else exits 1 rather than being ignored, the `guard anchors` rule so a read-only-sounding flag can never read as consent). A leaf module: imports `store`, nothing imports it back.
- **`contexer/miner.py`** - deterministic convention mining, stdlib only (`ast`/`tomllib`/`re`/`configparser`/`subprocess`). `mine_conventions(repo_path) -> list[dict]` (`{"content", "subtype": convention|pattern, "tier": high|medium}`) measures conventions with whole-repo evidence embedded in the sentence itself ("Functions use snake_case naming (98% of 412 functions across 37 files)"): config-encoded rules (ruff line-length/quotes, mypy strict, pytest coverage floor, .editorconfig, pre-commit hook ids via regex, prettier/eslint/tsconfig-jsonc, CI `run:` lines), AST source statistics (naming dominance, type-hint/docstring coverage, absolute-vs-relative imports, custom exception classes, bare-except absence), test conventions (layout, naming pattern, plain-assert vs unittest dominance, fixture count), and commit-message convention (Conventional Commits % over the last 100). Thresholds are the verification story: ≥90% dominance with ≥20 samples → tier high, 60–89% → medium, below either bar → not emitted (silence over noise); presence detectors need ≥3 occurrences. Caps: ≤400 .py files, ≤200KB/file, ≤2000 dirs; skips `_SKIP_DIRS` and ALL dot-directories (tool state like `.claude` worktrees would poison the statistics). Never raises; never emits `subtype="constraint"` (scan-sourced entries bypass the constraint→pending rule in `_classify_level`). A leaf module: imported by store.py, never imports it (own tiny `run_git`). JS/TS/Go/Rust *source* stats are deliberately out of scope - their conventions are captured via configs, which is the verified path.
- **`contexer/redact.py`** — deterministic secret redaction, stdlib only (`re`). `scrub(text) -> (redacted_text, count)` (plus `scrub_text` / `count_secrets` convenience wrappers) replaces each detected secret with `[REDACTED:<kind>]`. **Balanced** detection: high-confidence provider token shapes (AWS `AKIA/ASIA`, GitHub `gh*_`/`github_pat_`, Slack `xox*`, Stripe `[sr]k_live_`, Google `AIza`, OpenAI/Anthropic `sk-`/`sk-ant-`, SendGrid, `npm_`, `pypi-`, Twilio `SK`), PEM private-key blocks, JWTs, `Bearer` tokens, and connection-string passwords, PLUS a keyword-gated generic catch-all (`password|secret|token|api_key|access_key|client_secret|private_key|auth …[:=] value`) that redacts the value only when it **looks secret-like** (`_looks_secretlike`: ≥6 chars AND not a plain lowercase word / hyphenated phrase) and **skips placeholder-ish values** (`<…>`, `***`, `env(…)`, `${…}`, empty). The prose gate is deliberate: without it the catch-all mauls ordinary decision text like `auth: required` or `token = short-lived` (known tradeoff: an all-lowercase passphrase reads as prose and is missed — provider patterns still catch real API keys, and not corrupting stored decisions wins). No entropy heuristic (rejected — would false-positive on SHAs/UUIDs/base64). **Idempotent** (the `[REDACTED]` placeholder never re-matches) and **never raises** (any failure degrades to best-effort). A leaf module: imported by `store.py` and `remote.py`, imports neither. **Redaction is EGRESS-ONLY by deliberate design** — capture is NOT scrubbed, so the local store stays a faithful, verbatim record of decisions (scrubbing local `0600` files buys little when the real secrets sit in `~/.aws`/`.env`, and a redactor that silently rewrites captured decisions would corrupt the product's core value). Secrets are removed only where a decision actually LEAVES the machine: **`remote._wire_args`** (the last-mile every push/batch/drain funnels through → the hard guarantee no secret reaches the remote MCP), plus **`store._share_projection`** (so the confirm-preview + durable outbox show exactly what will be sent), with `format_share_preview` surfacing a `(N secrets redacted before sending)` banner. Honors a `_redaction_enabled()` fail-soft toggle reading `config.redact_secrets` (default **True** — safety holds unconfigured; opt out with `redact_secrets = false`). The flag is resolved **once per operation** and threaded down, never re-read per element: `get_shareable`/`get_shareable_all`/`_share_projection` and `remote._wire_args` all take a `redact_on` param (None = resolve locally), the batch `apush_decisions` resolves it once for the whole batch, and `format_share_preview` resolves the profile once (governing both endpoint and redaction) so an explicitly-passed profile's `redact_secrets` is honored rather than a fresh global config read. `RemoteStore._redact_on()` likewise honors the `Profile` the store was built from (`from_profile`) — an explicit opt-in must not be lost to a global opt-out on disk — falling back to the global config only for a profile-less (directly-constructed) store. The generic keyword catch-all redacts a **quoted** value as a whole span (a quoted passphrase with spaces is fully removed, not just its first word), and `Bearer` matching is case-insensitive.
- **`contexer/adapters/`** — one module per AI-assistant target. `base.py` holds shared config-file helpers (`_load`/`_save`/marker checks). **Marker-matching has two variants and picking the wrong one fails silently:** `_in_groups` matches against `str(hook_dict)` (the dict's *repr*, so it sees command + statusMessage + matcher at once) — but a repr escapes quotes, and every real hook command is `py -c "..."`, i.e. contains a double quote, which forces repr to `'`-delimit and rewrite an inner `'codex'` as `\'codex\'`. A gate keyed on a quoted marker therefore never matches, never recognizes the hook it just installed, and re-fires on every install forever (this was live in `codex.py`'s team-poll gate: pure churn, since the correct hook was re-added each time, but no Codex install was idempotent). Use `_in_commands` — raw `command` match, quote-safe — for **any marker containing a quote**. The trap is that a marker with single quotes alone *appears* to work, because repr leaves those untouched. `claude.py`, `cursor.py`, `codex.py`, and `gemini.py` each own that tool's MCP registration, hook wiring, install/uninstall/status, and provider-specific hook output. `__init__.py` is the registry (`detect()` / `select()`). Gemini stores MCP and hook configuration together in `~/.gemini/settings.json`; it uses `SessionStart`, `BeforeAgent`, `AfterTool(write_file|replace)`, `PreCompress`, and `SessionEnd`. Because `PreCompress` is asynchronous and Gemini has no `PostCompress`, `gemini.py` sets flags and re-injects stored context at the next `BeforeAgent` event.
- **`contexer/memory_sync.py`** — imports Claude Code's memory-tool facts (`~/.claude/projects/<slug>/memory/*.md`) into the store, so decisions a session persisted to the file-based memory tool (instead of calling `update_context`) still reach Contexer. This is a *coexistence* path, not a competitor for capture: rather than fight an authority contest hook-injected reminders always lose against another tool's system-prompt memory workflow, Contexer becomes a deterministic sync target. No model in the loop — parses each fact's YAML frontmatter (`description`/`type`/`originSessionId`) + body, splits multi-section docs on `##` headings into one entry each (never a raw blob), assigns a subtype by keyword rules (ordered `convention` > `constraint` > `pattern` > `architecture`, with a frontmatter-`type` backstop — `feedback`→convention, `project`→architecture — and an architecture default, so *every* import is queryable via `get_context(entry_type=...)`), and upserts the whole dir in one load+save via `store.upsert_memory_batch`, keyed on a stable `memory_key` (source file + `##` section; repeated headings are disambiguated so they don't collide) so a fact reworded on disk updates its entry *in place* rather than silently dropping the edit (<30% change) or accumulating a near-duplicate (>30% change). First-time creation still passes the >70% novelty filter, so a memory fact that merely restates an existing decision is recorded as a recurrence, not double-stored across the two systems. Provenance: `session_id` = the fact's `originSessionId`. Fail-soft per file — a malformed memory file is skipped, never raised. The module is neutral (takes a dir path); `adapters/claude.py` owns the Claude-specific `_memory_dir(repo_path)` slug derivation (`re.sub(r"[^a-zA-Z0-9]", "-", repo_path)` — the one fragile coupling point, marked in code: if Claude Code changes its project-dir encoding, sync fails *safe* (finds nothing, never wrong data) but can go quietly dead) and `sync_memory(repo_path)`, which skips the whole import when a content fingerprint (`~/.contexer/.memory_synced_<slug>`) is unchanged.
- **`contexer/cli.py`** — the `contexer` console script: bare invocation runs the MCP server; subcommands `install [--target claude|cursor|codex|gemini|all]` / `uninstall [--purge]` / `reinstall` / `status` / `scope-audit` (read-only wrong-store report — see `scope_audit.py`) / `version` / `help` manage tool configs. `install` auto-detects present tools (`~/.claude` → Claude Code, `~/.cursor` → Cursor, `~/.codex` → Codex, `~/.gemini` → Gemini CLI) and falls back to Claude Code when none is detected; `--target` overrides.
- **`server.py`** (repo root) — back-compat shim importing `contexer.server`; keeps `uv run python server.py` working.
- **No `requirements.txt`.** `pyproject.toml` is the single dependency spec (managed by `uv`). A "kept for reference" `requirements.txt` used to sit here carrying its own copy of the `mcp>=1.9.4,<2` bound; nothing consumed it (not CI, not `scripts/`, not `CONTRIBUTING.md`), so it could only ever drift out of agreement with the real bound — where the upper bound is load-bearing, since mcp 2.0.0 removed `mcp.server.fastmcp` and an unbounded resolve installs a server that cannot start. Do not re-add one; `uv sync` is the install path.

## Module boundaries

Four modules were extracted out of `store.py` to one stated rule, and they landed at four different depths.
Two of the four were leaks rather than seams.
So the rule was restated as three clauses.
The clauses are enforced in `tests/test_module_boundaries.py` rather than left to review, because each one describes a drift that NOTHING fails on: a facade keeps answering correctly while the seam behind it erodes, a private name quietly acquires a second reader, and an alias makes a leaf's compiled regex reachable under a store name.
A rule that is only written down demonstrably does not hold here; that is what the four depths are evidence of.
The test also pins one PRE-EXISTING invariant these rules depend on, so it is four checks rather than three: a module reaching the store must import the module OBJECT, never `from contexer.store import X`, or a value a test patches on `contexer.store` is never seen at the call site.

What the measurement found before the rules, all of it re-checked with AST rather than grep:

- **The facade was not a published surface.** Of the 17 names re-exported through store.py's lazy `__getattr__`, exactly ONE had a production consumer (`server.py` calling `store.record_conflict_memo`). Every other production caller already imported the owner module. `store.py` has no `__all__`, so nothing mechanically backed the claim either. The facade is how the TEST SUITE addresses this code.
- **There was a shared core with no name.** 17 private `store` names were read by two or more of the extracted modules, and 11 by two or more modules across the whole package - `_atomic_write` by six, `_resolve_repo` by five. Those names were already an interface; they were merely spelled private, which is why 24 function-level imports existed to dodge the resulting import cycle.
- **`store.py` re-exported other modules wholesale.** 28 module-level assignments of the form `_x = <leaf>.x`, of which seven had no reader in `store.py` at all. Their only purpose was to let another module address a leaf through `store`, which is how `guard_engine` came to read one compiled regex in three hops.

**Rule 1. Production code imports the owner, always.**
The `store` facade is back-compat for names that were public on `store` before an extraction moved them, and nothing else.
It is frozen: an extraction may add to it, a name never public on `store` before its extraction never enters it, and a name with no consumer left is dropped.
Tests may address either, but a test that patches through the facade is pinning the shim rather than the behaviour, so prefer the owner there too.
Applying this dropped `team_snapshot` (no consumer of any kind) and repointed `server.py` at `conflicts.record_conflict_memo`.

**Rule 2. A `store` name read by a second module is interface, so it is public.**
One module reading a private name is coupling between two modules and is accepted.
A second reader means the name is depended on from outside, so it must either be public on `store` or move into its own leaf.
This is the clause that pays: it gives the next extraction a target instead of a judgement call, and it removes the reason the function-level cycle imports existed.
Applying it promoted 23 names, among them `load`, `save`, `save_global`, `load_global`, `store_lock`, `store_files`, `file_mtime`, `entry_by_id`, `entry_status`, `resolve_repo`, `resolve_repo_verbose`, `atomic_write`, `git_root`, `is_sane_repo`, `title_and_body`, `matches_query`, `query_pattern`, `MAX_SOURCE_FILES` and `GIT_FAST_TIMEOUT`.
Two were renamed rather than merely unprefixed: `_slug` became **`repo_slug`** because ten functions across five modules already bind a local named `slug`, and a module-level `slug` would be shadowed inside any of them that later needed to call it; and `_git` became **`run_git`**, which also names what the eventual unification of the four git wrappers (`store.run_git`, `store.git_root`, `anchors._run_git`, `miner._git`) should converge on.
The scope is every module, not only the extracted ones: `cli.py` reaching `store.resolve_repo` is structurally the same fact as `guard_engine` doing it, and the "was it carved out of store" distinction is historical.
**Known asymmetry, stated rather than quietly left:** this rule is about `store` names only, while Rule 3 applies to any owner.
Nine private names of OTHER modules currently have two or more readers, and none of them is a violation of anything written here: seven are `adapters/base.py` config-file helpers that the four adapters share by design (`_load`, `_save`, `_load_safe`, `_in_groups`, `_in_commands`, `_filter_groups`, `_BOOTSTRAP_CMD_MARKER`), and two are `guard_engine._guard_relpath` / `._escapes_repo`, read by `store.py` and `cli.py`.
The rule stays store-scoped because `store` is the module every other one depends on, so a second reader there is what actually blocks an extraction; generalising it would promote the adapters' deliberately-shared helpers for no gain.
The enforcing test is scoped the same way, on purpose.

**Rule 3. No module COPIES another module's names onto itself.**
A caller that needs a name reaches it qualified on its owner (`revisions.current_content`, `review.build_proposal`, `retrieval._TOPIC_ALIASES`).
Reaching a private name on its owner is fine under Rule 2 when there is one reader; copying any name onto a second module is not, because it creates two spellings for one thing and hides which module the dependency is really on.
The rule says COPIES, not re-exports, and the distinction is load-bearing: the Rule 1 facade re-exports 16 names by design, so a rule phrased as "no re-export" would forbid Rule 1.
What is banned is the second binding (`_x = <leaf>.x`), which makes both spellings live at once; the facade resolves lazily to the owner and creates no second name to drift.
Applying this removed all 28 aliases and replaced the worst of them with a real primitive: **`retrieval.raw_path_artifacts`** is now the single definition of "what a file path or dotted module looks like", shared by `extract_artifacts` (which segments the spans for BM25) and `guard_engine._guard_content_artifacts` (which needs them intact to compare against a staged path).
Exposing the match rather than the two patterns keeps that interface one function wide.
Removing an alias moves a dependency rather than deleting it: six modules (`anchors`, `conflicts`, `console_api`, `guard_engine`, `cli`, `scope_audit`) now import `revisions` or `review` directly, which is the point, since the edge is where the code actually reads from.

Removing an alias is more dangerous than it looks, which is why two of the boundary tests assert ABSENCE.
A straggler `store._current_content(...)` raises `AttributeError`, and several of these call sites sit inside fail-soft wrappers, so the feature does not break loudly - it silently stops working.
That is exactly what happened to the team-context dedup while these aliases were being removed, and only an unrelated assertion caught it.

## Storage

Context is stored at `~/.contexer/<repo_slug>.json` - one file per repo, plus `_global.json` for cross-repo decisions. The slug is the repo path with non-alphanumeric characters replaced by underscores. Each file holds a flat list of entries. Writes are atomic (unique temp file + `os.replace`, mode 0o600) so readers never see a torn file; corrupt files are read as empty rather than crashing. Three scoping notes. The first two were earned by review flagging a false positive; the third by a reproduced data-loss bug. **Whole-file REMOVAL is not a write**: `unlink` cannot produce a torn read (a reader sees the file or does not), so deleting a sidecar outright satisfies the invariant rather than deviating from it - `share.forget_shared_markers`/`discard_outbox` and `team_context.clear_caches` all remove rather than rewrite, and `discard_outbox` deliberately falls back to an atomic truncate only when `unlink` fails, because the two are different syscalls and a file that resists one can still yield to the other. **Reading a corrupt file as empty is for RENDER paths, never for a safety gate**: a fail-soft read cannot tell "nothing stored" from "could not parse", which is fine when the cost is a blank section and wrong when the cost is a wrong action. Where that distinction decides something, use a degrade-but-report reader that returns the error alongside the data - `store._read_global` vs `load_global` is the pattern, `share._read_outbox` vs `_load_outbox` follows it, and `discard_outbox` gates on the honest one because treating an unreadable outbox as an empty one left the previous account's queued shares on disk to be pushed to the next account that logged in. **A WRITE is the third case, and it is the most destructive of the three**: `_enqueue_unlocked` read through the fail-soft `_load_outbox` and then saved, so queueing one share against a damaged outbox wrote "empty plus the new row" over the top and every share already waiting was gone, silently (reproduced: 3 queued, 1 left, no error). It now reads through `_read_outbox` and RAISES, matching `_enqueue_reconciliation`, which already did exactly that for the identical failure on the other queue in the same module. Raising works because the callers already report a queue failure honestly rather than promising a retry; `_enqueue_unlocked`'s own docstring enumerates which caller says what, and is the single copy of that list. Two consequences are worth knowing here. The two `except asyncio.CancelledError` paths suppress the raise, because there a `RuntimeError` would REPLACE the `CancelledError` and a cancelled share would stop looking cancelled to its caller. And `server.share_decision`'s timeout path now branches on the RETURNED COUNT rather than on whether the call raised, because queuing records nothing both when the outbox is unreadable and when no id resolved to a shareable decision, and promising an automatic retry in either case states something untrue - the standard `share._finish_share` already keeps for its own failure branch. Both are pinned by tests and mutation-checked.

Linked git worktrees share the main worktree's store: `repo_slug` canonicalizes the STORE KEY ONLY via `_canonical_store_key` (a `.git` *file* whose `gitdir:` contains `/worktrees/` → one `git rev-parse --path-format=absolute --show-toplevel --git-common-dir` call, success-only cached, entirely fail-soft), so every slug-keyed artifact (store, lock, sidecars, flags, team cache) collapses while staleness/insight/miner still see the physical worktree path. Submodules (`gitdir: .../.git/modules/…`), `git init --separate-git-dir` repos, and worktrees of bare hosts (`repo.git`) deliberately keep their own keys. `migrate_worktree_strays(repo)` - called fail-soft at session start alongside `_gc_stale_session_files` - folds pre-fix stray worktree stores (self-detected plus `git worktree list` enumeration, never filename-prefix guessing) into the canonical store: id-first dedup, then the store's own >70% novelty gate, stray kept as `*.json.migrated` rather than deleted.

### Decision / Revision model (Git-like: storage preserves history, replay = current)

A decision is the logical engineering decision; a **revision** is one immutable version of it. Storage preserves every revision forever; replay exposes only the current approved one (like Git keeping every commit but cloning HEAD). This separation is what lets engineering history accumulate without ever growing the prompt or letting stale/pending values leak into a session.

The model is **embedded**, not normalized into a second collection: each decision entry owns its revisions inline (`revisions[]`) with an explicit `current_revision_id` pointer. This is the correct serialization for strict 1-to-many ownership (a revision belongs to exactly one decision, is never shared, never queried independently) and keeps the flat-list-per-repo storage and atomic whole-file write intact. The heavy query-side concerns (timeline, diff, audit, analytics, team approval, shared semantic search) live **upstream** in the remote teams MCP that decisions forward to (`push_decision`) - this OSS local store is a capture client + cache + outbox, so duplicating a relational/vector engine locally would be wasted. The embedded JSON maps 1:1 onto upstream `decisions` + `revisions` (+ a future `revision_embeddings` index) tables when that day comes, so no schema migration is needed to add those.

**Decision entry** carries: `id` (= decision_id), `type` (`task` | `decision`), `subtype` (`architecture` | `constraint` | `pattern` | `convention` - maps to the upstream 3-value `type` enum, with `pattern`→`architecture` on forward), `status` (`approved` | `suggested` | `pending_approval` | `ignored`), `current_revision_id` (the active revision - precedence is the pointer, **never** timestamps), `session_id`, `session_ids` (all sessions that have seen it), `timestamp` (Created At - immutable), `updated_at` (bumped when the current revision changes), `occurrence_count`, `created_by`, `revisions[]` (canonical list of all revisions incl. current), and optionally `proposed_revision` (a pending Suggested Update - never replayed until approved), `memory_key`, and `source_files`/`anchor_commit` (staleness anchor - see below). The decision also keeps `content` / `revision` (current `version_number`) / `confidence` / `confidence_factors` as a **synced HEAD-cache** of the current revision (`_sync_decision_cache`) so the many read sites stay O(1); the revisions are the source of truth, the cache is rewritten from them on every change.

**Revision object** (`_new_revision`): `revision_id`, `decision_id`, `version_number` (1-based), `content`, `confidence_score`, `evidence` (factor list), `created_at`, `approved_at`, `source` (provenance: `ai` | `human` | `scan` | `bootstrap` | `memory`). Revisions are immutable once superseded (the new-decision pre-approval edit amends v1 in place, since there is no prior version to preserve yet).

**Accessors / lifecycle:** `_current_revision(entry)` / `_current_content(entry)` resolve the pointer (fallback: last revision); `_append_revision(entry, content, source, approved_at)` creates the next version, advances `current_revision_id`, snapshots confidence onto the revision, and resyncs the cache; this is the single path used by trivial in-place updates, `_promote_proposal` (approve a Suggested Update), and memory-sync changes. Approving a brand-new `pending_approval` decision blesses revision 1 in place (no new version). **Migration is transparent and idempotent** (`_migrate_decision`, run from `load`): a legacy entry (old `content`/`revision` head + historical-only `revisions[]` snapshots) is rebuilt into full revision objects + a `current_revision_id` on first load; persisted on next save; fail-safe (a corrupt file still reads as empty).

**Which repo a tool call targets** is resolved by `store.resolve_repo(repo_path)` with this precedence: (1) an explicit, sane `repo_path` argument; (2) `_SESSION_REPO` - the repo bound to the running MCP-server process, captured once at startup from its own cwd's git root via `server.main` → `set_session_repo(git_root(os.getcwd()))`; (3) the shared `~/.contexer/.current_repo` pointer as a last resort. The per-process binding (2) exists because `.current_repo` is a single global file every assistant hook overwrites - a different tool or session could clobber it and send decisions to the wrong store file. `is_sane_repo` rejects the home dir and tool config dirs (`~/.claude`, `~/.cursor`, `~/.codex`, `~/.gemini`, `~/.contexer`, `~/.config`) on every read and write, so a poisoned pointer can never select a config-dir store file (it also rejects the filesystem root). **Hooks additionally fall back to their own cwd** (`store.hook_cwd_repo`, applied in `session_start_payload`, `bootstrap_prompt_payload`, and the per-prompt Claude entrypoints): hosts run hooks with cwd = the project directory, and non-git projects are first-class stores keyed by absolute path, so an empty git-root from the hook's shell must not erase the session's identity - the 0.16.1 bug was SessionStart claiming "no context stored" in a non-git dir whose store existed, while the MCP tools (explicit `repo_path`) found it fine. The fallback is `is_sane_repo`-guarded (a session opened in the home dir keeps the normal chain) and is deliberately NOT the retired `|| pwd` shell fallback: the shared pointer is only written from `session_start_payload` after the same sanity check, mirroring the git-repo case. `resolve_repo` itself is unchanged - adding a cwd fallback there would misresolve for MCP servers whose cwd is not the project (Cursor launches its server outside the workspace).

**Wrong-store writes are diagnosable, not yet prevented.** Decisions have been observed landing in the wrong repo's store - one session's nine captures split across THREE store files, five in the project it was working in and four in unrelated projects, where they now read as those projects' engineering decisions. Nothing leaked at read time (retrieval is already hard-scoped per repo); the records are physically in the wrong file. `resolve_repo_verbose(repo_path) -> (repo, source)` is the real resolver and returns WHICH branch chose the store - `argument` | `session` | `pointer` | `none` - with `resolve_repo` kept as a one-line wrapper so the eight read call sites in `server.py` are untouched. Precedence is **byte-for-byte unchanged** (the old `if repo_path:` branch was redundant with the chain below it and folds away). **Hooks get their own labels, and this is not cosmetic:** a hook process ALWAYS supplies a path - the installed shell wrapper passes `git rev-parse --show-toplevel`, and `hook_cwd_repo` substitutes the process cwd when that is empty - so through the plain resolver every hook capture could only ever report `argument`, the one label the audit reads as *a caller deliberately named this repo*, which would file each misrouted directive as intentional. `store._hook_repo_verbose` therefore reports `hook-arg` | `hook-cwd` before falling through to the shared chain, and Cursor, whose `workspace_roots` is a signal no other host has, labels that branch `workspace-root` via its own `_repo_from_verbose`. **Every capture surface stamps**, so an absent tag means what the report says it means: `update_context` and `capture_user_constraint` (MCP), the per-prompt constraint hooks on all four hosts, and `bootstrap_apply` - the largest bulk write in the system (one consolidated Stack entry plus every mined convention in a single save), which builds entries through `_new_decision_entry` directly and so stamps at both of its creation sites rather than inheriting `update_decision`'s. `update_decision` stamps on **newly created entries only** - a recurrence or containment route has already returned by then, and re-stamping would overwrite the provenance of the write that created the entry. What is deliberately NOT done: refusing the pointer when it disagrees with the server process's cwd. Disagreement is the NORMAL state whenever two projects are open (the pointer is one global file every session overwrites), and a host that launches the server outside the workspace - Cursor, documented above - has no sane cwd to corroborate against, so that rule would resolve to nothing at all for it. The policy stays put until the stamped provenance says which branch actually fires; guessing at a new one risks misrouting differently, not less.

## Session behaviour (hooks)

`~/.claude/settings.json` wires up hooks globally (applies to every repo):

- **`SessionStart`** — first runs `claude.sync_memory` to import any memory-tool facts (crash-recovery net: catches facts whose previous session ended without a clean `SessionEnd` flush), then injects all *approved* conventions, patterns, and constraints as project rules — constraint-subtype rules (and any rule with an open conflict) render in full, while convention/pattern rules render title-only (a footer points at `get_context` for the full reasoning, appended only when a body was actually clipped) to keep the injection within the host's `additionalContext` size limit; injects a count pointer for deferred architecture decisions (fetched JIT via `get_context`); the same deferral applies to the synced **team** context section this hook appends via `store.session_start_payload` (`_team_section(..., defer_architecture=True)`) — a team-synced architecture decision renders as a count-only pointer alongside the local ones, not full content, with `get_context(entry_type="architecture")` returning both personal (`[scope=personal]`) and team (`[scope=team]`) architecture decisions in full on demand; deferral exempts a team architecture row that already collapses to the cheap `[scope=team] ratifies local decision <id>` one-liner (>= 0.7 token overlap with a stored local decision) — that row is already as light as the deferred-count pointer itself, so hiding it too would only throw away its ratification signal for zero token savings (`team_context.count_deferred_architecture` mirrors this exemption so the `status` suffix's `(M shown)` figure — see below — only subtracts rows genuinely hidden behind the pointer); injects a **count-only** pointer for decisions awaiting review (never their content — pulled on demand via `review_pending`); injects a bootstrap offer if no context exists. **It also reconciles the evidence spool, on the shared store-side path every host traverses**: see the `contexer/reconcile.py` bullet for why it runs before the store read, why it is scoped to `session_id=""`, and why Claude's resulting double call is left harmless instead of suppressed. The four adapters name themselves to it (`host=`) so the pass receipt records who could observe what: Gemini and Cursor pass `NAME` from their Python `session_start`, and Claude and Codex pass a `'claude'` / `'codex'` literal inside their installed `ss_code` hook command, whose install-migration gate matches it with `_in_commands` (a quoted marker, so `_in_groups`' repr match would never fire). An install predating that argument keeps working and reports `manual`, whose static map claims nothing: the degradation direction is under-report, never over-claim. Resume-aware and compaction-aware via the `source` field read from hook stdin (`source_from_hook_stdin`): on `resume` with context, skips re-injection entirely (the conversation already contains it); on `resume` without context, injects transcript-mining instructions instead of the menu; on `compact` it takes the normal path and silently re-injects the full context (this is what reloads context after compaction — there is no separate `PostCompact` hook) (mine decisions from the visible conversation + store scan facts, all in the first turn — no human round-trip) and writes `~/.contexer/.resume_mining` so the UserPromptSubmit bootstrap fallback stays silent (the flag is consumed on first prompt; non-resume session starts clear stale flags).
- **`PostToolUse` (Write|Edit, silent)** - fires after every `Write` or `Edit` tool call, running `claude.post_write` (replacing the old shell-only `touch .pending_capture`). Two jobs in one hook: it records the edited file into a **per-repo** sidecar via `store.record_edited_file` (`~/.contexer/.edited_<slug>.json`, a list of `{path, mtime}` records canonicalized through `guard_engine._guard_relpath`, re-stamped in place on a repeat edit, capped at `_EDITED_FILES_CAP`=50 evicting the oldest by mtime) — the **flow** half of anchor accrual (see Commit-time guard below); and it touches `~/.contexer/.pending_capture` exactly as before. **Keying per repo — never per session — is load-bearing:** the writer is this hook's process (session id from the host's hook stdin) while the reader is the MCP server process (`server.SESSION_ID`, a uuid4 minted at server start), so a session-keyed filename could never once agree between the two and left the whole flow loop inert in production (while tests that handed both sides the same literal id passed). Staleness is bounded by each record's own timestamp instead: `store._read_edited_files` returns only paths edited within `_EDITED_FILES_WINDOW`=1800s, and the read is non-destructive, so several captures in one turn each see the same list. Concurrent writers on one repo race last-writer-wins on an atomic whole-file write — at worst one edit record is lost, costing a candidate suggestion and nothing else. Completely silent - no UI output. Codex reuses `claude.post_write` verbatim on its own `PostToolUse`; Gemini calls `store.record_edited_file` from its `AfterTool(write_file|replace)` hook (`adapters/gemini.py`'s `after_write`) — same signal, different event name. Cursor recording is out of scope for now (#175). The installed shell wrapper resolves the repo via `git rev-parse --show-toplevel`, matching every other per-prompt hook in this module — a diverging resolution here would key the sidecar under a different slug than the reader expects and silently kill the signal in a monorepo subdirectory.
- **`.pending_review` (deterministic mid-session nudge).** Unlike `.pending_capture` (written by a hook), the **per-repo** `~/.contexer/.pending_review_<slug>` flag is written by the **store**: `store.update_decision` touches it at the two spots that create a state awaiting the developer - a new `pending_approval` entry (gated on status) and a freshly-attached `proposed_revision` - after `save`, inside the store lock (`store._touch_pending_review(repo_path)`). Per-repo (not global) so a pending decision in repo A never nudges a session in repo B. The per-prompt consumer is `store.pending_review_nudge(repo_path)`: it fires the count-less "offer to `review_pending`, then `approve_decision`" nudge **only** when this repo has a freshly-set flag AND still has decisions pending (`get_pending_decisions`) - so a flag left by an already-approved decision, or by another repo, never yields a false nudge - then clears the flag (fire-once; a new pending decision re-arms it). So decisions captured mid-session resurface at the next natural turn instead of waiting for the next SessionStart. Consumers per adapter: **Claude/Codex** call the Python entrypoint `claude.review_nudge` from a UserPromptSubmit hook (Python, not shell, so it can compute the slug and verify the store; Codex reuses `claude.review_nudge` verbatim and lists it in `_EVENT_MARKERS` since it has no sentinel); **Gemini** calls `store.pending_review_nudge` in `before_agent`, independent of the compaction-reload branch (a reload re-injects `get_context`, which *excludes* pending decisions, so the nudge must still fire); **Cursor** can't inject per-prompt context (`beforeSubmitPrompt` returns `{continue}`), so its reminder rides the always-apply `.mdc` rule body instead. `capture_user_constraint` deliberately does NOT arm this flag for its own `pending_approval` entries - its in-band `constraint_ack` notice (self-approval-proofed) already tells the model to surface the pending decision to the developer that same turn, so a second, deferred nudge would only double up.
- **No `Stop` hook.** An end-of-turn `Stop` hook that prompted the model (via `additionalContext`) to capture/review decisions was evaluated and removed: it added latency and tokens and depended on model behavior, while delivering nothing the deterministic `PostToolUse` flag + next-prompt anchor reminder doesn't already deliver at a non-interrupting moment. `claude.install`/`codex.install` actively strip a previously-installed Contexer `Stop` hook (matched on `.pending_capture`) while leaving any foreign `Stop` hook intact; the `Stop` marker stays in the uninstall tables for this cleanup. Decision *updates* are surfaced deterministically (the `proposed_revision` Pending Update + `contexer review`), not by mid-turn prompting.
- **`UserPromptSubmit` (anchor, command, every prompt)** — writes the git root to `~/.contexer/.current_repo`, but only when actually inside a git work tree (no `|| pwd` fallback — that could poison the pointer with a non-repo dir). Also checks for `~/.contexer/.pending_capture`: if present, deletes it and injects `additionalContext` reminding Claude to call `update_context` for decisions from the previous turn. Silent to the user — only Claude sees the injected context.
- **Bookkeeping writes are best-effort everywhere (#152).** `~/.contexer/.current_repo`, `.pending_capture`, `.pending_review`, and `.resume_mining` are *bookkeeping*, not context: the pointer is only the last resort in `resolve_repo`, and the flags merely schedule a reminder. A sandboxed host can leave the workspace writable while `~/.contexer` is not (Codex's managed sandbox), and an unguarded write there used to raise `PermissionError` and abort `SessionStart` - Contexer injected nothing at all over a file it never needed in order to *read* context. So: every adapter anchors through the one fail-soft, sanity-checked `store.anchor_repo(repo)` helper (never a raw `write_text`); `_store_path`/`_global_path` treat their `STORE_DIR.mkdir` as best-effort so *readers* can't be crashed by an uncreatable store dir (writers still surface the failure at their own write); and the shell hooks guard both writes - `{ printf … > ~/.contexer/.current_repo; } 2>/dev/null || true` (braces matter: `cmd > f 2>/dev/null` opens the redirect *before* stderr is silenced, so a bare suffix still leaks the error) and `touch ~/.contexer/.pending_capture 2>/dev/null; echo '{}'` (`;` not `&&` - a failed touch must not swallow the hook's mandatory JSON output). `claude.install`/`codex.install` migrate the pre-#152 unguarded forms on the next `install`/`reinstall`, gated on `anchor_repo` in `ss_code` and on `claude._TOUCH_GUARD` / `claude._ANCHOR_GUARD` in the shell hooks. The invariant: **inability to write an optional bookkeeping file never prevents a hook from rendering context.**
- **`UserPromptSubmit` (bootstrap, command, once)** — calls `store.get_bootstrap_context_prompt` on the first prompt; injects the bootstrap offer if no context exists (fallback for when SessionStart is skipped).
- **`UserPromptSubmit` (constraint, command, every prompt)** — calls `claude.capture_constraint` with the prompt text. Detects prescriptive directives (`always X`, `never Y`, `from now on Z`) and stores them as `decision` entries automatically — no Claude involvement needed. Silent no-op for all other prompts. To avoid crowding the store, `_is_prescriptive_constraint` rejects anything that isn't a clean standalone directive: pasted blobs over `_MAX_DIRECTIVE_LEN` (300) chars, fenced code dumps, and tool/system-injected text (`<task-notification>`, `<system-reminder>`, Contexer's own injected context) — these merely *contain* directive words and are never genuine user rules. A further family of guards strips non-directive uses of a trigger word and re-checks, so a sentence that only *sounds* prescriptive doesn't land: the `never mind` dismissal clause (`_IDIOM_STRIP`, bounded on punctuation **and** on a coordinating conjunction, so a directive joined without punctuation — "never mind the perf concerns and always validate input" — isn't swallowed with it), predictive `will/would (always|never)` (`_MODAL_PREDICTIVE`, skipped when the imperative `you will/would …` construction is present, since "you will always X" is a command, not a forecast), and hedged `could/might/may (always|never)` (`_HEDGE_MODAL`). **`ensure you` / `make sure you` are treated as weak emphasis wrappers, not durability markers** (`_WEAK_EMPHASIS`): unlike `always`/`never`/`from now on`, they introduce one-off session work as readily as standing rules ("ensure you ship the dashboard" vs "ensure you never commit to main"), so when a wrapper is the ONLY trigger that matched, a durability signal — a prohibition (`not`) or a **recurrence** marker (`every`/`each`, `_DURABILITY_SIGNAL`) — is required before the prompt is stored at all; any other trigger word in the sentence already carries its own durability and passes this check inherently. `all`/`any` are deliberately NOT durability signals: they are OBJECT quantifiers, sizing what to act on rather than how often, so they read identically in a rule and in a one-off task (`ensure you fix any failing tests`) and would let that task through as a trusted standing constraint. Residual, pre-existing and out of this guard's reach: `do not`/`don't` is itself a full trigger, so `ensure you do not skip the migration step` never reaches the weak-only check — distinguishing that from the genuine `do not commit directly to main` needs a different mechanism than trigger strength. Also `for now` counts as deictic (`_TEMPORAL_SCOPE`), so a temporarily-scoped directive lands `pending_approval` rather than trusted. A clean standalone directive is stored **trusted** (`approved`) automatically; a directive carrying a conversation-local reference (`store._is_deictic`: this/these/those unless scoping the rule to `this repo`/`project`/`repository`/`codebase`; `it` unless in the self-resolving idiom `make it a <rule/...>`; non-trailing `here` — a trailing `here` means "in this repo" and stays trusted — bare `that` is excluded, relative/complementizer uses dominate) is stored `pending_approval` with an in-band ack (`store.constraint_ack`) that tells the model to notify the developer and explicitly forbids self-approval. A later clean restatement that matches (>70% token overlap) its own still-pending twin promotes it to `approved` in place rather than being silently dropped as a duplicate; entries the developer already `ignored` are excluded from that match so a re-typed rule lands fresh, not permanently blocked. When that overlap gate misses but the new directive is a containment match of a stored rule (>70% of the smaller side's tokens shared — a superset or subset restatement), it is routed onto that entry instead of accumulating: a superset of an approved rule becomes a `proposed_revision` (suggested update, developer-reviewed), a superset of its own pending twin promotes (clean) or amends in place (deictic), and a terse restatement of an approved rule records a recurrence — never a new overlapping entry; moderate lexical near-matches (0.25–0.7 overlap) are listed in the ack for developer-confirmed consolidation only.
- **`UserPromptSubmit` (rationale, command, every prompt)** — calls `claude.rationale` with the prompt text; auto-injects matching decisions when the prompt contains rationale keywords (why, reason, rationale, decided, etc.). Silent no-op for all other prompts. When it does inject, it also emits a user-facing `systemMessage` naming what was recalled ("Contexer: recalled N decision(s) (topics)" / "Contexer: pointed at related decisions (topics)"), with a token-savings estimate (injected estimate × `_SAVED_MULTIPLIER − 1`, benchmark-derived, nearest 10) appended only above `_COST_NOTE_TOKENS` — built from `store.get_context_for_prompt_with_meta`'s structured `{kind, count, topics}`, not scraped from the rendered text.
- **`UserPromptSubmit` (team poll, command, every prompt)** — calls `claude.team_poll(repo, raw, consumer)` (C7 delta-poll; `consumer` defaults to `"claude"`, Codex passes `"codex"` — Codex reuses this exact function). **Non-blocking by design: the prompt path never performs network I/O.** Mirrors the SessionStart deferral: a newly-approved `architecture`-typed row is never dumped into the "just approved" banner as full content — it's rolled into a single count-only line pointing at `get_context(entry_type="architecture")`, while non-architecture rows still render in full immediately. Delivery is a **per-repo sync log + per-consumer high-water mark** (replacing the old single `.team_pending_<slug>.json` file, which a single consumer would claim, starving any other session on the repo): `_sync` appends `{seq, ids}` to a `sync_log` inside the cache file whenever it merges new/updated team rows (`seq` is a stored monotonic counter, never wall-clock — deterministic, clock-skew-immune; the log is capped at the last 50 batches, oldest dropped — a consumer further behind than the cap just misses old *banners*, the rows stay reachable via `get_context`). Each consumer keeps its own marker `~/.contexer/.team_seen_<slug>_<consumer>.json`; `team_context.poll_nonblocking(repo, consumer)` returns the rows from every log batch with `seq >` that marker (deduped by id, current version resolved from the cache), advances the marker, and — at most once per 15s — spawns a detached refresher process (`python -m contexer.team_context <repo>`) whose synced batch surfaces on the *following* prompt. So a Claude and a Codex session on the same repo each receive every newly-synced batch exactly once, independently. A brand-new or corrupt marker initializes to the current log head (caught-up, injects nothing that once) rather than 0, because SessionStart already renders the existing backlog — the delta-poll must only surface batches logged *after* the session started. The throttle stamp is written *before* spawning so a crashing refresher can never cause a spawn storm; a leftover legacy pending file is deleted on first poll. All read paths are fail-soft (corrupt marker/log degrades to an empty injection, never raises). Trade-off (deliberate): one prompt of extra staleness vs. the synchronous poll, in exchange for a hard guarantee that a slow or hanging cloud (worst case previously: the full transport timeout, ~10s) can never stall prompt submission. The synchronous `team_context.poll()` remains for callers that want blocking semantics.
- **`PreCompact`** — runs `claude.sync_memory` to flush memory-tool facts before the context window collapses, then injects a systemMessage reminding Claude to call `update_context` for any unsaved decisions.
- **No `PostCompact` hook.** After compaction Claude Code fires `SessionStart` again with `source="compact"`, and that event silently re-injects the full context via `additionalContext` (the normal `session_start_payload` path) — so post-compaction reload is already owned, seamlessly, exactly like a fresh session start. A `PostCompact` hook was tried and removed: `PostCompact` supports no `additionalContext` and its `systemMessage` is user-facing only (the model never sees it), so it reloaded nothing and merely dumped the entire stored context into the transcript as visible noise on every `/compact`. `claude.install` now actively strips a previously-installed Contexer `PostCompact` hook (matched on `get_post_compact_context` / the sentinel) while leaving any foreign `PostCompact` hook intact; the `PostCompact` markers stay in the uninstall table for this cleanup. (The neutral `store.post_compact_payload` / `get_post_compact_context` helpers are retained for the Codex adapter and Gemini's `BeforeAgent` re-injection, which do inject on their own event models.)
- **`SessionEnd`** — runs `claude.sync_memory` to flush memory-tool facts on clean exit. The earlier decision to reject `SessionEnd` hooks was about *capture that needs the model to act* (a `SessionEnd` hook can't make Claude call a tool); this is a deterministic file import that needs no model, so it is valid here. These three triggers (`SessionStart`, `PreCompact`, `SessionEnd`) are the memory-sync surface; the import itself is idempotent, so running it at several of them is cheap.
- **Legacy repo-settings cleanup (upgrade hygiene).** The pre-CLI from-source installer (June 2026) wrote hooks into the *repo's* `.claude/settings.json` — including an `mcp_tool` hook calling the since-removed `capture_context` tool ("Unknown tool: capture_context" on every prompt) and a dead-clone `uv run --directory` SessionStart hook (a second, contradictory "no context stored yet" startup message next to the real global one). Modern installs only manage `~/.claude/settings.json`, so upgrades used to leave those behind. `claude.clean_legacy_repo_settings(repo)` strips hook groups that are recognizably ours (`_LEGACY_REPO_HOOK_MARKERS` match or an `mcp_tool` hook targeting the `contexer` server) and preserves everything foreign; it is called from `sync_memory` (so a plain package upgrade self-heals each repo the user opens a session in — `sync_memory` is the one adapter entrypoint every already-installed SessionStart hook calls, no reinstall needed) and from `install`/`uninstall` for the cwd's git root. `install` also prunes the stale `mcp__contexer__capture_context` allow entry, retires the legacy unconditional every-prompt reminder echo from home settings, and warns (cannot fix — plugin caches belong to Claude Code) when an installed Contexer *plugin* still ships the removed `capture_context` hook, advising `claude plugin update contexer`. The same package-only-upgrade class exists for removed hook *entrypoints*: pre-#58 installs wired `claude.capture_task` (Claude home settings and Codex `hooks.json` — the identical command string) and `cursor.capture_task` hooks, which would raise `AttributeError` on every prompt once the package is upgraded. Those entrypoints therefore exist as **self-retiring no-op stubs**: being invoked is proof of a stale hook (nothing else ever calls them), so the stub returns the host's silent no-op AND removes its own hook group — `claude.capture_task` heals `~/.claude/settings.json` and delegates `~/.codex/hooks.json` to `codex.retire_capture_task` (each module edits only its own file); `cursor.capture_task` heals `~/.cursor/hooks.json`. This adds zero cost to healthy installs (no per-prompt config reads — the stub only runs when a stale hook fires, and after the first fire the hook is gone). Gemini needs no stub: its `capture_task` use was internal to `before_agent`, whose installed hook command never changed.

**During a session**, call `update_context` whenever you make a significant decision, establish a pattern, or document a constraint. This is mandatory — not optional. After you write or edit files, the next user prompt will inject a reminder via `additionalContext`, but you should call it proactively within the same turn, not wait for the next prompt.

Call `update_context` for any of these:
- A technology, library, or approach chosen over alternatives (subtype: `architecture`)
- A file structure, naming convention, or code organization pattern established (subtype: `pattern`)
- A rule stated by the user or inferred from their preferences: "always X", "never Y" (subtype: `constraint` or `convention`)
- A build, deploy, or tooling convention established (subtype: `convention`)
- Any decision that would surprise a future Claude session if it wasn't stored
- A synthesized understanding of how a subsystem works, produced while scanning the codebase to answer a question (subtype: `architecture`) — capture it in the same turn; the session may end with the answer.

Pass the full reasoning, not just the conclusion. Pass `subtype` so decisions are retrievable by type. The server's novelty filter discards duplicates silently, so err on the side of calling it.

**Retrieving context JIT**: call `get_context` **before reading files** for any question about architecture, design decisions, rationale, constraints, patterns, or conventions. Fall back to reading files only when context is missing or the question is about current code state (exact syntax, current values). Use `query` for keyword search or `entry_type` to retrieve a specific subtype: `get_context(entry_type="constraint")` returns only constraints (up to 25). Use `limit` to override the display cap. When results are truncated, the output includes a `"showing N of M"` note so you know more exist.

## Commit-time guard (`contexer guard`)

A git `pre-commit` hook - install with `contexer guard --install-hook` (never wired automatically by `contexer install`) - that checks staged files against stored decisions when you commit. Two tiers, both implemented in `contexer/guard_engine.py` (grep `_GUARD_`; `store.py` re-exports the public entrypoints lazily as a compatibility facade - see the module bullet above) and dispatched from `cli.py`'s `guard()`/`_guard_*` family: **Tier 1 (advisory, non-blocking, always exit 0)** pairs a staged file against an `approved` decision whose provenance is trusted (`_guard_trusted`; `_GUARD_TRUSTED_SOURCES = {human, scan, bootstrap, plan}` - never `ai`/`memory`, so an unreviewed guess never nags at commit time; `plan` is trusted too because a plan-sourced decision that survived reconciliation AND developer approval is more vetted than `scan`, and the status check still keeps an unapproved plan suggestion untrusted; ALSO trusted regardless of source: `entry.get("approved_by") == "human"` - a decision a developer EXPLICITLY approved (`_apply_approval`'s approve/edit paths, per-id only - bulk approval was REMOVED precisely because clearing a list wholesale is not the deliberate, decision-by-decision gesture this trust model assumes, and the review queue is exactly where a mis-captured decision lands) is trusted even when its revision `source` stays `ai`/`memory`; an auto-approved entry no human ever reviewed - scan/bootstrap/memory born-approved routes, legacy migration, or an `ai` capture whose content merely matches a scan-fact pattern - never sets `approved_by` and stays untrusted (issue #180)) via `_guard_pairs`: either the file is in the decision's `source_files` (repo-store decisions only - global-store decisions carry no `source_files` and pair via artifact match only), or a path/module-shaped artifact pulled from the decision's content matches the staged path through `_artifact_path_match` (exact relpath, a dotted-module → path mapping, or a `/`-bounded multi-segment suffix - a bare basename can never match, by construction: a slashless non-module artifact falls through before reaching the suffix branch). Provenance is read from the current revision's `source`; a falsy `source` (legacy entries that predate provenance tracking) falls back to the decision's `created_by` for this trust check ONLY - a **read-time** fallback, not a migration that rewrites storage: `share.py`'s `_wire_source` deliberately preserves a stored `source: None` end-to-end (the cloud stores NULL = honest unknown provenance), so back-stamping it in storage would fabricate a false provenance on the share wire the moment that entry is pushed. The fallback therefore lives in `_guard_trusted` itself, at the one point that actually needs a trust verdict, and nowhere else. **Scoped ruling (#176): synthesis is derivation, not fabrication.** This "never fabricate" invariant covers only entries whose STORED revisions carry an explicit falsy `source` - those stay `None` end-to-end. It does not reach `_migrate_decision`'s synthesis path: when a legacy entry never had revision objects at all, deriving that revision's `source` from the entry's `created_by` is the truest available provenance, since nothing revision-level ever existed to preserve. Noise control layers two sidecars under `STORE_DIR` before the surfaced list is capped at `_GUARD_MAX_ADVISORIES`=5: a permanent per-(decision, file) dismiss set (`.guard_dismissed_<slug>.json`, driven by `--dismiss <hash|n>`, hashed via `_guard_hash` = sha1(decision_id+"\n"+relpath)[:12] - keyed on decision+file only, never content or line, so an ordinary edit never resurrects a dismissed pair) and a content-keyed throttle (`.guard_advised_<slug>.json`, `{hash: content_sha1}`, capped at `_GUARD_THROTTLE_CAP`=500) that only re-advises a pair once its file's staged content actually changes. **Tier 2 (blocking, exit 1)** fires only for a decision explicitly armed via `arm_guard` (CLI: `guard arm <id> --regex '<pattern>' [--flags i] [--paths <glob>] [--message <hint>]` or `--check secret`) - arming requires the decision to already be `approved` (an unreviewed decision can't be armed) and the check to be machine-checkable (`policy.validate_check`: regex must compile, only the `i` flag is accepted, `secret` takes no pattern - an invalid request raises `ValueError` at arm time, not commit time); approval is re-checked at RUN time by `_armed_rules`, never trusted from arm time, so a decision later `ignored` stops firing with no explicit disarm needed. **What a rule MEANS lives in `contexer/policy.py`, not here.** `policy.validate_check` decides what may be armed and `policy.rule_matches` decides what counts as a hit (the regex + `i` flag, `redact.HIGH_CONFIDENCE_PATTERNS`, the line numbers), so the deterministic check exists exactly once and the policy plane and the commit guard can never disagree about one rule. `guard_engine` keeps only the git-shaped half - which files, read how, budgeted by what, reported where: `_rule_selects` unwraps an ENTRY's `guard_check` and delegates the glob, and `_evaluate_rules` shapes `policy.evaluate_policies`' answer into `{path, line, decision_id, title, message}` violation rows plus a SECOND list of dead-rule rows. A rule the evaluator could not run at all (an unparseable pattern hand-edited into the store, an unknown check type) is REPORTED as `{decision_id, reason}` rather than passing as a clean scan: `arm_guard` refuses one at arm time, but a store is a JSON file a human or a botched migration can edit, and a rule that silently never fires is the failure a developer is least able to notice - they believe they are protected and they are not. It is named, never blocked on (the guard's own limitation, the same class as an exhausted budget), and reported once per RUN keyed on (decision, reason) rather than once per staged file, since a dead rule is a property of the rule and one broken pattern would otherwise print a line for every file it selects. **Invariant: the run path never blocks a commit on its own failure.** `guard_staged` (the single entrypoint, store-READ-ONLY - never calls `save`/`save_global`) wraps its entire body: Tier-2 violations run first under a `_GUARD_TIME_BUDGET`=2.0s wall-clock deadline checked between files/rules (Python's `re` has no per-call timeout, so one catastrophically backtracking regex can still overrun mid-match - the documented residual risk), and ANY exception or budget overrun returns `{"error": True}` with both lists empty rather than raising or half-blocking; `_guard_run` (the CLI entrypoint, deliberately NOT wrapped by `_run_guarded`) turns that into one stderr line and `sys.exit(0)`. `CONTEXER_GUARD=0` short-circuits before any work is done, in both the CLI and `guard_staged` itself. A merge in progress skips Tier-1 pairing but not Tier-2 (its violations already ran). **A staged file the guard cannot read is REPORTED, never a silent pass.** `_staged_content` returns `(text, reason)`, with `reason` one of `unreadable` / `too-large` / `binary` and `None` only on a real read; it previously returned a bare `""` for all three failures AND for a genuinely empty file, which is the same unreadable-versus-empty collapse `load_diagnostics`, `_read_store`, `_read_global` and `_inspect_store_file` exist to prevent, and it cost two things. Tier-2's `_guard_violations` did `if not content: continue`, so an over-cap file passed as a clean result: at the old `_GUARD_MAX_FILE_BYTES`=200,000 that silently exempted this repo's own `contexer/store.py` (376KB) and `tests/test_store.py` (390KB), the two most-edited files here, from every armed rule including `--check secret`. And Tier-1's throttle hashed that `""`, so an unreadable file always matched its stored stamp and the pair was suppressed FOREVER however much the file changed. Both are fixed. `_staged_content` now returns `(text, reason, fingerprint)`, where the fingerprint is the RAW staged bytes' sha1 and is absent ONLY for `unreadable`: the line is drawn at what git actually READ, not at what the scanner accepted, so an over-cap or binary file still has a comparable identity and its Tier-1 pair still throttles and still gets stamped. Withholding it from every non-None reason is the mirror-image bug of the freeze, and just as bad, since the pair would then re-advise on EVERY commit and, because the surfaced list is capped at `_GUARD_MAX_ADVISORIES`, crowd out fresh advisories (caught in review on this change). For valid UTF-8 the raw bytes' digest is identical to the previous decoded-text one, so on-disk throttle stamps carry over untouched. `_guard_violations` returns a third `unchecked` list of `{file, reason}`, gated three ways so it stays signal: only reasons in `_GUARD_UNCHECKED_REPORTED` (`too-large`/`unreadable`/`budget`, so a staged PNG is silent because skipping binary is correct rather than a gap), empty when no rule is armed (nothing needed checking, so nothing was skipped), and only when some armed rule's `paths` glob actually SELECTS the file via `_rule_selects` (the one definition shared with `_evaluate_rules`' own selection, since without it a rule scoped to `src/**/*.py` made an unscannable `data/dump.json` print a gap that does not exist). **Applicability is settled ONCE per file, at the top of `_guard_violations`, before the file is read or charged to the budget.** It used to be settled inside the per-rule judging instead, so a file no rule selects was still `git show`n and still added to `scanned` before being scanned against nothing, which is a security bug rather than mere waste: arm one rule `--paths "src/*.py"`, stage a few MB of `data/*.json` beside one `src/app.py` holding a secret, and the out-of-scope bulk exhausts the scan budget first, so the one file the rule covers is skipped with a non-blocking notice and its violation ships (caught by review on PR #241). Deciding once is also what stops this and the `unchecked` gate being two rules that can drift, which is why `_note` no longer re-tests it. `guard_staged` surfaces it under an `unchecked` key present ONLY when non-empty (the `total_advisories` convention, so a clean run's dict shape is unchanged), and `cli._print_guard_unchecked` renders one stderr line that never changes the exit code and is wrapped in its OWN try/except: `_guard_run`'s outer handler degrades to exit 0, so an exception while rendering a purely informational notice would otherwise swallow the blocking violation printed after it and pass the commit. **The cap is 1,000,000, and the number comes from the expensive rule type.** A `secret` rule runs all 14 `redact.HIGH_CONFIDENCE_PATTERNS` over the whole content, measuring ~155ms/MB (57ms for store.py's 374KB, 306ms at 2MB) against the 2000ms budget, i.e. ~57x a four-regex probe over the same bytes, so a 2MB cap would let SEVEN staged files exhaust the whole budget. That is not interchangeable with a per-file skip: a budget overrun fails OPEN by discarding every violation gathered so far, including those found in the small readable files, and reports only "internal error". 1MB clears this repo's worst file with 2.5x headroom while keeping one pathological file well short of the budget alone. The aggregate cost guard the per-file cap was being asked to double as is now explicit and separate, and it spends the REAL resource: Tier-2 scanning stops at `deadline - _GUARD_SCAN_RESERVE` (0.5s) and reports the selected files it did not reach through the same `unchecked` list (reason `budget`), rather than letting the hard deadline discard everything. **It was first written as a fixed 4MB byte cap, which was the right idea measured against the wrong resource** (caught by review on PR #241): bytes are only a proxy for cost, and the proxy's exchange rate depends on the armed rule mix, so a byte figure safe for 14 secret patterns throws most of the budget away for a single cheap regex. Concretely, 4MB is ~620ms against a 2000ms deadline, so staged selected text between ~4MB and ~12.9MB stopped being scanned while there was ample time for it, a coverage REGRESSION against the pre-budget code rather than merely a fail-open policy. Spending time directly has no exchange rate to get wrong. The reserve must exceed the cost of the largest single file that can start just before the cut-off, which is exactly what `_GUARD_MAX_FILE_BYTES` bounds (1MB is ~155ms against a 500ms reserve), so the two constants are related rather than independent guesses. The first selected file always scans (`checked_any`), so a run always makes forward progress even if it arrives already past the cut-off. **Running out of budget does not block the commit**, deliberately and per the invariant above: exhausting it is the guard's own limitation, not a rule violation, so the file is NAMED rather than blocked on. The trade-off is real and deliberately in the open, pinned by `test_running_out_of_time_does_not_block_the_commit`: a violation inside a file that went unscanned is not caught. `guard --install-hook` embeds the resolved binary's absolute path (`shutil.which("contexer")`, else `sys.argv[0]`) in a fenced block in `.git/hooks/pre-commit` (existence-guarded, so an uninstalled/upgraded binary no-ops instead of breaking the commit) and refuses - with guidance - when `core.hooksPath` is set or the existing hook was generated by the pre-commit framework (use `.pre-commit-hooks.yaml` at the repo root instead, id `contexer-guard`); `--uninstall-hook` strips exactly that fenced block, byte-preserving any foreign content.

**Approval-time anchoring.** `approve_decision(repo_path, entry_id, action, content="", *, source_files=None)` (in `store.py` — approval machinery, not guard engine) takes a keyword-only `source_files`: when non-empty and the resolved action is `approve` or `edit`, it anchors the entry via `_anchor_sources` (`source_files` + `anchor_commit` = current HEAD) once the approval actually applies — a Suggested Update's own stashed `source_files` anchors through `_promote_proposal` instead, so `approve_decision` skips the redundant re-anchor call in that case. Approval is treated as a human revalidation of the content: approve/edit is only ever legal on a decision still awaiting review (a brand-new `pending_approval` entry, or a live decision's Suggested Update) — `_apply_approval` rejects approve/edit outright on an already-active decision with no pending proposal, so there is no "re-approve" of a settled decision. On the two transitions where approve/edit IS legal, an entry that is *already* anchored gets `anchor_commit` refreshed to current HEAD regardless of whether `source_files` was passed this call, clearing any stale flag. `source_files` here is **single-id only**: `approve_decision` raises `ValueError` when `entry_id` is a comma-list or `"all"`/`"*"`, or when `action` isn't `approve`/`edit`. There is no bulk path at all any more: `store.approve_decisions` was deleted and `server.approve_decision` returns a refusal (`_BULK_REFUSAL`) for `"all"`/`"*"`/comma-lists, so every approval is one reviewed id. This is what makes the `contexer guard`/staleness pairing above possible without a separate capture-time `source_files` call: a decision approved with `source_files=["src/app.py"]` is immediately guard-pairable and staleness-trackable, the same as one anchored at capture time via `update_context`.

**Anchor accrual (issue #175).** An unanchored decision is not invisible to Tier 1 — `_guard_pairs` pairs on `source_files` **or** on a path/module artifact mined from the decision's own content — but it is invisible to **staleness** (`_staleness_note` needs `source_files` + `anchor_commit`), and it can only ever pair on whatever files it happens to name in its own prose. Anchoring after the fact is what closes both gaps: it makes the pairing explicit rather than incidental (reason `source_files match` instead of `path artifact ...`, and files the text never mentions become pairable) and it turns on staleness tracking for that decision. Two converging paths do it, one for the existing corpus (stock) and one for new captures going forward (flow), and both funnel through the SAME write primitive, `_anchor_sources`:

- **Stock: assisted backfill.** `guard_engine.anchor_candidates_for_backfill(repo_path)` is read-only: for every decision that is BOTH `_guard_trusted` AND currently unanchored, it mines the decision's OWN content for path/module-shaped artifacts (the same `_guard_content_artifacts` extraction Tier-1 pairing uses), maps any dotted module onto its file spelling(s), and keeps only candidates that actually `exist` in the working tree right now (no rename detection in v1 — a renamed file yields no candidate for that artifact rather than guessing). **What it buys, precisely:** because candidates come from the SAME extraction `_guard_pairs` already pairs on, a backfilled decision was ALREADY producing its Tier-1 advisory before the backfill (reason `path artifact ...`) — backfill adds no new advisories. What it adds is **staleness anchoring** (`source_files` + `anchor_commit`, which `_staleness_note` requires and content artifacts can never supply) and a firmer pairing reason (`source_files match`), plus the `[E]dit` path's ability to anchor files the decision's prose never named. `test_backfilled_decision_pairs_when_file_staged` pins exactly that BEFORE/AFTER pair of reasons. The CLI, `contexer guard anchors [--list]` (`cli.py`'s `_guard_anchors`), is its interactive counterpart: `--list` prints the candidate table and mutates nothing (also the non-TTY/agent-facing surface — the `[Y]/[E]/[S]/[Q]` loop refuses outright when stdin isn't a TTY); a ratified run applies every selection in ONE batch via `store.apply_backfill_anchors(repo_path, {decision_id: [file, ...]})` — one load+lock+save for the whole run, not one write per decision — which re-checks "not already anchored" at write time too (a concurrent capture/approval/backfill could have anchored it between the CLI's read and this write), so "never overwrite an existing anchor" holds even under a race. Two guards on that loop: a **Ctrl-C/EOF at either prompt aborts the whole run and writes nothing** — not even selections ratified before the interrupt (a plain `[Q]`uit still writes them, which is what the prompt promises); and `--list` is the ONLY accepted argument — anything else exits 1, so a read-only-sounding `--dry-run` can never fall through into the write flow.
- **Flow: capture-time candidates.** `store.update_decision` no longer requires the model to name `source_files` for a new capture to eventually anchor. When a captured entry lands `pending_approval` (status-gated on the ACTUAL resulting status, not on `created_by` alone — self-enforcing against future `created_by` values) and did NOT come with `source_files` and isn't scan/bootstrap/memory-sourced (those never touched a specific file THIS session, so the edited-files signal wouldn't correlate), the repo's recently-edited files (`store._read_edited_files`, fed by `record_edited_file` — see `PostToolUse` above; only edits inside the 30-minute freshness window) are stashed on the entry as `anchor_candidates` — a field the guard's pairing engine (`_guard_pairs`) never reads, so a candidate can NEVER pair as a Tier-1 advisory before a human blesses it. `format_pending_review` surfaces the stash as a `would anchor: <files>` line beneath the rendered decision (both the brand-new-entry and the Suggested-Update branch), so the developer reviewing it sees what will happen on approval before it happens — the informed-signature rule below. The same accrual runs on `capture_user_constraint`'s **deictic** path (the one that lands `pending_approval`, `created_by="human"`): that provenance is guard-TRUSTED the instant it is approved, making those entries the highest-value candidate carriers of all — a clean directive, born `approved`, is excluded by the identical status gate, since it can never see the pending→approved transition that blesses candidates. `contexer review`/`review_pending` never anchor by themselves; only `approve_decision`'s pending→approved (or proposal-approval) transition does, via `_apply_approval`, which blesses `anchor_candidates` into a real `source_files` anchor through `_anchor_sources` and clears the candidate field — precedence is caller-passed `source_files` (approval's own explicit kwarg) > a Suggested Update's own stashed `source_files` > `anchor_candidates`, each branch skipping the ones below it once it fires, so a caller-supplied anchor is never silently overridden by a stale candidate guess. A `clear_anchors` proposal (anchors.py's retirement) vetoes the whole ladder: it deliberately leaves the entry unanchored, so the candidates are dropped rather than blessed.

**The informed-signature rule, stated once:** no anchor ever becomes guard input without a human having seen the file(s) it names at the moment they signed off - a backfill candidate is shown and ratified per-decision in the CLI loop before `apply_backfill_anchors` writes it, and a capture-time candidate is rendered as `would anchor:` in the same review surface (`format_pending_review`) the developer is already reading before they call `approve_decision`. Neither path ever anchors a `pending_approval` decision on its own; a candidate sits inert until that human signature arrives. **One read of `anchor_candidates` lives OUTSIDE the guard**, and stays outside it: `_share_projection` falls back to the candidates when `source_files` is empty, so a decision shared before its local approval reaches Teams with the files it is actually about rather than none - a `pending_approval` decision IS shareable (`_shareable_entries` excludes only `ignored`). It is deliberately one-directional (it reads candidates, it never writes `source_files`, so the guard's Tier-1 pairing input still only ever contains human-blessed anchors), and safe on the wire because contexer-teams renders received paths as claimed, unverified metadata - the trust level a candidate actually has. What that argument does NOT buy is local silence: sharing is outward and hard to undo, so `format_share_preview` marks such a line `(unconfirmed - this session's edits, not yet approved)` via the projection's extra `source_files_unconfirmed` key, keeping the confirm surface as honest as the `would anchor:` lines everywhere else.

**Anchor truncation is recorded, not silent.** `_anchor_sources` is the ONE truncation point for anchors (`apply_backfill_anchors` delegates to it, and `anchors.py`'s own `[:MAX_SOURCE_FILES]` slices a list this function already capped, so it can never fire), and a decision that genuinely governs more than `MAX_SOURCE_FILES`=10 files keeps the first 10 with the rest gone for good. It therefore stamps `source_files_total` when - and only when - it actually truncated, popping it otherwise so a later re-anchor to fewer files can't leave a stale count behind; `cli._review_metadata` and `format_share_preview` render it as `(first 10 of 40)`, so the developer can narrow the anchor themselves instead of never learning it was partial. Raising the cap is deliberately NOT the fix: 10 is also the server's `INPUT_LIMITS.sourceFiles` bound (raising locally first would re-create the `-32602` outbox poisoning the wire gate exists to prevent), and `anchors._ANCHOR_GIT_BUDGET` is *derived* from it (`_RENAME_CHAIN_MAX * 2 * MAX_SOURCE_FILES + 1`), so a 10x cap is a 10x git-subprocess budget at session start under the store lock. The real answer for a subsystem-wide decision is a directory/prefix anchor rather than 100 paths, tracked in #224.

**`source_files` on the wire (issue #174 Task 5).** `remote._WIRE_SOURCE_FILES` gates whether anchors egress at all. It shipped `False` because the contexer-teams push schema is server-controlled and an unknown field poisons the outbox with permanent validation failures (this happened for real with `source="plan"`: -32602 on every retry, 192 attempts); it is now `True`, contexer-teams having accepted the field on both `push_decision` and `push_decisions` (server commit `e1a2189`, snake_case on the wire - note the same schema spells `decisionId` in camelCase, so the field name is not guessable). Deliberately a constant and not a config flag: a toggle could be flipped on against an old server and reintroduce the failure mode. The gate is read at CALL time inside `_wire_args`, never captured by a caller, so an entry queued to the outbox under one setting drains under whatever the constant is AT DRAIN TIME - in both directions. `_wire_args` also CLAMPS the field to the server's own bounds (`_WIRE_SOURCE_FILES_MAX_ITEMS`=10 / `_MAX_LEN`=300, after the redaction scrub so a redaction-lengthened path is measured at its wire length, omitting the key entirely rather than sending `[]`, which would CLEAR the column via `excluded.source_files` on re-push). The count was already capped at capture; the LENGTH never was, and the singular `push_decision` rejects over-bounds at its zod boundary, which is the poisoning case itself. **The bound is ONE definition (`remote.bound_source_files`) applied at TWO layers, the same shape redaction already has, and both are load-bearing:** `store._share_projection` applies it so the confirm-preview and the durable outbox carry exactly what will be sent (without it the preview advertises a path the wire then silently drops, at the surface a developer approves an outward push from - caught in review on #225), and `_wire_args` applies it again as the hard guarantee, since it is the only chokepoint EVERY push funnels through: a legacy outbox row queued before this existed, or a direct `push_decision` caller, never passed through a projection at all. Bounding once at the chokepoint is a guarantee; bounding at each capture site would be a promise several writers have to keep. A drop at either layer surfaces through the same `(sending N of M)` preview line capture-time truncation already uses, so it needs no second notice.

**Lifecycle history and revision identity on the wire (plan E1/E2).** `remote._WIRE_LIFECYCLE` is the same kind of gate as `_WIRE_SOURCE_FILES` above, and it ships CLOSED for the reason that one shipped closed: the contexer-teams push schema is server-controlled, an unknown field is a -32602 on every retry, and a poisoned outbox row is permanently stuck. The difference is that this gate covers a strictly BIGGER set of unknowns - three GUESSED field names and two closed vocabularies, against one name there - so the pre-flip checklist is stated in full in `remote.py` beside the constant rather than as "confirm it the way `_WIRE_SOURCE_FILES` was confirmed", because a maintainer who greps `_WIRE_LIFECYCLE` must be able to decide safely from that comment alone. The record-list field name (`lifecycle`) is guessed by analogy with `source_files`; the revision-identity name (`revision_id`) is the WEAKEST of the three and the counter-evidence sits in the same file, where `asubmit_team_decision` spells the same conceptual field `revisionId`; the record's own key names mirror the local `lifecycle.lifecycle_record` shape; `_WIRE_LIFECYCLE_KINDS`/`_WIRE_LIFECYCLE_ACTORS` are closed vocabularies checked against the server's real enums, since `source="plan"` was a rejected VALUE rather than a rejected key; and the count/length bounds were invented by analogy with `INPUT_LIMITS.sourceFiles` and match nothing anyone has read. The exit condition is therefore the identical LIVE validation `source_files` got - same client, same decision, pushed with the gate off and then on against a real endpoint, confirming no -32602 on either `push_decision` or `push_decisions` and that the data actually lands and renders rather than storing NULL. Deliberately a constant and not a config toggle, for the same reason: a toggle can be flipped on against a server that rejects the field, which is the failure mode itself. Everything else in the negotiation is already live - discovery parses, the projection bounds, the outbox carries - so only the unverified spellings stay off the wire.

## Design constraints

- **Silent operation is essential.** Tools must not produce noise — `update_context` silently discards filtered (non-novel) content without logging. This governs *capture and filtering* noise specifically; it does not forbid every user-facing message. Two deliberate, developer-ratified exceptions: the rationale hook's recall notice (above) — a short, structured line naming what Contexer fetched, so retrieval is observable rather than spooky — and `capture_lint`'s bounce message, a model-facing corrective ack (like `constraint_ack`) that tells the calling model to restate a narrative-shaped capture in the same turn; silently discarding those would lose the decision instead of fixing its shape.
- **Secrets never egress (capture stays faithful).** `redact.py` scrubs only where a decision leaves the machine — `remote._wire_args` (the wire guarantee) and `store._share_projection` (preview/outbox parity), surfaced by the `(N secrets redacted before sending)` preview banner. Capture is deliberately **not** redacted: the local store is a verbatim record, and silently rewriting captured decisions would corrupt the product's core value (scrubbing `0600` local files also buys little against a reader who already has `~/.aws`/`.env`). Redaction is default-on (`config.redact_secrets`), deterministic, idempotent, and fail-soft (a config error keeps it ON). Do not add an outbound path that bypasses `_wire_args` without extending redaction to it.
- **No abstraction beyond what exists.** The module structure (`server.py` / `store.py` / `cli.py` / `adapters/`) is intentional. Do not add classes, config files, or layers unless the spec changes. **Adding support for a NEW AI-ASSISTANT TARGET = one new module in `adapters/`; no other files change** - that clause is about tool targets specifically, and is the one case where a whole feature genuinely fits in a single new file because `adapters/__init__.py`'s registry is the only seam it needs. It is **not** a rule that every change must land in one file. A behaviour that is inherently cross-cutting touches every module that owns a piece of it, and confining it to one would mean either reaching into another module's files or duplicating its logic - both worse than the spread. Two shipped examples: the account-switch cache invalidation of #232 has its trigger in `auth.py`, its pull caches in `team_context.py` and its marker log in `share.py`, because each module owns the file it deletes; and `share --global` (#239) needs a selector in `store.py` (which owns `_global.json`) and a push path in `share.py` (which owns the wire and outbox). The test that separates the two cases is ownership, not file count: if each touched module is doing something only it can do, the change is correctly shaped. Adding a *layer* - an interface with one implementation, a config file for a constant, a factory for one product - is what this constraint actually forbids, at any file count.
- **`update_context` is called by Claude Code, not the developer.** Claude Code nominates content; the server filters. The filtering criterion is novelty — >70% token overlap with any existing decision is rejected as a duplicate, not an LLM call.
- **Git hooks and CLI commits are out of scope for capture.** The MCP tool call path is the only capture mechanism — the commit-time guard's git hook (see above) reads and checks already-stored, already-approved decisions; it never captures a new one.
