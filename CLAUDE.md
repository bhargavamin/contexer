# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) and other coding agents when working with code in this repository.

## Commands

```bash
# Install dependencies
uv sync

# Run the server (stdio transport - for manual testing)
uv run python server.py

# Smoke-test the server responds to MCP initialize
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"test","version":"0"}}}' | uv run python server.py

# Test the commit-time guard against currently staged changes
uv run contexer guard --explain

# Preview the assisted anchor backfill (read-only)
uv run contexer guard anchors --list
```

## Architecture

A small package (`contexer/`), intentionally minimal. Each module below is a cohesive concern; adding a feature means finding the module that owns it, not adding a new layer.

- **`contexer/revisions.py`** - pure decision-revision lifecycle and derived metadata: normalization, title derivation, confidence scoring, immutable revision creation, HEAD resolution, cache synchronization, and append transitions. It mutates an already-loaded decision only; persistence, migration, approval, and locking remain in `store.py`. Callers reach these functions on the owner (`revisions.current_content(entry)`), never through a private alias on `store` - see Module boundaries below.
- **`contexer/reconciliation.py`** - pure team-reconciliation state transitions: proposal-slot protection, remote-head deduplication, convergence clearing, and approved/dismissed outcome receipts. It mutates an already-loaded decision only; the dependency stays one-way (`store.py` imports this leaf, never the reverse).
- **`contexer/review.py`** - pure proposal-slot policy: the trust order for the single unreviewed `proposed_revision` slot (`PROPOSAL_TRUST` = human > plan > ai > scan), the displace-and-archive claim (`claim_proposal_slot`), the model-facing refusal ack, and proposal construction (`build_proposal`). Promotion/approval itself stays in `store.py`, since it shells out to git and mutates the entry.
- **`contexer/retrieval.py`** - pure lexical retrieval primitives: `index_tokens` (tokenization for the index/query, distinct from the novelty filter's own tokenizer), `derive_topics` (a fixed topic-alias table), `bm25_rank` (BM25 ranking over the store's decisions), and `extract_artifacts` (file-path/module/error-class/route pattern extraction used both for indexing and for guard file-pairing). The index sidecar (build/read/write) stays in `store.py`, since every writer already holds the store lock there.
- **`contexer/evidence.py`** - bounded, fail-soft evidence-event construction for host hooks and agent-reported conclusions. It records observations only; it never creates an active decision, anchor, or policy effect. The shared directive wrapper emits for both stored changes and store-reported recurrences, using the sanitized repeated directive so aggregation can settle it against the existing decision without opening a duplicate. `record_agent_conclusion` is the sole production emitter for agent conclusions: it refuses blank or capture-lint-invalid text, records rationale presence, and reports spool failure rather than presenting loss as capture. Candidate scoring limits what qualifies for review; reconciliation separately bounds how many qualifying atomic candidates reach review without dropping their raw events. Host coverage uses a closed vocabulary and per-adapter declarations, allows runtime state only to downgrade coverage, and reports assistant conclusions as model-reported rather than automatically captured. Hook callers emit last so evidence failure cannot change editor or prompt behavior.
- **`contexer/spool.py`** - atomic per-repository evidence-spool storage, retention, holds, quarantine, and durable receipts. Raw acknowledged events remain recoverable until a terminal attributed receipt exists; malformed state is reported rather than overwritten as empty. A valid event whose repository identity does not match its physical spool is routed to that spool's quarantine only after its own fixed-size identity receipt names the event, observed key, expected key, reason, time, and physical spool slug. The spool binding is part of the receipt filename and validation, so a copied or damaged receipt cannot authorize another spool's raw deletion. These per-event receipts deliberately outlive raw-quarantine retention: a bounded total ledger plus raw expiry could erase both records of an older route. Routing lists and parses pending files once for a batch; receipt failure leaves the pending source untouched, and a crash after the receipt but before the atomic move is retried idempotently. The pre-existing bounded aggregate receipt ledger remains read-only upgrade input. The held candidate manifest is also the durable half of the candidate state machine: `deferred_attention` retains every event id outside destructive retention until review capacity opens; state updates are atomic and refuse missing, unreadable, or unknown state rather than inventing progress; legacy manifests migrate on read, and invalid/split states remain visible as incomplete. An orphaned hold whose decision no longer exists is deleted only after an idempotent, bounded orphan receipt is durably written; a failed or damaged receipt ledger leaves the raw hold intact and reports the incomplete cleanup. Its cumulative gap ledger distinguishes unreceipted/malformed quarantine loss (`drops`) from pending-event expiry (`expired`); expiry of valid identity-routed raw is counted separately and is not loss because the durable receipt remains. Status reports receipt count, unreadable count, and bytes; unreadable receipt state retains valid raw fail-closed. TTL-gated maintenance remains independent of whether reconciliation runs so contention and early-return paths still receive retention and orphan cleanup. Status discovery enumerates spool-only repository slugs so evidence cannot disappear merely because no store entry exists yet. Disposition vocabulary contains only states the system actually writes.
- **`contexer/candidates.py`** - pure deterministic aggregation and scoring from evidence events into review candidates and uncertain signals. Candidate identity and ordering are stable across input permutations, enabling idempotent hold-first recovery. The public attention key orders lifecycle and security significance, certainty tier, score, first observation and candidate id, so new and deferred work share one deterministic admission order. Every signal has a closed typed relationship and explicit certainty. Structural links work in either event order and are the only automatically proposed file scope. Forward causal proximity is bounded within a session and remains supporting evidence, but its files are only possibly related; backward-only temporal links stay uncertain, score zero, never consume the event, and also contribute only possible source files. Reconciliation explicitly replaces the store's recent-edit anchor guesses with the candidate's structurally confirmed `source_files`, including an empty list, so temporal proximity cannot re-enter the anchor pipeline through the sidecar. Contradiction scoring requires opposite negation polarity so a prohibition repeated verbatim cannot contradict itself. The 1,000-event aggregation cases are performance-gated; the optimized postings path reduces observed cost but does not claim to remove every worst-case quadratic comparison.
- **`contexer/reconcile.py`** - coordinator that drains eligible spool events into review-only decisions, lifecycle proposals, or durable disposition receipts. Before candidate aggregation, it compares every event's repository identity at the normal consumer chokepoint; a failed route keeps the source pending and suppresses that pass's retention. No editor-hook writer scans or validates the spool. Reconciliation admits at most five new review items per pass and never takes a repo beyond ten total pending reviews; every existing review lane consumes that capacity, while duplicates and insufficient evidence continue without a slot. Excess atomic candidates enter spool-owned `deferred_attention` and resume in deterministic priority order from the exact proposal and lifecycle basis frozen in their manifest, not by reclassifying against earlier admitted batches. Reconciliation owns coordination and crash-boundary idempotency while spool, store, candidates, and lifecycle retain their extracted concerns. Its persisted state machine holds and verifies evidence before writing through the ordinary store or lifecycle owner, re-reads authoritative state, records disposition evidence, and removes the hold only after review. Interrupted phases reclassify their own held events under the same deterministic directory identity; unknown phases, missing sources, and unattributed holds stay visible and are never guessed away. Every host reconciles on shared session start before reading the store, using an unscoped session id so crash-left evidence remains recoverable. Complete passes with no error and no deferred attention stay silent; deferred work emits one count-only status, and partial/error diagnostics remain visible. Reconciliation uses a non-blocking per-repo `flock`; contention defers the pass, lock unavailability fails closed with evidence retained, dry runs create no state, and the lock is acquired only after the unlocked fast path finds work.
- **`contexer/policy_api.py`** - read-only facade that selects approved policy decisions, invokes `policy.py`, and formats advisory operation reports for MCP and CLI. A reported block is not itself enforcement; the operation-owning adapter decides whether and how to enforce it.
- **`contexer/review_impact.py`** - read-only owner of the approval-impact preview shared by MCP review, the CLI, and the console's one-decision detail view; the console consumes the same rendered lines rather than maintaining a second presentation, and its polling dashboard does not pay the review-context cost. Evidence is separated into confirmed, supporting, and possibly related tiers, proposal provenance is distinguished from the standing decision's origin, and untrusted free text is collapsed to one line at the render boundary. Confirmed-anchor wording is lane-aware: lifecycle and reconsideration evidence files are never promised as anchors because those actions do not write anchors. Non-authoritative possible files appear only here under their canonical `possible_source_files` key and are never included in approval anchoring. Armed-policy status is selected through the guard's own active selector, while approval itself never arms a rule. Displaced reconsideration holds with a stale basis revision remain visible instead of being mistaken for the question currently on screen.
- **`contexer/server.py`** - MCP server entry point. Defines the thin public tools for capture, human review, lifecycle and reconsideration actions, agent-reported conclusions, evidence reconciliation, advisory policy evaluation, retrieval, bootstrap, and sharing using `FastMCP`; deterministic storage and evaluation stay in their owner modules. Generates a `SESSION_ID` (UUID) at process start shared across all tool calls in a session. An AI-inferred constraint or architecture decision that lands `pending_approval` returns a "pending review - does not block your work" notice, never a blocking prompt; pending items are pulled on demand via `review_pending`, and SessionStart injects only a count. `share_decision` previews what would leave the machine before sending (`confirm=false` by default) and requires an explicit `confirm=true` to push; `list_shareable` and a comma-separated multi-select support reviewing and pushing several decisions in one call.
- **`contexer/store.py`** - all read/write and filtering logic for the local decision store. `_passes_filter` is the core novelty gate: content is stored only if it is not a near-duplicate of an existing decision (token-overlap check). In front of it, at the write tools, a capture-quality gate (`capture_lint`) rejects a long AI/plan-sourced capture that reads as narrative rather than a stated decision, or that bundles multiple unrelated claims into one record, and asks the calling model to restate it in the same turn rather than silently discarding it. A `replace_id` correction that is outranked by a higher-trust pending proposal is refused in-band rather than silently dropped, and the model is told to surface both versions to the developer. Repetition of an active decision records bounded recurrence history by session, source, match kind, and count without changing confidence or approval; inactive matches do not accrue corroboration and are reported only to the reconsideration lane. Per-decision evidence summaries are separately capped and record actual evictions, preserving honest truncation without conflating collapsed recurrence rows with distinct disposition receipts. Human-facing renders (`contexer review`, the approval CLI) show full decision bodies with capture metadata (time, origin, corroboration, source files, staleness); model-facing renders clip long bodies with a pointer to the full text. Legacy pre-provenance entries are migrated transparently on load. A periodic re-verification pass re-checks scan-derived conventions against the current codebase and proposes withdrawals when evidence disappears. Storage is capped at `MAX_ENTRIES = 500` per repo, with separate, smaller display caps for overview vs. filtered queries. Bootstrap (first-run setup) infers how familiar the developer is with the repo from git signals, asks a small number of intent-focused questions the codebase itself cannot answer, and self-stores a consolidated architecture summary plus each measured convention as its own decision, tiered by evidence strength. Retrieval for ad hoc prompts (`get_context_for_prompt`) is BM25-ranked against a disposable per-repo index built from the store; a query with strong relevance gets full decision content injected, weaker relevance gets a one-line pointer, and no match stays silent. A prompt naming a specific file is additionally routed through the same file-pairing signal the commit-time guard uses, so decisions governing that file surface without an explicit query. Every entry that is anchored to source files gets a staleness check at render time (has the anchored code changed since capture) and a working-set cache avoids re-injecting a decision already shown this session. Decisions governing a set of files are retrievable directly via `get_context(files=[...])`, backed by `guard_engine.decisions_for_files` (see below). Anchor lifecycle verification (renamed/removed anchors) lives in `contexer/anchors.py`; conflict rendering (a decision with both a standing value and an unreviewed proposed update) lives in `contexer/conflicts.py` - see their own bullets.
- **`contexer/guard_engine.py`** - the commit-time guard engine (staged-file plumbing, Tier-1 advisory pairing, Tier-2 armed blocking rules), extracted out of `store.py`. `store.py` stays the public facade for it: it re-exports the five public entrypoints (`guard_staged`, `guard_candidates`, `arm_guard`, `disarm_guard`, `dismiss_guard`) lazily via a module `__getattr__`, not an eager import, to avoid a load-order cycle with `store.py`. Approval-time anchoring stays in `store.py` (it's approval machinery, not guard logic). `decisions_for_files(repo_path, files, decisions=None)` is the retrieval surface used by `get_context(files=...)`: which stored decisions govern a given set of files, matched via `source_files` membership or a path/module-shaped artifact mined from the decision's own content, across both the repo and global stores.
- **`contexer/policy.py`** - pure deterministic policy selection and evaluation shared by the commit guard and evidence-policy surfaces. It owns check validation, path applicability, regex/secret matching, line-level outcomes, and honest omitted/partial results; callers retain responsibility for deadlines, transport, and whether an incomplete evaluation fails open or closed. Keeping rule meaning here prevents the guard and other policy consumers from implementing divergent evaluators. Its request path rules and 300-character bounds intentionally mirror `evidence.py` rather than importing them, because `policy.py` must remain a leaf while `evidence.py` imports store; changes to either copy require parity updates.
- **`contexer/anchors.py`** - anchor lifecycle verification, extracted out of `store.py` to keep a second verification family out of the main file. `verify_anchors(repo_path, force=False)` periodically re-checks every anchored, active-status decision's `source_files` against the working tree: a renamed file is detected via git history and the anchor address is silently corrected in place (not a review event, since the decision's content is unchanged); if every anchored file for a decision is truly gone, a retirement proposal is attached and routed through the normal review flow rather than silently dropped. Approving a retirement clears the entry's anchor so it exits decay participation. Verification work is time/call-budgeted per run; running out of budget leaves the remaining entries unverified this cycle rather than guessing.
- **`contexer/lifecycle.py`** - decision retirement and restoration, including the independent `proposed_lifecycle` review lane. Content updates and lifecycle changes use separate proposal slots so neither can displace the other. A third `proposed_reconsideration` lane asks whether an explicitly restated inactive decision should return; only explicit user-directive evidence can open it, its identity binds the inactive basis revision, and restore/edit/skip/dismiss outcomes are recorded durably. Reconciliation supplies the basis revision and inactive state it classified; attachment rechecks both under the store lock and returns structured stale/occupied/not-found/live reasons. A stale basis or state leaves the materializing hold and its raw evidence intact so the same candidate can be replayed against current state instead of attaching a question to a different revision. Restoration without trustworthy historical active status fails toward pending review, while only an explicit restore-with-edit can return approved. Retirement requires an explicit human action, records immutable lifecycle history against the reviewed revision, settles any evidence checkpoint only when the lifecycle transition actually occurs, and moves the decision to the tombstone sidecar; restoration appends history rather than rewinding it. The module owns the local lifecycle vocabulary (`RECORD_KINDS`/`RETIRED_KINDS`), with reconciliation deriving its retired set from that owner; the remote wire vocabulary remains deliberately separate because it represents the server contract. The module reaches store-owned persistence helpers through the `store` module object. `store.restore_decision` remains a lazy compatibility export because it was public before extraction; new lifecycle callers import the owner directly.
- **`contexer/conflicts.py`** - conflict rendering and resolution memos, extracted out of `store.py`. A live decision carrying an unreviewed Suggested Update that isn't purely bookkeeping (a scan re-verification or an anchor-retirement clause) or a title-only edit is an *open conflict*: both the standing content and the labeled update render together, with dates, everywhere a decision is shown to the model, with guidance not to resolve it via code exploration - only the developer knows which is right. `resolve_conflict(entry_id, choice)` records the developer's explicit pick; the pick is advisory (it changes what's shown) rather than authoritative (a full review/approval action is still required to change the decision's actual status).
- **`contexer/console_api.py`** - local-console read projections: every shape the `contexer ui` console renders for one repo, one store, or the global rules. A one-way dependency (`ui/api.py` -> `console_api` -> `store`); the console never opens a store file directly. Everything here is a pure read except `delete_global_rule`.
- **`contexer/scope_audit.py`** - a read-only cross-store audit that finds decisions saved into the wrong repo's store, using session-id fingerprinting (one write-session id appearing in more than one repo store is evidence of a misroute). Excludes deleted-store tombstones and unattributed memory-sync imports, which would otherwise produce false positives. Reports only; remediation (ignoring or moving an entry) is a manual developer action. Surface: `contexer scope-audit`.
- **`contexer/repo_key.py`** - canonical remote-key normalization plus the evidence repository-identity comparison. A batch derives the checkout's local identity and origin once, then compares every distinct observed key against that frozen basis. Only that trusted checkout origin may invoke SSH alias resolution; untrusted remote-shaped spool keys receive bounded syntactic normalization and can never spawn one `ssh -G` process per attacker-chosen host during session start. Local event keys use `store.canonical_store_key` and real paths so a linked worktree and its main checkout compare equal; remote-shaped event keys are accepted only when the checkout's origin normalizes to the same canonical key. A non-empty key that cannot be verified is a mismatch. Schema V1 has always required `repo_key`, so a missing key receives no legacy compatibility exemption: the schema reader quarantines it as malformed before aggregation.
- **`contexer/miner.py`** - deterministic convention mining, stdlib only. `mine_conventions(repo_path)` measures conventions with whole-repo evidence embedded in the sentence itself (e.g. "Functions use snake_case naming (98% of 412 functions across 37 files)"): config-encoded rules (linters, formatters, CI), AST source statistics (naming, type hints, docstrings, imports, exception style), test conventions, and commit-message style. A convention needs >=90% dominance with >=20 samples to be marked high-confidence (auto-approved), 60-89% is medium-confidence (lands pending review), and anything below either bar is not emitted at all - silence over noise. Never raises; JS/TS/Go/Rust source-level statistics are out of scope (only their config-encoded conventions are mined).
- **`contexer/updates.py`** - update delivery, stdlib only: how a developer finds out a new release exists. Owns the FACT (the latest release, and any declared minimum supported version, read from the PyPI JSON the version check already downloaded) and the POLICY (whether to say something right now), never the rendering, which belongs to each adapter's `notify()`. State lives in one machine-global sidecar rather than a per-repo flag, because the budget is once per *release* and a slug-keyed flag fires once per repo per release. `notice()` reads that file and never performs network I/O; fetching happens only in a detached background process (`spawn_refresh`) or from an explicit CLI command, which is what keeps the per-prompt hook path free of network calls. Every host refreshes, including Cursor, which has no channel to render a notice into: without that call its state would never be fetched at all and the terminal backstop would have nothing to say. `deliver(render)` hands the owed notice to an adapter's `notify` and records it as said **only if that adapter actually delivered it**, so a host with no user-facing channel does not silently burn the notice. A declared floor produces a louder line that replaces the routine one; nothing here ever mutates an install. `CONTEXER_NO_UPDATE_CHECK` disables the module entirely.

  **Declaring a floor is a manual, case-by-case maintainer act, and nothing automates it.** No floor is published today; absent key means no floor. To declare one, add a `Minimum supported version` entry to `[project.urls]` in `pyproject.toml`, pointing at the release tag that explains why the floor moved (the value is a URL rather than a bare version precisely so it leads somewhere that explains itself). release-please must never set this key: cutting a release is routine, and declaring every older install unsupported is not. Below the floor Contexer prints one louder line and nothing else - it never refuses to run and never degrades, because that would make it worse than not being installed on a machine that may be offline and unable to upgrade.
- **`contexer/redact.py`** - deterministic secret redaction, stdlib only. `scrub(text)` replaces each detected secret with `[REDACTED:<kind>]`. Detects high-confidence provider token shapes (AWS, GitHub, Slack, Stripe, Google, OpenAI/Anthropic, SendGrid, npm, PyPI, Twilio), PEM private keys, JWTs, Bearer tokens, and connection-string passwords, plus a keyword-gated generic catch-all for `password`/`secret`/`token`/`api_key`/etc. that only fires on values that look secret-shaped (skipping obvious placeholders). No entropy heuristic - it would false-positive on SHAs/UUIDs/base64. Idempotent and never raises. **Redaction is egress-only by design**: local capture is never scrubbed (the store is meant to be a faithful, verbatim record), and secrets are removed only at the two points a decision can leave the machine - the outbound wire call and the share-preview projection, both funneling through the same bound. Default-on, fail-soft toward staying on. Do not add an outbound path that bypasses the existing redaction chokepoint.
- **`contexer/remote.py`** - outbound Teams protocol adapter. Lifecycle history (`lifecycle`) and OSS revision identity (`revision_id`) are enabled only against the validated Teams contract; a shared, hash-pinned fixture keeps both repositories' field names, bounds, and enum vocabularies aligned while local lifecycle vocabulary remains independently owned by `lifecycle.py`. If a server advertises lifecycle support but rejects the augmented payload, the client retries the base decision exactly once through the ordinary serializer; only a successful base retry proves an optional-protocol rejection, and batch fallback records blocked lifecycle state only for rows the retry explicitly confirms saved. A lifecycle identity conflict is a permanent contested row rather than an invalid shape and never triggers a base-only resurrection. The refused delta is retained as `lifecycle_pending`, keyed to the advertised capability fingerprint and re-offered only after that fingerprint changes, preventing both data loss and retry storms. Outbox reconciliation treats base delivery and lifecycle-delta delivery as separate facts: a shared decision ID cannot purge the pending delta, which is settled only when the lifecycle retry itself succeeds. Stage-aware merging refuses to downgrade a lifecycle-pending row to an ordinary retry, preserving the fingerprint while refreshing the decision body. The author-scoped `sourceRetired` read projection decodes only to `RemoteDecision.source_retired`; it is presentation state, never converted into a local lifecycle transition.
- **`contexer/team_context.py`** - bounded, separately persisted team-context cache and render owner. It preserves the author-scoped `source_retired` boolean through full and incremental pulls, renders one concise “personal source retired; team copy remains authoritative” marker (including architecture rows normally deferred), and carries open/clear transitions through the bounded per-consumer sync log. Account changes delete the whole cache namespace. The marker never calls reconciliation proposal, local lifecycle, suppression, or Guard paths.
- **`contexer/adapters/`** - one module per AI-assistant target (`claude.py`, `cursor.py`, `codex.py`, `gemini.py`), each owning that tool's MCP registration, hook wiring, install/uninstall/status, provider-specific hook output, a static `EVIDENCE_COVERAGE` declaration, and the host name passed into shared reconciliation. Coverage is honest-first: Cursor has prompt directives but no edit hook, unimplemented test/diff capture stays unavailable, and agent conclusions are model-reported rather than observed. Prompt/editor hooks pass host payload plus process cwd into the shared filesystem resolver: it walks parents for a `.git` marker and canonicalizes linked-worktree store identity without spawning Git. These paths never wait on the decision-store lock, scan the spool, call a model/network, or run Git; prompt retrieval deliberately omits Git-backed staleness decoration while explicit MCP/UI reads retain it. Session-start reconciliation is owned by the shared store path so new adapters inherit crash recovery without duplicating it. `__init__.py` is the registry (`detect()` / `select()`). `base.py` holds shared config-file helpers. Hook migration is owner-aware and filters each entry independently: a current Contexer command retires stale Contexer siblings without deleting foreign commands in the same group, while generic substrings such as `update_context.py` or `uv run --directory` are never sufficient ownership evidence. Exact namespaced legacy identities remain removable. **A real gotcha for anyone touching adapter marker-matching:** matching a hook's identity against `str(hook_dict)` (its Python repr) breaks silently whenever the command contains a double quote (any `python -c "..."` command does), because repr re-escapes inner quotes - a marker check written that way will never recognize the hook it just installed and will re-fire on every install forever. Use the raw-command match helper instead for any marker containing a quote. Gemini stores MCP and hook configuration together in `~/.gemini/settings.json` and uses different event names (`SessionStart`, `BeforeAgent`, `AfterTool`, `PreCompress`, `SessionEnd`); because it has no `PostCompress` equivalent, it sets a flag and re-injects context at the next `BeforeAgent` event instead.
- **`contexer/memory_sync.py`** - imports Claude Code's memory-tool facts (`~/.claude/projects/<slug>/memory/*.md`) into the store, so decisions a session persisted to the file-based memory tool instead of calling `update_context` still reach Contexer. No model in the loop: parses YAML frontmatter + body, splits multi-section docs into one entry per `##` heading, assigns a subtype by keyword rules, and upserts keyed on a stable key derived from source file + section, so an edited fact updates in place rather than duplicating. Fail-soft per file.
- **`contexer/share_status.py`** - typed outcome objects (`ShareStatus`, `ReconcileStatus`) for what a share or reconciliation batch actually did, plus one renderer (`describe`) that turns a status into English. Every public `share.py` entry point returns one of these frozen objects rather than a prose sentence, so a caller (CLI, console API) can read `outcome`/`sent`/`queued`/`at_capacity`/`invalid`/`lost` as data instead of pattern-matching text. `outcome` is a stable machine token. A shared refusal-classification table (`share._TRANSIENT_REFUSALS`) decides whether a failed remote write is retried (transient - e.g. a rate limit) or dropped (terminal); rate limiting is classified by exception type, not by matching wording in an error string. The outbox lock is asyncio-native: a non-blocking `flock` attempt with a poll-and-retry loop, so one process holding the file lock never freezes every other tool call on the MCP server. Lifecycle-pending rows are durable protocol deltas, not disposable ordinary retries: they are persisted atomically after a successful base fallback, cannot be evicted to admit an ordinary row, and a full outbox reports an honest not-queued outcome rather than claiming success for a row it discarded.
- **`contexer/cli.py`** - the `contexer` console script: bare invocation runs the MCP server; subcommands `install [--target claude|cursor|codex|gemini|all]` / `uninstall [--purge]` / `reinstall` / `upgrade [--dry-run]` / `status` / `scope-audit` / `version` / `help` manage tool configs. `upgrade` upgrades the binary and then re-syncs config, but only for an install it can upgrade safely: a clone installed with `uv tool install --from <path>` (identified by PEP 610 `direct_url.json`) and a pip install both print the right command instead of running it, since replacing a developer's own build, or picking an environment that is theirs to choose, is not the CLI's call. Restarting the assistant is always the developer's step, because the MCP server is spawned once per session. `install` auto-detects present tools and falls back to Claude Code when none is detected; `--target` overrides.
- **`server.py`** (repo root) - back-compat shim importing `contexer.server`; keeps `uv run python server.py` working.
- **No `requirements.txt`.** `pyproject.toml` is the single dependency spec (managed by `uv`); do not re-add one. The `mcp` dependency is bounded below 2.0, since `mcp` 2.0.0 removed the module this server imports.

## Module boundaries

`store.py` is decomposed into single-purpose owner modules (`revisions.py`, `reconciliation.py`, `review.py`, `retrieval.py`, `evidence.py`, `spool.py`, `candidates.py`, `reconcile.py`, `policy.py`, `policy_api.py`, `lifecycle.py`, `review_impact.py`, and others), enforced by dynamic caller discovery plus the three rules in `tests/test_module_boundaries.py`, so extraction cannot erode silently as new modules are added:

- **Rule 1 - production code imports the owner, always.** `store.py` keeps a small, frozen back-compat facade (a lazy `__getattr__`) for names that were public on `store` before an extraction moved them; nothing new is added to it, and a name with no consumer left is dropped. Tests should address the owner module too, not the facade, so a test doesn't end up merely pinning the shim.
- **Rule 2 - a `store` name read by a second module is interface, so it becomes public** (unprefixed, no leading underscore) rather than staying a "private" name two modules already depend on. This applies to `store` specifically, since it's the module everything else depends on; it does not extend to other modules' shared private helpers.
- **Rule 3 - no module copies another module's names onto itself.** A caller that needs a name from a leaf module reaches it qualified on the owner (`revisions.current_content(entry)`, `review.build_proposal(...)`), never through a second local alias. A stale alias fails silently (an `AttributeError` inside a fail-soft wrapper just stops working, with nothing raised loudly), which is why this is enforced by a test rather than left to code review.

A module reaching into `store` must always import the module object (`from contexer import store`), never `from contexer.store import X` - a value a test monkeypatches on `contexer.store` is only visible at the call site through the module-object form.

## Storage

Context is stored at `~/.contexer/<repo_slug>.json` - one file per repo, plus `_global.json` for cross-repo decisions. The slug is the repo path with non-alphanumeric characters replaced by underscores. Each file holds a flat list of entries. Writes are atomic (unique temp file + `os.replace`, mode `0o600`) so readers never see a torn file; a corrupt file is read as empty on RENDER paths, but any write path that could destroy queued data (e.g. the share outbox) must read through a reader that raises on corruption rather than silently treating "unreadable" as "empty" - the two are not the same thing, and collapsing them on a write path risks overwriting data that was actually still there.

Linked git worktrees share the main worktree's store: `canonical_store_key` reads the worktree gitfile and its `commondir` directly, with no subprocess, so every slug-keyed artifact (store, lock, sidecars, flags, team cache) collapses onto one file while code-staleness checks still see the physical worktree path. Failed/partial metadata is not cached; submodules and separate-git-dir repos keep their own keys.

### Decision / Revision model (Git-like: storage preserves history, replay = current)

A decision is the logical engineering decision; a **revision** is one immutable version of it. Storage preserves every revision forever; replay exposes only the current approved one (like Git keeping every commit but cloning HEAD).

The model is **embedded**, not normalized into a second collection: each decision entry owns its revisions inline (`revisions[]`) with an explicit `current_revision_id` pointer. This local store is a capture client + cache + outbox; heavier query-side concerns (timeline, diff, audit, team approval, semantic search) live upstream in the optional remote teams service that decisions can be pushed to.

**Decision entry** carries: `id`, `type` (`task` | `decision`), `subtype` (`architecture` | `constraint` | `pattern` | `convention`), `status` (`approved` | `suggested` | `pending_approval` | `ignored`), `current_revision_id`, `session_id`, `session_ids`, `timestamp` (immutable), `updated_at`, `occurrence_count`, `created_by`, `revisions[]`, and optionally `proposed_revision` (a pending Suggested Update, never replayed until approved), `memory_key`, and `source_files`/`anchor_commit` (staleness anchor). The entry also keeps a synced head-cache (`content`/`revision`/`confidence`) of the current revision for O(1) reads.

**Revision object**: `revision_id`, `decision_id`, `version_number` (1-based), `content`, `confidence_score`, `evidence`, `created_at`, `approved_at`, `source` (provenance: `ai` | `human` | `scan` | `bootstrap` | `memory`). Revisions are immutable once superseded.

**Which repo a tool call targets** is resolved with this precedence: (1) an explicit, sanity-checked `repo_path` argument; (2) the repo bound to the running MCP-server process at startup; (3) a shared `~/.contexer/.current_repo` pointer as a last resort, guarded against ever selecting a config directory as a store target. Hooks resolve host payload fields first and then their process cwd, walking parents for a `.git` marker without Git; a non-git project remains a first-class store keyed by its absolute path. Every capture surface stamps which resolution branch it used, and this resolution is diagnosable (`contexer scope-audit`) if a decision ever ends up in the wrong repo's store.

## MCP integration

`contexer install` registers the server in `~/.claude.json` under `mcpServers`, pointing at the installed console script:

```json
{
  "contexer": {
    "type": "stdio",
    "command": "/Users/<you>/.local/bin/contexer"
  }
}
```

(A from-source dev install via `scripts/install.sh` wires `uv run --directory <clone> python server.py` instead.)

For Cursor, the equivalents are `~/.cursor/mcp.json` (MCP server registration) and `~/.cursor/hooks.json` (hook wiring), managed by `contexer/adapters/cursor.py`. The MCP server entry in `mcp.json` uses the same `contexer` command; hooks use Cursor's `sessionStart` and `beforeSubmitPrompt` event names.

For Codex, the MCP server is registered in `~/.codex/config.toml` (TOML) as `[mcp_servers.contexer]` with `command = "<contexer-bin>"`, and hooks live in `~/.codex/hooks.json` (JSON, same schema and event names as Claude's `settings.json` `hooks` block), both managed by `contexer/adapters/codex.py`. The `config.toml` edit is surgical text manipulation (validated with `tomllib` before writing) so only the contexer stanza is touched.

For Gemini CLI, both the MCP server and managed hooks live in `~/.gemini/settings.json`, managed by `contexer/adapters/gemini.py`. Installation preserves unrelated keys, servers, and hook groups.

## Session behaviour (hooks)

`~/.claude/settings.json` wires up hooks globally (applies to every repo):

- **`SessionStart`** - imports any pending memory-tool facts, then injects all *approved* conventions, patterns, and constraints as project rules (constraints render in full; conventions/patterns render title-only with a pointer to the full reasoning, to stay within the host's context-injection size limit), a count pointer for deferred architecture decisions and for decisions awaiting review, and a bootstrap offer if no context exists yet. Resume- and compaction-aware: a resumed session with existing context in the transcript is not re-injected; a `compact` source silently re-injects the full context, since there is no separate post-compaction hook that could do it instead.
- **`PostToolUse` (Write|Edit, silent)** - records the edited file into a per-repo sidecar (recently-edited files feed the anchor-candidate mechanism below) and flags that a capture reminder is owed on the next prompt. Completely silent to the user.
- **Deterministic mid-session review nudge.** A per-repo flag is set by the store itself whenever a new item lands in pending-review state (a new `pending_approval` entry, or a freshly attached proposed update), and cleared once a nudge has fired for it and the repo still has something pending. This surfaces mid-session, not only at the next `SessionStart`.
- **No `Stop` hook.** An end-of-turn hook that prompted the model to capture/review decisions was tried and removed - it added latency and depended on model behavior for no benefit over the deterministic flag-based approach above.
- **`UserPromptSubmit` (anchor/reminder, every prompt)** - the Python directive hook resolves host payload/PWD without Git and refreshes the shared pointer fail-soft; a separate shell-only command owns no repository identity and checks the pending-capture flag, injecting a reminder to call `update_context` for decisions from the previous turn.
- **Bookkeeping writes are best-effort everywhere.** The shared repo pointer and the various flag files are bookkeeping, not context - a sandboxed host that can write the workspace but not `~/.contexer` must still get full context injection; the invariant is that inability to write an optional bookkeeping file never prevents a hook from rendering context.
- **`UserPromptSubmit` (bootstrap, command, once)** - injects the bootstrap offer on the first prompt if no context exists, as a fallback for when SessionStart is skipped.
- **`UserPromptSubmit` (constraint, command, every prompt)** - detects prescriptive directives in the raw prompt text ("always X", "never Y", "from now on Z", or an explicit "store this decision:") and stores them as constraint/convention decisions automatically, no model involvement needed. Known speaker/transcript, output/results/response, log, traceback, pytest, blockquote, attribution, changelog, grep, diff, fenced-code and closed harness-container shapes are removed before classification; unbounded Contexer/usage-limit injections fail closed as a whole. A clean, standalone, present-tense directive is stored trusted (`approved`) immediately; a directive with a conversation-local referent or ambiguous arbitrary-name label is stored `pending_approval`, while explicit scope/topic labels and authority wrappers preserve recall. A later restatement that substantially overlaps its own pending twin promotes it in place instead of accumulating a duplicate.
- **`UserPromptSubmit` (rationale, command, every prompt)** - when the prompt contains rationale-style language (why, reason, decided, etc.) or is a comprehension question, matching decisions are retrieved and injected automatically; a short user-facing note names what was recalled. Silent no-op otherwise. This hook also carries the **new-release notice**, rather than a hook of its own: it already runs on every prompt, so carrying it costs no extra process, and `systemMessage` is a single slot, so a recall note and an update notice can never both be emitted in one turn. Recall wins when both are due, and the update notice is not consumed when it yields, so it is still owed on the next quiet prompt. Gemini carries the same notice on its own `SessionStart` hook, the event whose documentation names `systemMessage`. Cursor is the one host with no user-facing channel at all (its `user_message` renders only when an action is BLOCKED), so a Cursor developer gets the notice through the CLI instead, on the next `contexer` command; Cursor's prompt hook still refreshes the state so that command has something to say.
- **`UserPromptSubmit` (team poll, command, every prompt)** - non-blocking delta poll for newly-synced team decisions; the prompt path never performs network I/O itself, a background refresher does that and results surface on a later prompt.
- **`PreCompact`** - flushes memory-tool facts and reminds the model to call `update_context` for anything not yet stored, before the context window collapses.
- **No `PostCompact` hook** - after compaction, Claude Code fires `SessionStart` again with `source="compact"`, which already re-injects the full context; a separate `PostCompact` hook was tried and removed since it could only dump raw content into the visible transcript, not inject it.
- **`SessionEnd`** - flushes memory-tool facts on clean exit.
- **Legacy cleanup on upgrade.** Older installs may have left stale hook entries (repo-local settings, hooks pointing at removed tool names) behind; the installer self-heals these on the next install/session start rather than requiring a manual uninstall/reinstall cycle.

**During a session**, call `update_context` whenever you make a significant decision, establish a pattern, or document a constraint. This is mandatory, not optional. Call it proactively within the same turn a decision is made, rather than waiting for the next prompt's reminder.

Call `update_context` for any of these:
- A technology, library, or approach chosen over alternatives (subtype: `architecture`)
- A file structure, naming convention, or code organization pattern established (subtype: `pattern`)
- A rule stated by the user or inferred from their preferences: "always X", "never Y" (subtype: `constraint` or `convention`)
- A build, deploy, or tooling convention established (subtype: `convention`)
- Any decision that would surprise a future Claude session if it wasn't stored
- A synthesized understanding of how a subsystem works, produced while scanning the codebase to answer a question (subtype: `architecture`) - capture it in the same turn; the session may end with the answer.

Pass the full reasoning, not just the conclusion. Pass `subtype` so decisions are retrievable by type. The server's novelty filter discards duplicates silently, so err on the side of calling it.

**Retrieving context JIT**: call `get_context` **before reading files** for any question about architecture, design decisions, rationale, constraints, patterns, or conventions. Fall back to reading files only when context is missing or the question is about current code state (exact syntax, current values). Use `query` for keyword search or `entry_type` to retrieve a specific subtype. Use `limit` to override the display cap. When results are truncated, the output includes a `"showing N of M"` note so you know more exist.

## Commit-time guard (`contexer guard`)

A git `pre-commit` hook - install with `contexer guard --install-hook` (never wired automatically by `contexer install`) - that checks staged files against stored decisions when you commit. Two tiers, both implemented in `contexer/guard_engine.py`:

**Tier 1 (advisory, non-blocking, always exits 0)** pairs a staged file against an `approved` decision whose provenance is trusted (human, scan, bootstrap, or plan-sourced, or explicitly approved by a developer - never an unreviewed AI guess). Pairing is via `source_files` membership or a path/module-shaped artifact mined from the decision's own content. Noise control: a permanent per-(decision, file) dismiss list, and a content-keyed throttle that only re-advises a pair once the file's staged content actually changes since the last advisory. Capped at a small number of advisories per run.

**Tier 2 (blocking, exit 1)** fires only for a decision explicitly armed via `arm_guard` (CLI: `guard arm <id> --regex '<pattern>' [--flags i] [--paths <glob>] [--message <hint>]` or `--check secret`). Arming requires the decision to already be `approved` and the check to be machine-checkable; approval is re-checked at run time, not trusted from arm time, so an armed decision that's later un-approved stops firing automatically. The deterministic meaning of an armed check lives once in `policy.py`; `guard_engine.py` owns only staged-file plumbing, budgets, and commit-time fail-open behavior.

**Invariant: the run path never blocks a commit on its own failure.** The whole guard run is wrapped in a time budget and a broad exception guard; any internal error or budget overrun degrades to a warning line and exit 0, never a half-blocked or crashed commit. A staged file the guard could not read (too large, binary, unreadable) is explicitly reported as unchecked rather than silently treated as clean, whenever an armed rule's scope would otherwise have covered it.

`guard --install-hook` embeds the resolved binary's absolute path in a fenced block in `.git/hooks/pre-commit` (existence-guarded, so an uninstalled/upgraded binary no-ops instead of breaking the commit), and refuses with guidance when `core.hooksPath` is set or an existing pre-commit-framework hook is detected (use `.pre-commit-hooks.yaml` instead). `--uninstall-hook` strips exactly that fenced block, preserving any foreign content.

**Approval-time anchoring.** `approve_decision(repo_path, entry_id, action, content="", *, source_files=None)` takes a keyword-only `source_files`: when supplied on an `approve`/`edit` action, it anchors the entry to those files and the current HEAD commit. Approval is treated as a human revalidation of content: approve/edit is only legal on a decision still awaiting review, never a "re-approve" of an already-settled decision. There is no bulk approval path - every approval is one reviewed id at a time, by design.

**Anchor accrual.** An unanchored decision can still be Tier-1 paired incidentally (via a content artifact match), but it is invisible to staleness tracking, which needs a real `source_files` anchor. Two mechanisms close that gap, both requiring an explicit human signature before a candidate anchor ever becomes guard input:
- **Assisted backfill** (`contexer guard anchors [--list]`) mines a trusted, currently-unanchored decision's own content for path-shaped artifacts that still exist on disk, and lets the developer ratify which ones to anchor in an interactive CLI loop.
- **Capture-time candidates**: when a new capture lands `pending_approval` without explicit `source_files`, the repo's recently-edited files (from `PostToolUse` tracking) are stashed as an unconfirmed possible relationship on the entry. It is never read by Guard, staleness, sharing, or Teams Check, and the review UI labels it "Possible files … NOT anchored on approval". Plain approval expires this guess; it becomes a real anchor only when the reviewer explicitly selects it through `approve_decision(source_files=[...])`. Evidence reconciliation uses a separate provenance marker for structurally confirmed candidates, which plain approval may promote and pending sharing may preserve as proposed Team scope.

Anchor truncation (a decision governing more files than the cap allows) is recorded explicitly rather than silently dropped, so the developer can see and correct a partial anchor. Anchors can optionally be included when a decision is pushed to the optional remote team service, subject to the same length/count bounds enforced on capture.

## Design constraints

- **Silent operation is essential.** Tools must not produce noise - `update_context` silently discards filtered (non-novel) content without logging. This governs *capture and filtering* noise specifically; it does not forbid every user-facing message. Two deliberate exceptions reach the DEVELOPER: a short structured note naming what the rationale hook fetched (so retrieval is observable, not spooky), and the new-release notice. A third deliberate non-silent behaviour reaches the MODEL rather than the developer: the capture-quality bounce, a corrective ack returned through the MCP tool result telling the calling model to restate a narrative-shaped capture in the same turn - silently discarding it would lose the decision instead of fixing its shape.

  The new-release notice is bounded by TWO rules, not one: a given release is announced at most once, AND no two routine notices land within `updates.MIN_NOTICE_INTERVAL` (24 hours). "Once per release" is only a budget while releases are occasional, and this project has shipped bursts of two in a day, so the time floor is what stops a burst of releases becoming a burst of notices. The constant carries the measurement and the conditions for re-tuning it. Inside a session the notice yields to any other Contexer line in the same turn, which is what the single `systemMessage` slot enforces. The CLI backstop is a different surface and makes no such claim: it prints after whatever the command itself said, on stderr, and is suppressed only where the command already covers the same ground (`status`, `upgrade`, and a guard run that printed anything). `CONTEXER_NO_UPDATE_CHECK` silences all of it.
- **Secrets never egress; capture stays faithful.** Redaction happens only where a decision leaves the machine (the wire call and the share preview), never on local capture - the local store is meant to be a verbatim record, and silently rewriting captured content would corrupt that. Redaction is default-on, deterministic, idempotent, and fail-soft toward staying on. Do not add an outbound path that bypasses the existing redaction chokepoint.
- **No abstraction beyond what exists.** The module structure (`server.py` / `store.py` / `cli.py` / `adapters/`) is intentional. Do not add classes, config files, or layers unless the spec changes. Adding support for a new AI-assistant target is the one case that genuinely fits in a single new file, because the adapter registry is the only seam it needs - it is not a rule that every change must land in one file. A behaviour that is inherently cross-cutting touches every module that owns a piece of it; the test is ownership, not file count. Adding a *layer* - an interface with one implementation, a config file for a value that never changes, a factory for one product - is what this constraint forbids.
- **`update_context` is called by Claude Code, not the developer.** Claude Code nominates content; the server filters. The filtering criterion is novelty - substantial token overlap with any existing decision is rejected as a duplicate, not an LLM call.
- **Git hooks and CLI commits are out of scope for decision capture.** The commit-time guard reads and checks already-stored, already-approved decisions; it never creates one. Decision nomination comes from MCP calls or from host-hook evidence reconciled into human review, never from commit enforcement.
- **Never claim complete decision capture.** Coverage is best-effort and host-specific. The guarantee is narrower: acknowledged evidence is held, summarized onto a decision, or counted as a gap, and inferred or inactive knowledge cannot become trusted, injected, anchored, or armed without the required human action.
- **Thin semantic MCP tools, rich deterministic internals.** The model-facing MCP surface stays small and centered on decisions, review, retrieval, and sharing - not internal storage/sync mechanics. A new tool proposal must answer two questions before it's added: why must the model choose this action directly (versus an existing tool's parameter, or something adapters/local Python already handle), and what invariant stays enforced in deterministic code regardless of what the model passes? Prefer higher-level arguments that reflect user intent over internal storage operations, ids, or enum spellings. See contexer-ai/contexer-teams#178 for the matching decision on the Teams client side, so server/client surface boundaries evolve together.
