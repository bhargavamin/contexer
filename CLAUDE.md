# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Install dependencies
uv sync

# Run the server (stdio transport — for manual testing)
uv run python server.py

# Smoke-test the server responds to MCP initialize
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"test","version":"0"}}}' | uv run python server.py

# Test the commit-time guard against currently staged changes (see Commit-time guard below)
uv run contexer guard --explain

# Preview the assisted anchor backfill (read-only; see Anchor accrual below)
uv run contexer guard anchors --list
```

## Architecture

A small package (`contexer/`), intentionally minimal:

- **`contexer/server.py`** — MCP server entry point. Defines tools (`capture_user_constraint`, `update_context`, `approve_decision`, `resolve_conflict`, `review_pending`, `get_context`, `get_context_for_prompt`, `bootstrap_context`, `list_shareable`, `share_decision`, `update_global_context`, `get_global_context`) using `FastMCP`. Generates a `SESSION_ID` (UUID) at process start shared across all tool calls in a session. Delegates all logic to `store.py`. **Pending-review UX is non-blocking:** `update_context` capturing an AI-inferred constraint / L3 architecture decision returns a *"pending review — not yet trusted, does not block your work"* notice (never a "wait for the developer" prompt); the identified list with content is pulled on demand via `review_pending` (the in-session twin of `contexer review`), and SessionStart injects only a **count** (not per-decision content) to keep startup light. **`share_decision` is confirmed-by-default:** an outward push previews what would leave the machine (`confirm=false`, a pure local read, only when a team endpoint is configured) and requires `confirm=true` to send; a developer can opt out with `skip_confirm = true` in `config.toml`. When the developer hasn't named a decision, `list_shareable` returns an identified list to pick from, and `share_decision` accepts a comma-separated **multi-select** (`"id1,id2"`) so a whole selection previews + pushes in one call. The CLI mirror is `contexer share` with no args → a numbered interactive multi-select picker.
- **`contexer/store.py`** — All read/write and filtering logic. `_passes_filter` is the core gate: content is stored only if it is novel (token-overlap check — >70% overlap with existing decisions = duplicate). In front of it, at the two server write tools only (`update_context`/`update_global_context`), sits **`capture_lint`**: a long (>400 chars) ai/plan-sourced capture whose first sentence reads as investigation narrative ("Investigated…", "Bug fix…", a date stamp) or runs 45+ words without stating a decision is BOUNCED with same-turn restate instructions instead of stored — a deliberate, model-facing exception to silent filtering (same in-band-ack precedent as `constraint_ack`), because a silent discard would lose the capture the lint exists to reshape. Human/scan/bootstrap/memory sources, `replace_id` corrections, and short content never bounce. **A second bounce, same gate, different defect: the multi-claim split (`_LINT_SPLIT_BOUNCE`).** A capture carrying ≥`_LINT_MIN_SECTIONS`=3 distinct ALL-CAPS section labels is a DOCUMENT, not a decision — independent claims sharing one record, which then ages at the rate of its fastest-rotting part: one anchored file changes and the whole entry renders "may be stale", tarring the durable subsystem understanding inside it by association with the implementation detail beside it. The bounce says SPLIT (one `update_context` per claim), not restate — a model handed the narrative bounce here would fix the wrong thing. What counts as a label is measured, not guessed, against the 193 real long captures across every store on one machine: a run of ≥2 whitespace-separated tokens of which ≥2 are **digit-free** ALL-CAPS words, followed **directly** by a `:` (an intervening parenthetical allowed), counted only **outside code and URLs**, and counted **distinctly**. Every qualifier was earned by a false positive rather than reasoned into existence — digit-free drops ticket noise (`PRT-54 Q5`, `FE SA-108/109`) that otherwise scored as high as a real header; blanking code (fenced blocks **including an unterminated one** — a routine LLM output shape a close-fence-only pattern let leak its contents straight back to the scanner — plus inline spans) with the `:` rule eliminates the SQL class outright (`UUID PRIMARY KEY` / `TEXT NOT NULL` / `ORDER BY` / `ON CONFLICT … DO UPDATE` scored **7** labels on one schema-quoting decision without it, **0** with it); blanking URLs stops "the HTTP API docs live at `https://…`" reading as a label off the scheme's own colon; requiring the `:` to follow **directly** (bare parenthetical allowed, because real headers look like `KNOWN GAP (pre-existing, untouched):`) stops a comma-joined header being double-counted — `WHY CHECKOUT, NOT THE PORTAL:` scored 2, which inflated the very corpus the threshold was set against; distinct counting stops a thrice-repeated `DO NOT:` reading as three sections. Measured with all of it applied, the corpus is 183 captures at 0 labels, 7 at 1, and one each at 2, 3 and 4 — `_LINT_MIN_SECTIONS`=3 catches exactly the 3 and the 4, both genuine multi-section documents, one of them the record this gate was built from. **That is a one-count margin, not a wide gap**, stated plainly because the earlier looser matcher made the gap look bigger than it was. Known residual shape, accepted rather than tuned away on a single example: a one-claim decision that uses three `LABEL:` constructs of its own (`the API GATEWAY: … the DB LAYER: … the CI PIPELINE: …`) does bounce; every tightening that would exclude it (three-word runs, sentence-initial position) also drops the real headers the gate exists to catch. Same narrow scope as the narrative bounce: ai/plan only, >400 chars, no `replace_id`. **Refused corrections ack in band (#202):** an entry has ONE `proposed_revision` slot, trust-ordered by `_claim_proposal_slot` (`_PROPOSAL_TRUST` = human > plan > ai > scan, #200) — when a `replace_id` correction's source is strictly outranked by the sitting proposal, the slot keeps the higher-trust version and the caller still returns success (failing toward review of the better proposal), so the refusal is reported through `update_decision_with_meta`'s `meta["refusal_ack"]` (the 3-tuple variant `update_decision` wraps, house pattern: `get_context_for_prompt_with_meta`) and `update_context` returns that ack instead of the pending-approval prompt: the model is told its correction was refused, not queued, must not retry, and must surface BOTH versions to the developer that turn. Same in-band-ack precedent as `capture_lint`/`constraint_ack`. **Human review surfaces clip:** `format_pending_review` and `format_shareable_list` render bodies through `_clip_body` (400 chars, word boundary, `… [+N chars]`, one footer line pointing at the full text when anything clipped); model-facing renders (`get_context`, `_render_prompt_decisions`, session-start payloads), the CLI edit path, and the wire-accurate `format_share_preview` stay full. **`contexer review` renders bodies IN FULL too** (`cli._print_wrapped`), deliberately: it is the one-decision-at-a-time surface whose entire purpose is judging an approval without running a second command — it previously clipped at 400 chars with no footer saying so, so the only way to read a long decision was to enter `[E]` edit mode and submit empty. Alongside the body it renders the metadata that makes an approval accurate (`cli._review_metadata`): capture time + origin (`created_by`, humanised via `_ORIGIN_LABELS`), corroboration (`occurrence_count`/`session_ids`, shown only when >1), `source_files` plus a `_staleness_note` warning when that code moved since capture, `anchor_candidates` as `Would anchor`, the anchor commit via `store.review_anchor_note`, and a warning when `repo_source == "pointer"` — the one resolution branch that can silently target the WRONG repo. `review_anchor_note` reads the PR number off the anchor commit's own SUBJECT (`(#211)` / `Merge pull request #211`); no PR number is stored in the schema, so this costs one `git log -1` and works retroactively. Both git lookups are fail-soft — a hiccup drops a row, never the review — and both route through `cli._budgeted`, a per-run memo + **time** budget (`_REVIEW_GIT_BUDGET` = 3s, built once per invocation by `_review_git_budget`). Deliberately a time budget, not the call-count cap the batch renders use (`_STALENESS_MAX_CHECKS` = 3): that cap protects a prompt's critical path where the developer is blocked and never asked for the work, whereas here they explicitly ran `contexer review`, so a 3-call cap would blank the accuracy rows from the 4th decision onward even on a warm repo where each call costs ~10ms. Memoising is what actually pays: a review queue is normally decisions captured in one session, which share an `anchor_commit`, so the whole queue collapses to one lookup. On exhaustion the row SAYS `(git is slow — anchor/staleness checks skipped this run)` rather than rendering bare and reading as "nothing to report" — the same honest-on-exhaustion rule `anchors.py` enforces with `_BudgetExceeded`. `[Q]` quits the loop leaving the remainder pending. **Legacy stamping:** `_migrate_decision` stamps missing `status`→`approved` / `created_by`→`ai` on pre-provenance entries (schema v4; behavior-neutral — readers already default through `_entry_status`). **Scan-convention re-verification:** `verify_scan_conventions` runs at non-resume/compact session start (24h TTL stamp written before scanning; fast-path exit before any mining when the store has no scan-sourced stats-bearing participants): a still-measured rule refreshes its evidence sentence in place (including fuzzy wording-drift matches against stat-bearing fresh sentences only), a disappeared rule attaches a rule-shaped withdrawal `proposed_revision` ("… (evidence withdrawn on re-scan: …)") through the normal review flow, a reappearing rule retracts its stale scan-sourced proposal, an empty fresh scan flags nothing (silence over noise), and the session-start payload re-reads the store when verification reports a change so the new session renders verified state. Storage is capped at `MAX_ENTRIES = 500` per repo. Display is separately capped: `_UNFILTERED_DISPLAY = 10` for overview calls, `_FILTERED_DISPLAY = 25` for query/type-filtered calls. Bootstrap is insight-aware: `_detect_insight(repo_path)` infers the user's familiarity (`high`/`medium`/`low` + decisive flag) from git signals — commit authorship by `user.email`, first-commit authorship, fresh-clone reflog entries. Detection order is load-bearing: the empty-email check must run before any `--author` query (an empty author pattern matches every commit). Detection is TTL-cached by `_cached_insight` (24h, `~/.contexer/.insight_<slug>`, fail-soft), validated on read against the current `user.email` + `HEAD` — a cache hit costs 2 git subprocesses instead of ~6, and a changed identity or re-cloned/rewound repo invalidates immediately rather than after the TTL; `_detect_insight` stays pure for tests. `bootstrap_scan(repo_path, insight, mined=None)` filters gap questions by each gap's `min_insight` AND suppresses questions the miner already measured (tests-in-scope, CI, team conventions when ≥3 conventions mined); empty `insight` auto-detects. **`bootstrap_apply(repo_path, session_id, insight)` is the self-storing bootstrap** (what the `bootstrap_context` tool runs by default, `apply=True`): scan + `miner.mine_conventions` + persist under one store lock with one save — exactly ONE consolidated `"Stack: ..."` architecture entry (never ~15 per-fact entries), each mined convention as its own decision tier-gated by evidence (≥90% dominance → born `approved` via `created_by="scan"`; 60–89% → `pending_approval` — deliberately NOT `suggested`, which would inject at session start and never surface in `review_pending` — arming the `.pending_review` nudge). Idempotent: skip-don't-bump `_find_match` dedup, so re-calls store 0 and never touch `occurrence_count`. The model's only remaining bootstrap jobs are reporting the returned `stored`/`pending` counts and asking the residual author-only gap questions. Non-decisive detection makes the offer ask the user directly. **The offer is a numbered menu of at most FOUR options in every variant**, and the injected block tells the model to render it as one interactive multiple-choice question where the host has that tool (Claude Code: `AskUserQuestion`), else as the numbered text list — a number and its own row's keyword mean the same thing, but **which** keyword sits at a given number is variant-dependent (`2` is `full` in the high/ambiguous menus and `quick` in the low one), so never hardcode a number→mode map. Four is the picker's option cap (plus its own free-text "Other"), which is why `some` has no row in the ambiguous variant: it stays a documented typed reply mapping to `insight='medium'`, and `scan` absorbs its "didn't build it" meaning — **so in the ambiguous variant `scan` routes to `insight='medium'`, not `'low'`**: `'low'` returns only the goal gap, silently dropping the purpose question (`min_insight='medium'`) for the one user class `some` existed to serve; the low-decisive variant, where the evidence says no commits, still routes `scan → 'low'`. For the same reason the affirmative is variant-relative: a bare "yes" means **option 1 of the variant on screen** (`quick` in high, `scan` in low), never a fixed keyword, since a blanket `yes → quick` would start the author interview precisely where the evidence says the user cannot answer — and in the **ambiguous** variant it resolves to nothing at all, because that question is "how well do you know this repo?" whose option 1 asserts authorship a bare "yes" never claims; there the model must ask which option instead of inferring. The offer rows are also emitted **unquoted**: the block used to be wrapped in script quotes, invisible in verbatim text mode but rendered into the picker's own labels (`not now"`). Gap questions are asked the same way, but that ask shape lives in **`store.GAP_ASK_GUIDE`**, attached by `server.bootstrap_context` as a `how_to_ask` field **only when the result carries gaps** — never inlined into `_build_bootstrap_context`, which is injected at every context-less session start, again at the first `UserPromptSubmit`, and post-compact, including the skip and STEP 0 paths where no gap is ever asked (~470 tokens per injection, ×2-3 per first turn). `/bootstrap` and the docs point at that field instead of restating it, so the rule cannot drift across copies — it had already drifted in `bootstrap_command.md` within one commit. The shape itself: ONE question at a time, never batched (batching would skip the between-answer re-evaluation that drops tests/CI/deploy gaps for a docs-only repo); last option = "Skip this one"; a "Correct" option (description = the gap's `assumption`) ONLY when that assumption actually answers the gap's question — **and `assumption` is an OPTIONAL key, omitted (never `""`) when no repo signal predicts the answer**, so no assumption means no Correct option and the question is asked openly. The goal gap is the one such gap: it asks what the USER intends to do here, which nothing in the repo forecasts. It used to carry `_infer_purpose(...)` — the repo's purpose, answering a different question — and the guide spent a paragraph teaching the model to discard it; deleting the field deleted the workaround, and an empty string was rejected as worse than absent because it renders as a blank Correct option. `_gap`'s signature moved `assumption` last with a default; every call site was already keyword-only (verified, zero positional). Up to two candidate options in between ONLY when the `hint` names distinct candidate answers (half the hints are one comma-list belonging to a single answer, or a restatement of the question); and the stored sentence must ANSWER THE QUESTION, never echo the assumption's wording. **Rule docs are EVIDENCE FOR A QUESTION, never a decision.** `GAP_ASK_GUIDE` opens by telling the model to read the files named in the result's `existing_context_files` before asking anything, and to convert a gap those files already answer into confirm-or-correct (quote the line, ask the developer) — storing the *confirmed answer*, never the quote, so provenance stays `human` and no unratified prose reaches the store. This is the safe direction of the import idea rejected in #19e5a6cb: docs → better question → human answer → store, never docs → store. Two disciplines make it survivable: rule docs may only reshape or drop existing gaps, **never add** one (a thirty-line rules file would otherwise become a thirty-question interview), and a rule doc contradicting a *measured* convention in the same result (a doc demanding full type hints beside a mined "61% of 556 functions") becomes the highest-value question in the interview, since both sides are evidence and only the developer can settle it. **Exactly ONE addition is carved out**, because the two rules collided in the first cut: a doc contradicting a sentence in the result's `measured_conventions` earns its own question even though it is not one of the returned `gaps` — the answer is stored as a `convention` that SAYS it supersedes the measurement, so the developer can retire the stale one from `contexer review` instead of both standing as equals. That check is only executable because `bootstrap_scan` now RETURNS `measured_conventions`: `bootstrap_apply` already mined them for gap suppression and then discarded them, so an earlier draft told the model to compare against measurements that were nowhere in the payload. The enumeration is the whole mechanism — the model can read only what the scan names — so `bootstrap_scan` also lists `AGENTS.md`, `CONTRIBUTING.md`, `GEMINI.md`, `.github/copilot-instructions.md` and `.claude/rules/*.md` (capped at `_MAX_RULE_DOCS`=5, with an explicit `(showing 5 of N)` row rather than a silent truncation), all previously invisible to bootstrap. **The model is pointed at `context_docs`, NOT `existing_context_files`:** the latter is every file the scan touched — `uv.lock`, `.github/workflows/`, and literal glob strings like `.eslintrc*` that are not readable paths at all — so aiming a "read these" instruction at it buys failed reads and wasted tokens. **A generated doc is skipped by its own BANNER** (`_is_generated_doc`: a marker — `auto-generated`/`autogenerated`/`@generated`/`do not edit` — on a SHORT line, ≤`_GENERATED_BANNER_CHARS`=80 chars once comment leaders are stripped, within the first `_GENERATED_BANNER_LINES`=5 lines; fail-soft toward *keeping* the file). The shape test is the whole point, and matching the marker anywhere in the header was wrong (caught in review on #220): a human rules file *discussing* generated code uses the same words — "the files under `src/proto` are auto-generated; do not edit them manually" — so a header-wide substring match silently dropped exactly the "never hand-edit the protos" rule that most deserves a confirm-or-correct question. The two failure modes are not symmetric, which is what sets the direction: enumerating a generated doc costs one skipped read, while excluding a human-authored one loses evidence with no signal. Residual and accepted: a rules file whose opening lines hold a short standalone sentence like "Protos are auto-generated." still reads as generated — separating a banner from a terse rule beyond that needs meaning, not shape: an earlier Contexer version wrote its own auto-generated mirror into `.claude/rules/` (36KB and months stale on this very repo until it was deleted; nothing in the current source regenerates it, but an install of that vintage still leaves one behind), and enumerating it would have the model quote Contexer's own output back to the developer to "confirm" — a decision round-tripping in as if human-authored, the exact loop this design exists to prevent. Enumeration and keyword-scanning are one table (`_CONTEXT_DOC_FILES`, second element = scan budget in chars, `0` = enumerate-only) so the invariant lives in data rather than in a comment beside a second loop. The four scanned entries (README/CLAUDE.md/.cursorrules/.windsurfrules) are **grandfathered, not endorsed** — a `CLAUDE.md` opening "For example, run `make deploy`" trips the same unanchored substring test and silently suppresses the tests/CI/deploy/exclusions gaps; narrowing `_SIMPLE_REPO_SIGNALS` is a separate behaviour-changing decision, deliberately not folded in here. **`readme_summary` was deleted outright**: the README's first non-heading line is as often markup as a tagline — on contexer's own README it evaluated to `'<p align="center">'`, which shipped as the purpose the developer was asked to confirm — and a length filter cannot rescue it (badge lines run 60–70 chars). **`_infer_purpose(name)` returns `""` rather than a placeholder**, and matches NAME TOKENS rather than substrings; both were fixed on review, and both were caused by deleting the README fallback that used to mask them. A truthy non-answer ("Purpose not yet documented", `'"x" — type not obvious from name alone'`) survives `_gap`'s omit-when-empty rule and renders as the "Correct" option for "What does this repo do?", so clicking it stored a non-answer as the ratified purpose; and `"api" in "rapid-sync"` is true (r-**api**d), so a sync tool was labelled a backend API, `webhook-processor` a frontend. With no README second opinion left, either mistake now reaches the developer unchallenged. What survives at the read sites is only the `_SIMPLE_REPO_SIGNALS` keyword scan; the `docs/*.md` three-file cap still needs its deterministic sort, since **which** three still decides `is_simple_repo` — what changed is that no ordering heuristic can improve the sample, because nothing is extracted from those files any more. No host plumbing: the capability line is host-neutral text in `_build_bootstrap_context`, so a host without the tool simply falls through to the text list and a new adapter inherits both for free. **The offer fires at most once per session per repo**, gated by `~/.contexer/.bootstrap_offered_<slug>` (`_arm_offer` / `_offer_already_made`): skipping stores no decision, so the `if decisions` guard never trips and every later prompt — plus every `/compact` — used to rebuild the block and re-open the picker the developer had just dismissed, one modal per prompt. A non-resume, non-`compact` session start clears the flag (a genuinely new session offers again); `compact` deliberately does not, since it continues the session in which the developer already answered. The STEP 0 newcomer-answer path is NOT gated — it shows no menu, and gating it would swallow the answer. Fail-soft (a flag error degrades to the old always-offer behaviour) and swept by `_gc_stale_session_files` for repos never reopened. Known limitation: commit count is repo-wide, so a few commits in one corner of a monorepo read as insight into the whole repo. **Retrieval V1 (topic router).** `get_context_for_prompt(repo_path, prompt, session_id="")` (called by `claude.rationale` — Codex reuses it verbatim — and Gemini's `before_agent`) is BM25-backed by a disposable index sidecar (`STORE_DIR/.retrieval_index_<slug>.json`, indexing every non-`ignored` decision — `approved`/`suggested`/`pending_approval` — since `pending_approval` entries ARE retrievable (`get_context` renders them with a `[pending]` tag) and the index must surface exactly what `get_context` can hand back; only `ignored` is excluded, permanently, so a stale index can never advertise a topic `get_context` would refuse to return) written ONLY at the tail of `_save` (every writer already holds the store lock, so no extra locking) and read-only per prompt via `_read_retrieval_index` — a missing/corrupt/wrong-version index falls back verbatim to the pre-V1 keyword lookup (`_legacy_prompt_context`), never rebuilt inline. **Session-start self-heal (`ensure_retrieval_index`).** The per-prompt reader stays strictly read-only, but "the repo's next `_save` rebuilds it" is only an adequate self-heal for a repo somebody is still writing to: an index *version* bump (v1→v2 at #187 fix round 1) rejects every already-indexed repo at once and silently demotes it to `_legacy_prompt_context`, whose keyword pick is `sorted(set(keywords), key=len, reverse=True)[:3]` — literally the three LONGEST words of the prompt, so a long prose word ("verification", "deliberately") outranks the short domain identifier that matters ("Clerk", "orgId"), and a repo nobody captures into never recovers at all. So `_local_session_start_payload` calls `ensure_retrieval_index(repo_path)` once per session start, positioned BEFORE the `resume` early-return and unconditional on `source` (a resumed/compacted session injects nothing there, but its later prompts still route through BM25). It rebuilds only when `_read_retrieval_index` returns None AND the store holds an indexable entry (the identical `decision`-minus-`ignored` filter `_build_retrieval_index` participates on — matching it exactly is what stops an all-ignored store from writing the zero-doc sidecar the guard exists to avoid; an empty sidecar buys nothing the legacy path doesn't already answer with the same silence). **Both bail-outs are tested UNLOCKED first and re-tested under the lock**, which is taken only around the write: `_store_lock` is `flock(LOCK_EX)` with no timeout and the other session-start passes hold that same per-store lock across genuinely long work (`verify_scan_conventions` across a whole-repo mine, `anchors.verify_anchors` across up to `_ANCHOR_GIT_BUDGET` git subprocesses, `bootstrap_apply` across another mine), so locking *before* the bail-outs would make a second session on the repo — and, on `resume`/`compact`, a session start that previously took no store lock at all — queue behind that work on every start, forever for a repo that can never satisfy the condition. The unlocked pass is therefore pure contention avoidance; the locked re-check stays the authority (and is what stops two sessions both rebuilding). The result is verified by reading it back rather than assuming the fail-soft `_write_retrieval_index` succeeded, then an `index_rebuild` event goes to the retrieval log — log-only, never user-facing, so silent operation holds. Fail-soft end to end **including that log write** (it sits inside the guard, not after it): the call site is deliberately unguarded on the strength of this promise and `get_session_start_context` is invoked by the SessionStart hook with no try/except of its own, so one escaping exception would cost the session its entire context injection over a bookkeeping file — which is also why `_retrieval_log`'s own guard was widened from `OSError` to include `UnicodeDecodeError` (a `ValueError`, so an `OSError`-only guard let a non-UTF-8 log file escape). Any failure leaves the sidecar untouched and the router on legacy, exactly as before. Consequence worth knowing: the standing topic map is index-backed, so a repo whose sidecar was missing now renders the map from the healed index at that same session start (`TestStandingTopicMap::test_map_returns_after_session_start_heals_a_missing_index`). Ranking (`_bm25_rank`, k1=1.5 b=0.75) tokenizes the query with `_index_tokens` — the same tokenizer the index itself uses — and expands any query term absent from the corpus to every indexed token sharing it as a prefix (restoring legacy `\b`-prefix recall: `postgres` still matches a doc holding only `postgresql`); that plus `_derive_topics` (a fixed alias table: db/api/auth/frontend/deploy/testing/config/perf/security) and `_extract_artifacts` (file paths, dotted modules, `*Error`/`*Exception`, route-shaped strings — double-weighted in the query) drive an injection ladder: STRONG matches (relative threshold, capped at 3) render full decision content under `[Contexer: auto-fetched for this question]`; else WEAK topic overlap returns a short pointer (`[Contexer] Related stored decisions: ...`) and logs a `pointer` event; else — for rationale/project prompts only — an overview fallback (`get_context()`, no query) and then a global-store lookup; anything else (a topic-word-only or artifact-only task prompt with no strong or weak hit) stays silent by design, matching the pinned `test_benchmark.py` misses. **The BM25 gate also opens for question-shaped prompts** (`_QUESTION_LEADS`: the prompt's FIRST token is what/how/where/which/when/who — deliberately not a trailing `?` and deliberately not can/does/is, since "can you add X?" is a task request), so a comprehension question carrying no rationale word ("what does the miner do?") reaches the ranker instead of being dropped at the gate. A *question-only* prompt (question lead, no rationale/project word) must additionally clear a **discriminative-term guard** to earn a STRONG injection: `_bm25_rank` returns a 4th element counting the doc's hits on query terms that are RARE in this corpus (`df <= max(2, n_docs // 20)`), and the top-ranked doc must have ≥1 — otherwise "what time is the standup?" would inject the p99-latency constraint on the word "time". The single-hit relaxation extends to question-only prompts only when the query has exactly ONE term (one lone hit out of several terms is noise, not an answer); the WEAK topic pointer is allowed as usual; the overview/global fallbacks stay restricted to rationale/project prompts; and the no-index legacy path is untouched — question-only prompts stay silent there, since the legacy keyword lookup has no scoring guard to make widening safe. **File route (issue #187).** A prompt naming a path/module-shaped file (`contexer/guard_engine.py`, `contexer.store` — never a bare word or symbol artifact; the identical `_pathlike_artifact` class the commit-time guard applies to DECISION content, reused via `guard_engine._guard_content_artifacts` on the PROMPT instead, never a second matcher) is looked up deterministically through the same anchor/content-artifact matching `guard_engine.decisions_for_files` uses (`_prompt_file_hits`) BEFORE BM25 runs. **Tiered by signal strength (fix round 1 — the ratified risk-asymmetry principle: a wrong STRONG injection plants false context as if human-approved, a wrong pointer costs one line):** a `source_files` match (`anchor_ids` — a human explicitly linked the file, via `contexer guard anchors`, an approval-time link, or a `source_files=` capture) LEADS the STRONG set (still capped at 3, still working-set-deduped via the same `ws` filter BM25 uses) with BM25 filling any remaining slots, deduped against the anchor hits; a content-artifact-only match (`mention_hits` — the file's name merely appears in a decision's prose) is capped at the WEAK pointer lane instead — one line naming the matched decisions' titles (`get_context(files=[...])` as the suggested follow-up), never full content, and reached only when nothing above already returned (an anchor hit or the pre-existing topic-overlap pointer both take priority, so a mention is never duplicated alongside either). Mention-tier pointers are deliberately NOT working-set-deduped (same precedent as the topic-overlap pointer — cheap and repeatable, unlike a STRONG injection). This tiering governs only what the FILE SIGNAL contributes; it does not reach into BM25's own, separately-already-shipped artifact-double-weighting mechanism (predates #187), so a mention-tier decision that also has genuine independent term overlap can still earn BM25 STRONG on its own merits — pinned by `TestIndexDominatesLegacy`. So a task-shaped prompt that names only an anchored file ("fix the pairing bug in contexer/guard_engine.py" — no rationale/project word, no question lead) injects the decisions that govern it with no voluntary `get_context(files=...)` call, closing the #172/#174 arc (files referenced on decisions → decisions found from files → found without anyone having to ask). The gate itself does not widen: a real path artifact already makes `_extract_artifacts`'s `artifacts` non-empty, which is what opens the ladder today, so the file route only refines what happens INSIDE an already-open gate — a bare topic word or a file nothing references stays exactly as silent as before (pinned: `please rename utils.py for me` stays silent both because "utils.py" governs nothing AND because the gate is unchanged). **Serving path (fix round 1's latency contract — shipped unconditionally per developer ruling, not gated on a runtime measurement):** the repo-scope half is served from the retrieval index sidecar's own per-doc `source_files`/`path_artifacts`/`title` fields (`_build_retrieval_index`, bumped to index schema `v=2` so a pre-#187 `v=1` index is rejected outright rather than half-served against docs missing those fields — self-heals on the repo's next `_save`, or at the next session start via `ensure_retrieval_index` above) via `_index_file_lookup` — dict/set operations against the already-loaded index, no per-prompt content re-scan; measured ~0.91ms p50 / ~0.93ms p95 at 500 synthetic decisions, vs. ~7.7ms p50 / ~8.6ms p95 for the live `decisions_for_files` scan it replaces (~8x faster, well under the ~5ms per-prompt budget the live scan breaches at that scale — see `_index_file_lookup`'s docstring and `TestFileRoute::test_index_lookup_meets_latency_budget`). The global-store half stays a small LIVE scan (`decisions_for_files` restricted to the loaded global entries) even on the fast path, mirroring how the global store is always a separate, smaller-scale fallback everywhere else in this router. A missing/corrupt/wrong-version index falls back to the full live `decisions_for_files` scan over both stores — the established fallback pattern (never rebuild the index inline to serve one prompt) — exactly as before this fast path existed. `get_context` itself retries a literal-miss query that names a bare topic (e.g. `query='db'`, exactly what a pointer suggests calling) against that topic's alias tokens, so the suggested follow-up actually returns the aliased decisions instead of nothing. A per-session working set (`working_set_ids`, `.ws_<slug>_<sid>.json`) skips re-injecting a decision already surfaced this session. `_local_session_start_payload` (via `session_start_payload`, which now takes an optional `session_id` threaded from the SessionStart hook's stdin) appends a size-gated standing topic map (`Stored decisions by topic: ...`) once a repo holds ≥20 decisions, and on a `compact` source with a session id re-injects the CONTENT of the session's most-recently-injected working-set decisions (capped at 10, active statuses only) under a `## Rehydrated working context` heading — the pre-compaction router state would otherwise be lost on replay. Compact-reload parity holds across all three hosts: Claude re-injects via `SessionStart(source="compact")`, Gemini's `before_agent` post-compression reload and Codex's post-compact entrypoint (`get_post_compact_context`) both thread the same `session_id` into `post_compact_payload`, which calls the identical `_rehydrate_working_set` helper — no host loses pre-compaction router state on replay. Every non-resume session start also runs a fail-soft GC sweep dropping working-set/log files older than 7 days. The retrieval log (`.retrieval_<slug>.jsonl`, tail-capped at 200 lines) records `pointer` events and, from the `get_context` MCP tool, a `followup` event when a query matches a still-fresh pointer's topic — a log-only usage signal, never a behavior change. **Staleness anchoring.** `_anchor_sources` stamps a decision with `source_files` (the repo-relative files it describes, capped at `_MAX_SOURCE_FILES`=10) plus `anchor_commit` (current HEAD) at entry creation, and a `replace_id` correction that passes non-empty `source_files` re-anchors the same way (clearing any stale flag); recurrences and containment routes never anchor. `_staleness_note` runs a one-dot `git diff --name-only <anchor> -- <files>` (working-tree aware, so an uncommitted edit is caught, not just a committed one) ONLY at the two render sites that show decision content — `get_context` and `_render_prompt_decisions` — never in `session_start_payload`; `_staleness_notes` budgets ≤3 git checks per render call (anchored entries past that budget render without a note) at a 2s timeout each and is fail-soft throughout (measured ~22ms per call). Re-capturing with `replace_id` + `source_files` is how a stale note gets cleared. **Decisions-for-files retrieval (Task 1 of #174).** `get_context(repo_path, files=[...])` returns only the decisions that GOVERN the given files — via `guard_engine.decisions_for_files`, which both the repo store and the global store participate in — each rendered with its real `[scope=personal]`/`[scope=global]` tag instead of the usual hardcoded personal tag; it combines with `entry_type` as an intersection and narrows further by `query`, files threaded in ahead of both. **Anchor lifecycle verification (Task 2 of #174)** — rename re-anchoring and review-gated retirement proposals for anchors whose files are truly gone — lives entirely in `contexer/anchors.py`; `store.py` carries only the session-start call site (`anchors.verify_anchors`, wired in immediately after `verify_scan_conventions`, same TTL-stamp/fast-path/re-read-on-change shape). See that module's own bullet for the rename-first, `clear_anchors` exit-participation, and honest-on-exhaustion details. **Conflict rendering (#193)** — labeled dual injection of a standing decision plus its unreviewed update, and the `resolve_conflict` resolution memos — lives entirely in `contexer/conflicts.py`; `store.py` carries only the call sites (the four render loops, `format_pending_review`'s memo lines, the two `conflict_memo` lifecycle pops in `_promote_proposal`/`_apply_approval`, and the proposal-content one-liners in `_matches_query`/`_build_retrieval_index` that keep a decision findable by the update's own terms). See that module's own bullet.
- **`contexer/guard_engine.py`** — the commit-time guard engine (staged-file plumbing, Tier-1 advisory pairing, Tier-2 armed blocking rules), extracted out of `store.py`. `store.py` stays the public facade: it re-exports the five public entrypoints (`guard_staged`, `guard_candidates`, `arm_guard`, `disarm_guard`, `dismiss_guard`) *lazily*, via a PEP 562 module `__getattr__` at the bottom of its file, not an eager `from contexer.guard_engine import ...` — `guard_engine.py` imports `store` at its own top (the module object, not `from`-imports, so store-owned values tests monkeypatch on `contexer.store` are still seen here at call time) for the store-owned helpers it needs (`STORE_DIR`, `_load`, `_save`, ...), so an eager import in `store.py` would make `store.py`'s own load depend on `guard_engine`, which depends on `store.py` having already finished loading — a cycle that only resolves if `store.py` happens to be the module that starts loading first. Resolving lazily means `store.py` finishes loading without ever needing `guard_engine`, so `guard_engine.py`'s own `from contexer import store` is safe in any import order, including `import contexer.guard_engine` as the very first touch of the package. Approval-time anchoring (`approve_decision`, `_apply_approval`, `_anchor_sources`) is approval machinery, not guard engine, and stays in `store.py`. **`decisions_for_files(repo_path, files, decisions=None)`** (Task 1 of #174) is the retrieval surface built on the same Tier-1 pairing signals (`source_files` membership, path-like content artifacts extracted from a decision's content) but is pure retrieval, not advisory noise control: no guard-trust filter (a `pending_approval`/`suggested` decision can still govern a file — the caller decides what to do with its status) and no throttle/dismissal state, since nothing here is ever surfaced repeatedly at commit time. Every non-`ignored` entry of both the repo and global store participates; `files_matched` on each hit lists, in the caller's input order, which queried files matched that decision (the reverse-tracing property), and `reason` is the single strongest signal across those files (`source_files match` beats any artifact reason). This is what `store.get_context(files=...)` calls to answer "which decisions govern this file."
- **`contexer/anchors.py`** — anchor lifecycle verification (Task 2 of #174), extracted out of `store.py` (user directive: don't crowd store.py with a second verification family) so `store.py` carries only the session-start call site (`anchors.verify_anchors`, wired in immediately after `verify_scan_conventions`, same re-read-on-change convention: a rename correction or a fresh retirement proposal makes the session re-`_load` so it renders the verified state). `verify_anchors(repo_path, force=False)` re-checks every anchored, active-status (`approved`/`suggested`) decision's `source_files` against the working tree, gated by a 24h TTL stamp (`.anchor_verify_<slug>`, mtime-based, written BEFORE any git work so a crash mid-run can't retry-storm the next session start), with a fast-path exit — before the stamp is even touched, before any git call — when no entry in the store carries `source_files` at all. Per participant, **rename detection runs first**: git-budgeted (`_ANCHOR_GIT_BUDGET` = `2 * _MAX_SOURCE_FILES + 1` = 21 calls/run — derived, not picked: one entry's worst case is every anchored path missing at 2 calls each plus one `rev-parse`, so the budget guarantees the first entry of every run always completes and the run makes forward progress; a smaller budget let one fat entry exhaust it inside its own file loop, silently starving that entry and every entry after it on every run forever, `store._GIT_FAST_TIMEOUT`-second timeouts, fail-soft) `git log --follow` + `git show --name-status` finds a confident single rename target for each vanished path; a target that's found and still exists on disk corrects the entry's `source_files`/`anchor_commit` in place — NOT a review event, since the decision's content is unchanged, only its address moved. No confident rename -> the file is `missing`; partial loss (something survives, as-is or renamed) is still a silent address-list refresh. Total loss (every anchored file gone, none renamed) attaches a rule-shaped `proposed_revision` — current content plus a trailing CLOSED, factual clause ("… (anchors withdrawn on re-verification: `<files>` no longer exist)"), never an open action-request, since an approved proposal ships as the decision's permanent live text — and arms the `.pending_review` nudge; a dedupe guard skips re-attaching if the content already carries the marker. **Approving that proposal clears the entry's `source_files`/`anchor_commit`** (`store._promote_proposal`'s `clear_anchors` handling, stashed on the proposal) so the entry exits anchor-decay participation instead of re-qualifying next TTL cycle and stacking a second withdrawal clause onto the content the first approval just wrote; `_apply_approval` also drops any `anchor_candidates` on a `clear_anchors` approval and skips its candidate-blessing branch, since that branch would otherwise read the freshly-emptied `source_files` as "unanchored" and promote a stale guess into a real anchor — re-anchoring the just-retired decision to unrelated files and pulling it straight back into decay participation and Tier-1 pairing. Dismissing leaves the entry, `source_files` included, untouched — and never writes the clause into the content, so the dedupe guard (which reads content) cannot fire for it: a dismissed retirement is re-proposed on EVERY TTL cycle until it is approved or the decision is ignored (dismiss means "not now", not "never ask again"). **Budget exhaustion is honest, not degraded**: once `_ANCHOR_GIT_BUDGET` is spent, `_call` raises `_BudgetExceeded` instead of returning a value indistinguishable from "git found nothing" (which previously could misclassify a cut-off entry as a total loss or a wrong partial refresh); the entries loop catches it and breaks immediately, leaving the in-progress entry and every entry after it completely UNVERIFIED this run — no proposal, no refresh, no re-anchor, no mutation — deferred to the next TTL window rather than guessed at. `anchor_candidates` (unconfirmed, human-not-yet-blessed anchor guesses) are never by themselves a reason to participate — participation requires a real `source_files` anchor — but they CAN ride along on a participant (candidates survive the pending-twin promote path and `_route_containment`, neither of which pops them), which is exactly why a retirement approval drops them too. Fail-soft throughout: any unexpected failure degrades to a no-op `{"reanchored": 0, "proposed": 0}` rather than raising out of session start.
- **`contexer/conflicts.py`** — conflict rendering + resolution memos (issue #193), extracted out of store.py on the same directive that produced `anchors.py` (one module per cohesive concern; `store.py` stays a thin call-site facade). Owns `_CONFLICT_GUIDE`, `_conflict_pair_key`, `_has_open_conflict`, `_conflict_view`, and `record_conflict_memo`; store-owned helpers (`_title_and_body`, `_current_revision`, `_current_content`, `_normalize_content`, `_store_lock`, `_slug`, `_load`, `_save`, `_entry_by_id`) are read through the `store` module OBJECT at call time — the identical load-order discipline `guard_engine.py` documents, so a test monkeypatching `contexer.store` is still seen here and store.py never needs this module at import time. **A live decision carrying a Suggested Update (`proposed_revision`) that is neither scan/`clear_anchors`-sourced (bookkeeping, not a conversational conflict — those keep the pre-existing flag-only `[update pending approval]` tag, since they re-propose on every 24h TTL cycle and "only the developer knows" is backwards for evidence-driven withdrawals) nor title-only (`_normalize_content`-equal to the current content) is an *open conflict*** (`_has_open_conflict`, the shared gate predicate) and renders BOTH the standing content and the labeled unreviewed update, with dates, at all four model-facing render sites — `get_context`, `_render_prompt_decisions`, the session-start project-rules loop, and `_rehydrate_working_set` (so the conflict survives post-compact rebuild) — via `_conflict_view` (replaces `_title_and_body` at those sites only, proposal-side title read from the proposal's own `title`, never the standing entry's). `_CONFLICT_GUIDE` ("don't resolve via codebase exploration — only the developer knows; ask, then record with `resolve_conflict`") renders once per call whenever any shown entry has an open conflict, not once per entry. **`resolve_conflict(entry_id, choice)`** (the MCP tool → `store.record_conflict_memo`, reachable on the facade through store.py's SAME lazy PEP 562 `__getattr__` block that re-exports guard_engine's entrypoints — the private helpers are deliberately NOT re-exported, so `cli.py`'s review branch imports this module directly for `_conflict_pair_key`) records the developer's EXPLICIT in-session pick as an on-entry `conflict_memo` (`{pair, choice, session_id, created_at}`, precedent: `superseded_proposals`) keyed by `_conflict_pair_key` (sha1 of the resolved current revision id + the proposal's content/title/`created_at`) — the `created_at` component is what stops an identical-content proposal rebuilt after a non-revision-advancing pop (e.g. `verify_scan_conventions`) from reviving a dead memo. `record_conflict_memo` is lock-guarded like `approve_decision`, requires an 8-char-minimum id (renders always emit 8-char ids; prefix resolution is first-match-wins), requires a render-eligible (non-scan, non-title-only) proposal, and writes none of `status`/`approved_by`/`source_files`/`anchor_commit` — so a memo can never arm the commit-time guard. The memo is deliberately **asymmetric**: `choice="standing"` fully hides the update (unreviewed content may be hidden by anyone); `choice="update"` makes the proposal operative but keeps the standing version as one demoted continuation line, since reviewed (human-approved) content may only ever be fully hidden by a review action (`store._apply_approval`'s promote/dismiss are the only two sites that pop the memo — every other proposal-death site leaves it as an inert orphan, harmless because `_conflict_view` early-returns on no-proposal). `store.format_pending_review` and `contexer review`'s terminal proposal branch both render the memo as a per-choice steer note beneath the `detected:`/`Detected:` line, phrased in the same picked/declined vocabulary as the model-facing markers and naming BOTH actions' consequences, so `approve` can't be misread on a declined pick (`the update was picked with the developer on <d> — approve to formalize (dismiss drops it)` vs `the update was declined with the developer on <d> — dismiss to formalize (approve applies it instead)`). Retrieval reachability stays in store.py: proposal content folds into `_matches_query` and the BM25 index's doc tokens (`_build_retrieval_index`), so a decision is findable by the update's own terms before anyone resolves the conflict.

Extracted out of store.py on the same directive that produced `anchors.py` and `conflicts.py` (one module per cohesive concern), and **the boundary was measured rather than chosen**: `contexer/ui/api.py` is the only production caller and it reaches for exactly those names and nothing else, while the rest of store.py called into the cluster exactly ONCE. It was moved out and then moved back when review caught the claim, and the episode is the rule: adjacency in a file is not a boundary, and anything added to `console_api.py` must have a console consumer or the one-caller claim stops being checkable. The console must never open a store file itself (the same one-write-path rule the MCP surface follows), so when a shape the console needs does not exist yet the fix is a new public read HERE, not a file read in `ui/api.py`. Everything is a PURE READ except `delete_global_rule`. **Three things deliberately did NOT move**, each for a reason that would have been invisible after the fact: `load_diagnostics` is the third of a family with `global_diagnostics` and `deleted_diagnostics` (both store-owned, and `ui/api.py` calls `global_diagnostics` directly), so splitting one off would scatter the trio; `_store_files`/`_is_repo_store_file` enumerate which files in `STORE_DIR` are repo stores, which is store-level knowledge `scope_audit.py` depends on by documented contract; and `_file_mtime` is read by `store.verify_scan_conventions` and `anchors.py` as well as here. - **`contexer/scope_audit.py`** — cross-store scope audit: finds decisions saved into the WRONG repo's store (see "Wrong-store writes" under Storage). The fingerprint needs no heuristic — **one session id appearing in more than one repo store**. A session belongs to one project, so decisions from it landing in two stores means at least one of those stores is wrong; that is exactly how the original case was found, and every entry already carries the field. Only the ORIGINATING `session_id` counts, never `session_ids` — the latter accumulates every session that has TOUCHED an entry, so a recurrence recorded from a second session is normal and would otherwise read as a misroute. Two exclusions keep it from crying wolf, both found by running it against real stores rather than reasoned about: **the store-file set comes from `store._store_files()`, never a local re-glob** — `<slug>.deleted.json` tombstones carry the same `{"repo_path", "entries"}` shape as a real store, so a hand-rolled "skip dotfiles and `_global`" filter reads a repo's deleted decisions as a SECOND store for that same repo and tells the developer to re-capture a decision they deliberately deleted; and **memory imports never participate** (`_is_memory_import`) — `memory_sync` stores an unattributed fact under the LITERAL id `"memory-sync"`, so every repo that ever imported one shares that id and pairs with every other such repo forever, and even a real `originSessionId` records where the FACT came from rather than which repo a writer targeted. That second exclusion is detected three ways (`created_by`, `memory_key`, the sentinel id) because entries are read RAW here, without `_load`'s migration — which is also why the per-entry title derivation is individually guarded AND every rendered field goes through `_text()`: a raw field can be a JSON null (`.get(k, "")` returns `None` when the key EXISTS with a null value, which then blows up the timestamp sort and every slice in the report), a number, or a list, and a read-only command must never exit on a traceback. The global store never participates (cross-repo BY DESIGN), and a corrupt store contributes nothing rather than raising. **A store FILE is not the unit of identity** — `_repo_identity` groups by `os.path.realpath(_canonical_store_key(repo_path))`, because a pre-fix stray worktree store sits beside its canonical file until that repo's next session start folds it in (`migrate_worktree_strays`), and counting both would report a correctly-scoped session as split. The `realpath` on top is load-bearing rather than defensive: a main worktree fast-paths out of `_canonical_store_key` with its path unchanged while a linked worktree goes through `git rev-parse --path-format=absolute`, so under a symlinked root (`/tmp`→`/private/tmp`) the two canonical keys differ by that prefix alone and would not merge. A store whose own `repo_path` is unreadable stays keyed by its file rather than being merged blindly. **Known limit, labelled rather than papered over:** this can only merge a worktree that still EXISTS — once the directory is removed or pruned there is no `.git` file to read and `git worktree list` no longer enumerates it, so nothing on disk ties the stray back to its main worktree (`migrate_worktree_strays` cannot fold such a stray either, for the same reason) and merging would mean guessing from path shape, which worktrees do not constrain. That store is therefore rendered with a `(path no longer exists — a removed worktree or deleted checkout)` note so the row explains itself, and `_exists` is fail-soft so an unstattable path (dead mount, permission wall) is never accused of being gone. **The report states a question, not a verdict**: the fingerprint is a WRITE-SESSION id, and for MCP captures that is `server.SESSION_ID`, a uuid4 minted per server PROCESS — so a developer who deliberately captured into a second repo by naming it, or a host reusing one server process across workspaces, produces this exact shape with nothing wrong (`[via argument]` is the tell). It caps at `_MAX_ENTRIES_SHOWN`=10 per store with a `showing N of M` note, like every other human-facing surface here, and its remediation names `approve_decision(action="ignore")` or the console — deliberately NOT `contexer review`, which lists only decisions still PENDING in the CURRENT repo while a misrouted decision is normally already approved and in another one. Each reported entry carries its stamped `repo_source`, so a deliberate cross-repo write (`argument` — a developer named the repo) is distinguishable at a glance from a misrouted one. **Read-only, and staying that way:** moving an entry rewrites where a decision is recorded as having been made, and this module can tell only that two stores disagree, never which one is wrong — so it reports, names the files, and stops, per the same informed-signature rule the anchor backfill already established. Surface: `contexer scope-audit` (no arguments; anything else exits 1 rather than being ignored, the `guard anchors` rule so a read-only-sounding flag can never read as consent). A leaf module: imports `store`, nothing imports it back.
- **`contexer/miner.py`** — deterministic convention mining, stdlib only (`ast`/`tomllib`/`re`/`configparser`/`subprocess`). `mine_conventions(repo_path) -> list[dict]` (`{"content", "subtype": convention|pattern, "tier": high|medium}`) measures conventions with whole-repo evidence embedded in the sentence itself ("Functions use snake_case naming (98% of 412 functions across 37 files)"): config-encoded rules (ruff line-length/quotes, mypy strict, pytest coverage floor, .editorconfig, pre-commit hook ids via regex, prettier/eslint/tsconfig-jsonc, CI `run:` lines), AST source statistics (naming dominance, type-hint/docstring coverage, absolute-vs-relative imports, custom exception classes, bare-except absence), test conventions (layout, naming pattern, plain-assert vs unittest dominance, fixture count), and commit-message convention (Conventional Commits % over the last 100). Thresholds are the verification story: ≥90% dominance with ≥20 samples → tier high, 60–89% → medium, below either bar → not emitted (silence over noise); presence detectors need ≥3 occurrences. Caps: ≤400 .py files, ≤200KB/file, ≤2000 dirs; skips `_SKIP_DIRS` and ALL dot-directories (tool state like `.claude` worktrees would poison the statistics). Never raises; never emits `subtype="constraint"` (scan-sourced entries bypass the constraint→pending rule in `_classify_level`). A leaf module: imported by store.py, never imports it (own tiny `_git`). JS/TS/Go/Rust *source* stats are deliberately out of scope — their conventions are captured via configs, which is the verified path.
- **`contexer/redact.py`** — deterministic secret redaction, stdlib only (`re`). `scrub(text) -> (redacted_text, count)` (plus `scrub_text` / `count_secrets` convenience wrappers) replaces each detected secret with `[REDACTED:<kind>]`. **Balanced** detection: high-confidence provider token shapes (AWS `AKIA/ASIA`, GitHub `gh*_`/`github_pat_`, Slack `xox*`, Stripe `[sr]k_live_`, Google `AIza`, OpenAI/Anthropic `sk-`/`sk-ant-`, SendGrid, `npm_`, `pypi-`, Twilio `SK`), PEM private-key blocks, JWTs, `Bearer` tokens, and connection-string passwords, PLUS a keyword-gated generic catch-all (`password|secret|token|api_key|access_key|client_secret|private_key|auth …[:=] value`) that redacts the value only when it **looks secret-like** (`_looks_secretlike`: ≥6 chars AND not a plain lowercase word / hyphenated phrase) and **skips placeholder-ish values** (`<…>`, `***`, `env(…)`, `${…}`, empty). The prose gate is deliberate: without it the catch-all mauls ordinary decision text like `auth: required` or `token = short-lived` (known tradeoff: an all-lowercase passphrase reads as prose and is missed — provider patterns still catch real API keys, and not corrupting stored decisions wins). No entropy heuristic (rejected — would false-positive on SHAs/UUIDs/base64). **Idempotent** (the `[REDACTED]` placeholder never re-matches) and **never raises** (any failure degrades to best-effort). A leaf module: imported by `store.py` and `remote.py`, imports neither. **Redaction is EGRESS-ONLY by deliberate design** — capture is NOT scrubbed, so the local store stays a faithful, verbatim record of decisions (scrubbing local `0600` files buys little when the real secrets sit in `~/.aws`/`.env`, and a redactor that silently rewrites captured decisions would corrupt the product's core value). Secrets are removed only where a decision actually LEAVES the machine: **`remote._wire_args`** (the last-mile every push/batch/drain funnels through → the hard guarantee no secret reaches the remote MCP), plus **`store._share_projection`** (so the confirm-preview + durable outbox show exactly what will be sent), with `format_share_preview` surfacing a `(N secrets redacted before sending)` banner. Honors a `_redaction_enabled()` fail-soft toggle reading `config.redact_secrets` (default **True** — safety holds unconfigured; opt out with `redact_secrets = false`). The flag is resolved **once per operation** and threaded down, never re-read per element: `get_shareable`/`get_shareable_all`/`_share_projection` and `remote._wire_args` all take a `redact_on` param (None = resolve locally), the batch `apush_decisions` resolves it once for the whole batch, and `format_share_preview` resolves the profile once (governing both endpoint and redaction) so an explicitly-passed profile's `redact_secrets` is honored rather than a fresh global config read. `RemoteStore._redact_on()` likewise honors the `Profile` the store was built from (`from_profile`) — an explicit opt-in must not be lost to a global opt-out on disk — falling back to the global config only for a profile-less (directly-constructed) store. The generic keyword catch-all redacts a **quoted** value as a whole span (a quoted passphrase with spaces is fully removed, not just its first word), and `Bearer` matching is case-insensitive.
- **`contexer/adapters/`** — one module per AI-assistant target. `base.py` holds shared config-file helpers (`_load`/`_save`/marker checks). **Marker-matching has two variants and picking the wrong one fails silently:** `_in_groups` matches against `str(hook_dict)` (the dict's *repr*, so it sees command + statusMessage + matcher at once) — but a repr escapes quotes, and every real hook command is `py -c "..."`, i.e. contains a double quote, which forces repr to `'`-delimit and rewrite an inner `'codex'` as `\'codex\'`. A gate keyed on a quoted marker therefore never matches, never recognizes the hook it just installed, and re-fires on every install forever (this was live in `codex.py`'s team-poll gate: pure churn, since the correct hook was re-added each time, but no Codex install was idempotent). Use `_in_commands` — raw `command` match, quote-safe — for **any marker containing a quote**. The trap is that a marker with single quotes alone *appears* to work, because repr leaves those untouched. `claude.py`, `cursor.py`, `codex.py`, and `gemini.py` each own that tool's MCP registration, hook wiring, install/uninstall/status, and provider-specific hook output. `__init__.py` is the registry (`detect()` / `select()`). Gemini stores MCP and hook configuration together in `~/.gemini/settings.json`; it uses `SessionStart`, `BeforeAgent`, `AfterTool(write_file|replace)`, `PreCompress`, and `SessionEnd`. Because `PreCompress` is asynchronous and Gemini has no `PostCompress`, `gemini.py` sets flags and re-injects stored context at the next `BeforeAgent` event.
- **`contexer/memory_sync.py`** — imports Claude Code's memory-tool facts (`~/.claude/projects/<slug>/memory/*.md`) into the store, so decisions a session persisted to the file-based memory tool (instead of calling `update_context`) still reach Contexer. This is a *coexistence* path, not a competitor for capture: rather than fight an authority contest hook-injected reminders always lose against another tool's system-prompt memory workflow, Contexer becomes a deterministic sync target. No model in the loop — parses each fact's YAML frontmatter (`description`/`type`/`originSessionId`) + body, splits multi-section docs on `##` headings into one entry each (never a raw blob), assigns a subtype by keyword rules (ordered `convention` > `constraint` > `pattern` > `architecture`, with a frontmatter-`type` backstop — `feedback`→convention, `project`→architecture — and an architecture default, so *every* import is queryable via `get_context(entry_type=...)`), and upserts the whole dir in one load+save via `store.upsert_memory_batch`, keyed on a stable `memory_key` (source file + `##` section; repeated headings are disambiguated so they don't collide) so a fact reworded on disk updates its entry *in place* rather than silently dropping the edit (<30% change) or accumulating a near-duplicate (>30% change). First-time creation still passes the >70% novelty filter, so a memory fact that merely restates an existing decision is recorded as a recurrence, not double-stored across the two systems. Provenance: `session_id` = the fact's `originSessionId`. Fail-soft per file — a malformed memory file is skipped, never raised. The module is neutral (takes a dir path); `adapters/claude.py` owns the Claude-specific `_memory_dir(repo_path)` slug derivation (`re.sub(r"[^a-zA-Z0-9]", "-", repo_path)` — the one fragile coupling point, marked in code: if Claude Code changes its project-dir encoding, sync fails *safe* (finds nothing, never wrong data) but can go quietly dead) and `sync_memory(repo_path)`, which skips the whole import when a content fingerprint (`~/.contexer/.memory_synced_<slug>`) is unchanged.
- **`contexer/cli.py`** — the `contexer` console script: bare invocation runs the MCP server; subcommands `install [--target claude|cursor|codex|gemini|all]` / `uninstall [--purge]` / `reinstall` / `status` / `scope-audit` (read-only wrong-store report — see `scope_audit.py`) / `version` / `help` manage tool configs. `install` auto-detects present tools (`~/.claude` → Claude Code, `~/.cursor` → Cursor, `~/.codex` → Codex, `~/.gemini` → Gemini CLI) and falls back to Claude Code when none is detected; `--target` overrides.
- **`server.py`** (repo root) — back-compat shim importing `contexer.server`; keeps `uv run python server.py` working.
- **No `requirements.txt`.** `pyproject.toml` is the single dependency spec (managed by `uv`). A "kept for reference" `requirements.txt` used to sit here carrying its own copy of the `mcp>=1.9.4,<2` bound; nothing consumed it (not CI, not `scripts/`, not `CONTRIBUTING.md`), so it could only ever drift out of agreement with the real bound — where the upper bound is load-bearing, since mcp 2.0.0 removed `mcp.server.fastmcp` and an unbounded resolve installs a server that cannot start. Do not re-add one; `uv sync` is the install path.

## Storage

Context is stored at `~/.contexer/<repo_slug>.json` - one file per repo, plus `_global.json` for cross-repo decisions. The slug is the repo path with non-alphanumeric characters replaced by underscores. Each file holds a flat list of entries. Writes are atomic (unique temp file + `os.replace`, mode 0o600) so readers never see a torn file; corrupt files are read as empty rather than crashing.

Linked git worktrees share the main worktree's store: `_slug` canonicalizes the STORE KEY ONLY via `_canonical_store_key` (a `.git` *file* whose `gitdir:` contains `/worktrees/` → one `git rev-parse --path-format=absolute --show-toplevel --git-common-dir` call, success-only cached, entirely fail-soft), so every slug-keyed artifact (store, lock, sidecars, flags, team cache) collapses while staleness/insight/miner still see the physical worktree path. Submodules (`gitdir: .../.git/modules/…`), `git init --separate-git-dir` repos, and worktrees of bare hosts (`repo.git`) deliberately keep their own keys. `migrate_worktree_strays(repo)` — called fail-soft at session start alongside `_gc_stale_session_files` — folds pre-fix stray worktree stores (self-detected plus `git worktree list` enumeration, never filename-prefix guessing) into the canonical store: id-first dedup, then the store's own >70% novelty gate, stray kept as `*.json.migrated` rather than deleted.

### Decision / Revision model (Git-like: storage preserves history, replay = current)

A decision is the logical engineering decision; a **revision** is one immutable version of it. Storage preserves every revision forever; replay exposes only the current approved one (like Git keeping every commit but cloning HEAD). This separation is what lets engineering history accumulate without ever growing the prompt or letting stale/pending values leak into a session.

The model is **embedded**, not normalized into a second collection: each decision entry owns its revisions inline (`revisions[]`) with an explicit `current_revision_id` pointer. This is the correct serialization for strict 1-to-many ownership (a revision belongs to exactly one decision, is never shared, never queried independently) and keeps the flat-list-per-repo storage and atomic whole-file write intact. The heavy query-side concerns (timeline, diff, audit, analytics, team approval, shared semantic search) live **upstream** in the remote teams MCP that decisions forward to (`push_decision`) - this OSS local store is a capture client + cache + outbox, so duplicating a relational/vector engine locally would be wasted. The embedded JSON maps 1:1 onto upstream `decisions` + `revisions` (+ a future `revision_embeddings` index) tables when that day comes, so no schema migration is needed to add those.

**Decision entry** carries: `id` (= decision_id), `type` (`task` | `decision`), `subtype` (`architecture` | `constraint` | `pattern` | `convention` - maps to the upstream 3-value `type` enum, with `pattern`→`architecture` on forward), `status` (`approved` | `suggested` | `pending_approval` | `ignored`), `current_revision_id` (the active revision - precedence is the pointer, **never** timestamps), `session_id`, `session_ids` (all sessions that have seen it), `timestamp` (Created At - immutable), `updated_at` (bumped when the current revision changes), `occurrence_count`, `created_by`, `revisions[]` (canonical list of all revisions incl. current), and optionally `proposed_revision` (a pending Suggested Update - never replayed until approved), `memory_key`, and `source_files`/`anchor_commit` (staleness anchor - see below). The decision also keeps `content` / `revision` (current `version_number`) / `confidence` / `confidence_factors` as a **synced HEAD-cache** of the current revision (`_sync_decision_cache`) so the many read sites stay O(1); the revisions are the source of truth, the cache is rewritten from them on every change.

**Revision object** (`_new_revision`): `revision_id`, `decision_id`, `version_number` (1-based), `content`, `confidence_score`, `evidence` (factor list), `created_at`, `approved_at`, `source` (provenance: `ai` | `human` | `scan` | `bootstrap` | `memory`). Revisions are immutable once superseded (the new-decision pre-approval edit amends v1 in place, since there is no prior version to preserve yet).

**Accessors / lifecycle:** `_current_revision(entry)` / `_current_content(entry)` resolve the pointer (fallback: last revision); `_append_revision(entry, content, source, approved_at)` creates the next version, advances `current_revision_id`, snapshots confidence onto the revision, and resyncs the cache; this is the single path used by trivial in-place updates, `_promote_proposal` (approve a Suggested Update), and memory-sync changes. Approving a brand-new `pending_approval` decision blesses revision 1 in place (no new version). **Migration is transparent and idempotent** (`_migrate_decision`, run from `_load`): a legacy entry (old `content`/`revision` head + historical-only `revisions[]` snapshots) is rebuilt into full revision objects + a `current_revision_id` on first load; persisted on next save; fail-safe (a corrupt file still reads as empty).

**Which repo a tool call targets** is resolved by `store._resolve_repo(repo_path)` with this precedence: (1) an explicit, sane `repo_path` argument; (2) `_SESSION_REPO` — the repo bound to the running MCP-server process, captured once at startup from its own cwd's git root via `server.main` → `set_session_repo(_git_root(os.getcwd()))`; (3) the shared `~/.contexer/.current_repo` pointer as a last resort. The per-process binding (2) exists because `.current_repo` is a single global file every assistant hook overwrites — a different tool or session could clobber it and send decisions to the wrong store file. `_is_sane_repo` rejects the home dir and tool config dirs (`~/.claude`, `~/.cursor`, `~/.codex`, `~/.gemini`, `~/.contexer`, `~/.config`) on every read and write, so a poisoned pointer can never select a config-dir store file (it also rejects the filesystem root). **Hooks additionally fall back to their own cwd** (`store._hook_cwd_repo`, applied in `session_start_payload`, `bootstrap_prompt_payload`, and the per-prompt Claude entrypoints): hosts run hooks with cwd = the project directory, and non-git projects are first-class stores keyed by absolute path, so an empty git-root from the hook's shell must not erase the session's identity - the 0.16.1 bug was SessionStart claiming "no context stored" in a non-git dir whose store existed, while the MCP tools (explicit `repo_path`) found it fine. The fallback is `_is_sane_repo`-guarded (a session opened in the home dir keeps the normal chain) and is deliberately NOT the retired `|| pwd` shell fallback: the shared pointer is only written from `session_start_payload` after the same sanity check, mirroring the git-repo case. `_resolve_repo` itself is unchanged - adding a cwd fallback there would misresolve for MCP servers whose cwd is not the project (Cursor launches its server outside the workspace).

**Wrong-store writes are diagnosable, not yet prevented.** Decisions have been observed landing in the wrong repo's store — one session's nine captures split across THREE store files, five in the project it was working in and four in unrelated projects, where they now read as those projects' engineering decisions. Nothing leaked at read time (retrieval is already hard-scoped per repo); the records are physically in the wrong file. `_resolve_repo_verbose(repo_path) -> (repo, source)` is the real resolver and returns WHICH branch chose the store — `argument` | `session` | `pointer` | `none` — with `_resolve_repo` kept as a one-line wrapper so the eight read call sites in `server.py` are untouched. Precedence is **byte-for-byte unchanged** (the old `if repo_path:` branch was redundant with the chain below it and folds away). **Hooks get their own labels, and this is not cosmetic:** a hook process ALWAYS supplies a path — the installed shell wrapper passes `git rev-parse --show-toplevel`, and `_hook_cwd_repo` substitutes the process cwd when that is empty — so through the plain resolver every hook capture could only ever report `argument`, the one label the audit reads as *a caller deliberately named this repo*, which would file each misrouted directive as intentional. `store._hook_repo_verbose` therefore reports `hook-arg` | `hook-cwd` before falling through to the shared chain, and Cursor, whose `workspace_roots` is a signal no other host has, labels that branch `workspace-root` via its own `_repo_from_verbose`. **Every capture surface stamps**, so an absent tag means what the report says it means: `update_context` and `capture_user_constraint` (MCP), the per-prompt constraint hooks on all four hosts, and `bootstrap_apply` — the largest bulk write in the system (one consolidated Stack entry plus every mined convention in a single save), which builds entries through `_new_decision_entry` directly and so stamps at both of its creation sites rather than inheriting `update_decision`'s. `update_decision` stamps on **newly created entries only** — a recurrence or containment route has already returned by then, and re-stamping would overwrite the provenance of the write that created the entry. What is deliberately NOT done: refusing the pointer when it disagrees with the server process's cwd. Disagreement is the NORMAL state whenever two projects are open (the pointer is one global file every session overwrites), and a host that launches the server outside the workspace — Cursor, documented above — has no sane cwd to corroborate against, so that rule would resolve to nothing at all for it. The policy stays put until the stamped provenance says which branch actually fires; guessing at a new one risks misrouting differently, not less.

## Session behaviour (hooks)

`~/.claude/settings.json` wires up hooks globally (applies to every repo):

- **`SessionStart`** — first runs `claude.sync_memory` to import any memory-tool facts (crash-recovery net: catches facts whose previous session ended without a clean `SessionEnd` flush), then injects all *approved* conventions, patterns, and constraints as project rules — constraint-subtype rules (and any rule with an open conflict) render in full, while convention/pattern rules render title-only (a footer points at `get_context` for the full reasoning, appended only when a body was actually clipped) to keep the injection within the host's `additionalContext` size limit; injects a count pointer for deferred architecture decisions (fetched JIT via `get_context`); the same deferral applies to the synced **team** context section this hook appends via `store.session_start_payload` (`_team_section(..., defer_architecture=True)`) — a team-synced architecture decision renders as a count-only pointer alongside the local ones, not full content, with `get_context(entry_type="architecture")` returning both personal (`[scope=personal]`) and team (`[scope=team]`) architecture decisions in full on demand; deferral exempts a team architecture row that already collapses to the cheap `[scope=team] ratifies local decision <id>` one-liner (>= 0.7 token overlap with a stored local decision) — that row is already as light as the deferred-count pointer itself, so hiding it too would only throw away its ratification signal for zero token savings (`team_context.count_deferred_architecture` mirrors this exemption so the `status` suffix's `(M shown)` figure — see below — only subtracts rows genuinely hidden behind the pointer); injects a **count-only** pointer for decisions awaiting review (never their content — pulled on demand via `review_pending`); injects a bootstrap offer if no context exists. Resume-aware and compaction-aware via the `source` field read from hook stdin (`source_from_hook_stdin`): on `resume` with context, skips re-injection entirely (the conversation already contains it); on `resume` without context, injects transcript-mining instructions instead of the menu; on `compact` it takes the normal path and silently re-injects the full context (this is what reloads context after compaction — there is no separate `PostCompact` hook) (mine decisions from the visible conversation + store scan facts, all in the first turn — no human round-trip) and writes `~/.contexer/.resume_mining` so the UserPromptSubmit bootstrap fallback stays silent (the flag is consumed on first prompt; non-resume session starts clear stale flags).
- **`PostToolUse` (Write|Edit, silent)** - fires after every `Write` or `Edit` tool call, running `claude.post_write` (replacing the old shell-only `touch .pending_capture`). Two jobs in one hook: it records the edited file into a **per-repo** sidecar via `store.record_edited_file` (`~/.contexer/.edited_<slug>.json`, a list of `{path, mtime}` records canonicalized through `guard_engine._guard_relpath`, re-stamped in place on a repeat edit, capped at `_EDITED_FILES_CAP`=50 evicting the oldest by mtime) — the **flow** half of anchor accrual (see Commit-time guard below); and it touches `~/.contexer/.pending_capture` exactly as before. **Keying per repo — never per session — is load-bearing:** the writer is this hook's process (session id from the host's hook stdin) while the reader is the MCP server process (`server.SESSION_ID`, a uuid4 minted at server start), so a session-keyed filename could never once agree between the two and left the whole flow loop inert in production (while tests that handed both sides the same literal id passed). Staleness is bounded by each record's own timestamp instead: `store._read_edited_files` returns only paths edited within `_EDITED_FILES_WINDOW`=1800s, and the read is non-destructive, so several captures in one turn each see the same list. Concurrent writers on one repo race last-writer-wins on an atomic whole-file write — at worst one edit record is lost, costing a candidate suggestion and nothing else. Completely silent - no UI output. Codex reuses `claude.post_write` verbatim on its own `PostToolUse`; Gemini calls `store.record_edited_file` from its `AfterTool(write_file|replace)` hook (`adapters/gemini.py`'s `after_write`) — same signal, different event name. Cursor recording is out of scope for now (#175). The installed shell wrapper resolves the repo via `git rev-parse --show-toplevel`, matching every other per-prompt hook in this module — a diverging resolution here would key the sidecar under a different slug than the reader expects and silently kill the signal in a monorepo subdirectory.
- **`.pending_review` (deterministic mid-session nudge).** Unlike `.pending_capture` (written by a hook), the **per-repo** `~/.contexer/.pending_review_<slug>` flag is written by the **store**: `store.update_decision` touches it at the two spots that create a state awaiting the developer — a new `pending_approval` entry (gated on status) and a freshly-attached `proposed_revision` — after `_save`, inside the store lock (`store._touch_pending_review(repo_path)`). Per-repo (not global) so a pending decision in repo A never nudges a session in repo B. The per-prompt consumer is `store.pending_review_nudge(repo_path)`: it fires the count-less "offer to `review_pending`, then `approve_decision`" nudge **only** when this repo has a freshly-set flag AND still has decisions pending (`get_pending_decisions`) — so a flag left by an already-approved decision, or by another repo, never yields a false nudge — then clears the flag (fire-once; a new pending decision re-arms it). So decisions captured mid-session resurface at the next natural turn instead of waiting for the next SessionStart. Consumers per adapter: **Claude/Codex** call the Python entrypoint `claude.review_nudge` from a UserPromptSubmit hook (Python, not shell, so it can compute the slug and verify the store; Codex reuses `claude.review_nudge` verbatim and lists it in `_EVENT_MARKERS` since it has no sentinel); **Gemini** calls `store.pending_review_nudge` in `before_agent`, independent of the compaction-reload branch (a reload re-injects `get_context`, which *excludes* pending decisions, so the nudge must still fire); **Cursor** can't inject per-prompt context (`beforeSubmitPrompt` returns `{continue}`), so its reminder rides the always-apply `.mdc` rule body instead. `capture_user_constraint` deliberately does NOT arm this flag for its own `pending_approval` entries — its in-band `constraint_ack` notice (self-approval-proofed) already tells the model to surface the pending decision to the developer that same turn, so a second, deferred nudge would only double up.
- **No `Stop` hook.** An end-of-turn `Stop` hook that prompted the model (via `additionalContext`) to capture/review decisions was evaluated and removed: it added latency and tokens and depended on model behavior, while delivering nothing the deterministic `PostToolUse` flag + next-prompt anchor reminder doesn't already deliver at a non-interrupting moment. `claude.install`/`codex.install` actively strip a previously-installed Contexer `Stop` hook (matched on `.pending_capture`) while leaving any foreign `Stop` hook intact; the `Stop` marker stays in the uninstall tables for this cleanup. Decision *updates* are surfaced deterministically (the `proposed_revision` Pending Update + `contexer review`), not by mid-turn prompting.
- **`UserPromptSubmit` (anchor, command, every prompt)** — writes the git root to `~/.contexer/.current_repo`, but only when actually inside a git work tree (no `|| pwd` fallback — that could poison the pointer with a non-repo dir). Also checks for `~/.contexer/.pending_capture`: if present, deletes it and injects `additionalContext` reminding Claude to call `update_context` for decisions from the previous turn. Silent to the user — only Claude sees the injected context.
- **Bookkeeping writes are best-effort everywhere (#152).** `~/.contexer/.current_repo`, `.pending_capture`, `.pending_review`, and `.resume_mining` are *bookkeeping*, not context: the pointer is only the last resort in `_resolve_repo`, and the flags merely schedule a reminder. A sandboxed host can leave the workspace writable while `~/.contexer` is not (Codex's managed sandbox), and an unguarded write there used to raise `PermissionError` and abort `SessionStart` — Contexer injected nothing at all over a file it never needed in order to *read* context. So: every adapter anchors through the one fail-soft, sanity-checked `store.anchor_repo(repo)` helper (never a raw `write_text`); `_store_path`/`_global_path` treat their `STORE_DIR.mkdir` as best-effort so *readers* can't be crashed by an uncreatable store dir (writers still surface the failure at their own write); and the shell hooks guard both writes — `{ printf … > ~/.contexer/.current_repo; } 2>/dev/null || true` (braces matter: `cmd > f 2>/dev/null` opens the redirect *before* stderr is silenced, so a bare suffix still leaks the error) and `touch ~/.contexer/.pending_capture 2>/dev/null; echo '{}'` (`;` not `&&` — a failed touch must not swallow the hook's mandatory JSON output). `claude.install`/`codex.install` migrate the pre-#152 unguarded forms on the next `install`/`reinstall`, gated on `anchor_repo` in `ss_code` and on `claude._TOUCH_GUARD` / `claude._ANCHOR_GUARD` in the shell hooks. The invariant: **inability to write an optional bookkeeping file never prevents a hook from rendering context.**
- **`UserPromptSubmit` (bootstrap, command, once)** — calls `store.get_bootstrap_context_prompt` on the first prompt; injects the bootstrap offer if no context exists (fallback for when SessionStart is skipped).
- **`UserPromptSubmit` (constraint, command, every prompt)** — calls `claude.capture_constraint` with the prompt text. Detects prescriptive directives (`always X`, `never Y`, `from now on Z`) and stores them as `decision` entries automatically — no Claude involvement needed. Silent no-op for all other prompts. To avoid crowding the store, `_is_prescriptive_constraint` rejects anything that isn't a clean standalone directive: pasted blobs over `_MAX_DIRECTIVE_LEN` (300) chars, fenced code dumps, and tool/system-injected text (`<task-notification>`, `<system-reminder>`, Contexer's own injected context) — these merely *contain* directive words and are never genuine user rules. A further family of guards strips non-directive uses of a trigger word and re-checks, so a sentence that only *sounds* prescriptive doesn't land: the `never mind` dismissal clause (`_IDIOM_STRIP`, bounded on punctuation **and** on a coordinating conjunction, so a directive joined without punctuation — "never mind the perf concerns and always validate input" — isn't swallowed with it), predictive `will/would (always|never)` (`_MODAL_PREDICTIVE`, skipped when the imperative `you will/would …` construction is present, since "you will always X" is a command, not a forecast), and hedged `could/might/may (always|never)` (`_HEDGE_MODAL`). **`ensure you` / `make sure you` are treated as weak emphasis wrappers, not durability markers** (`_WEAK_EMPHASIS`): unlike `always`/`never`/`from now on`, they introduce one-off session work as readily as standing rules ("ensure you ship the dashboard" vs "ensure you never commit to main"), so when a wrapper is the ONLY trigger that matched, a durability signal — a prohibition (`not`) or a **recurrence** marker (`every`/`each`, `_DURABILITY_SIGNAL`) — is required before the prompt is stored at all; any other trigger word in the sentence already carries its own durability and passes this check inherently. `all`/`any` are deliberately NOT durability signals: they are OBJECT quantifiers, sizing what to act on rather than how often, so they read identically in a rule and in a one-off task (`ensure you fix any failing tests`) and would let that task through as a trusted standing constraint. Residual, pre-existing and out of this guard's reach: `do not`/`don't` is itself a full trigger, so `ensure you do not skip the migration step` never reaches the weak-only check — distinguishing that from the genuine `do not commit directly to main` needs a different mechanism than trigger strength. Also `for now` counts as deictic (`_TEMPORAL_SCOPE`), so a temporarily-scoped directive lands `pending_approval` rather than trusted. A clean standalone directive is stored **trusted** (`approved`) automatically; a directive carrying a conversation-local reference (`store._is_deictic`: this/these/those unless scoping the rule to `this repo`/`project`/`repository`/`codebase`; `it` unless in the self-resolving idiom `make it a <rule/...>`; non-trailing `here` — a trailing `here` means "in this repo" and stays trusted — bare `that` is excluded, relative/complementizer uses dominate) is stored `pending_approval` with an in-band ack (`store.constraint_ack`) that tells the model to notify the developer and explicitly forbids self-approval. A later clean restatement that matches (>70% token overlap) its own still-pending twin promotes it to `approved` in place rather than being silently dropped as a duplicate; entries the developer already `ignored` are excluded from that match so a re-typed rule lands fresh, not permanently blocked. When that overlap gate misses but the new directive is a containment match of a stored rule (>70% of the smaller side's tokens shared — a superset or subset restatement), it is routed onto that entry instead of accumulating: a superset of an approved rule becomes a `proposed_revision` (suggested update, developer-reviewed), a superset of its own pending twin promotes (clean) or amends in place (deictic), and a terse restatement of an approved rule records a recurrence — never a new overlapping entry; moderate lexical near-matches (0.25–0.7 overlap) are listed in the ack for developer-confirmed consolidation only.
- **`UserPromptSubmit` (rationale, command, every prompt)** — calls `claude.rationale` with the prompt text; auto-injects matching decisions when the prompt contains rationale keywords (why, reason, rationale, decided, etc.). Silent no-op for all other prompts. When it does inject, it also emits a user-facing `systemMessage` naming what was recalled ("Contexer: recalled N decision(s) (topics)" / "Contexer: pointed at related decisions (topics)"), with a token-savings estimate (injected estimate × `_SAVED_MULTIPLIER − 1`, benchmark-derived, nearest 10) appended only above `_COST_NOTE_TOKENS` — built from `store.get_context_for_prompt_with_meta`'s structured `{kind, count, topics}`, not scraped from the rendered text.
- **`UserPromptSubmit` (team poll, command, every prompt)** — calls `claude.team_poll(repo, raw, consumer)` (C7 delta-poll; `consumer` defaults to `"claude"`, Codex passes `"codex"` — Codex reuses this exact function). **Non-blocking by design: the prompt path never performs network I/O.** Mirrors the SessionStart deferral: a newly-approved `architecture`-typed row is never dumped into the "just approved" banner as full content — it's rolled into a single count-only line pointing at `get_context(entry_type="architecture")`, while non-architecture rows still render in full immediately. Delivery is a **per-repo sync log + per-consumer high-water mark** (replacing the old single `.team_pending_<slug>.json` file, which a single consumer would claim, starving any other session on the repo): `_sync` appends `{seq, ids}` to a `sync_log` inside the cache file whenever it merges new/updated team rows (`seq` is a stored monotonic counter, never wall-clock — deterministic, clock-skew-immune; the log is capped at the last 50 batches, oldest dropped — a consumer further behind than the cap just misses old *banners*, the rows stay reachable via `get_context`). Each consumer keeps its own marker `~/.contexer/.team_seen_<slug>_<consumer>.json`; `team_context.poll_nonblocking(repo, consumer)` returns the rows from every log batch with `seq >` that marker (deduped by id, current version resolved from the cache), advances the marker, and — at most once per 15s — spawns a detached refresher process (`python -m contexer.team_context <repo>`) whose synced batch surfaces on the *following* prompt. So a Claude and a Codex session on the same repo each receive every newly-synced batch exactly once, independently. A brand-new or corrupt marker initializes to the current log head (caught-up, injects nothing that once) rather than 0, because SessionStart already renders the existing backlog — the delta-poll must only surface batches logged *after* the session started. The throttle stamp is written *before* spawning so a crashing refresher can never cause a spawn storm; a leftover legacy pending file is deleted on first poll. All read paths are fail-soft (corrupt marker/log degrades to an empty injection, never raises). Trade-off (deliberate): one prompt of extra staleness vs. the synchronous poll, in exchange for a hard guarantee that a slow or hanging cloud (worst case previously: the full transport timeout, ~10s) can never stall prompt submission. The synchronous `team_context.poll()` remains for callers that want blocking semantics.
- **`PreCompact`** — runs `claude.sync_memory` to flush memory-tool facts before the context window collapses, then injects a systemMessage reminding Claude to call `update_context` for any unsaved decisions.
- **No `PostCompact` hook.** After compaction Claude Code fires `SessionStart` again with `source="compact"`, and that event silently re-injects the full context via `additionalContext` (the normal `session_start_payload` path) — so post-compaction reload is already owned, seamlessly, exactly like a fresh session start. A `PostCompact` hook was tried and removed: `PostCompact` supports no `additionalContext` and its `systemMessage` is user-facing only (the model never sees it), so it reloaded nothing and merely dumped the entire stored context into the transcript as visible noise on every `/compact`. `claude.install` now actively strips a previously-installed Contexer `PostCompact` hook (matched on `get_post_compact_context` / the sentinel) while leaving any foreign `PostCompact` hook intact; the `PostCompact` markers stay in the uninstall table for this cleanup. (The neutral `store.post_compact_payload` / `get_post_compact_context` helpers are retained for the Codex adapter and Gemini's `BeforeAgent` re-injection, which do inject on their own event models.)
- **`SessionEnd`** — runs `claude.sync_memory` to flush memory-tool facts on clean exit. The earlier decision to reject `SessionEnd` hooks was about *capture that needs the model to act* (a `SessionEnd` hook can't make Claude call a tool); this is a deterministic file import that needs no model, so it is valid here. These three triggers (`SessionStart`, `PreCompact`, `SessionEnd`) are the memory-sync surface; the import itself is idempotent, so running it at several of them is cheap.
- **Legacy repo-settings cleanup (upgrade hygiene).** The pre-CLI from-source installer (June 2026) wrote hooks into the *repo's* `.claude/settings.json` — including an `mcp_tool` hook calling the since-removed `capture_context` tool ("Unknown tool: capture_context" on every prompt) and a dead-clone `uv run --directory` SessionStart hook (a second, contradictory "no context stored yet" startup message next to the real global one). Modern installs only manage `~/.claude/settings.json`, so upgrades used to leave those behind. `claude.clean_legacy_repo_settings(repo)` strips hook groups that are recognizably ours (`_LEGACY_REPO_HOOK_MARKERS` match or an `mcp_tool` hook targeting the `contexer` server) and preserves everything foreign; it is called from `sync_memory` (so a plain package upgrade self-heals each repo the user opens a session in — `sync_memory` is the one adapter entrypoint every already-installed SessionStart hook calls, no reinstall needed) and from `install`/`uninstall` for the cwd's git root. `install` also prunes the stale `mcp__contexer__capture_context` allow entry, retires the legacy unconditional every-prompt reminder echo from home settings, and warns (cannot fix — plugin caches belong to Claude Code) when an installed Contexer *plugin* still ships the removed `capture_context` hook, advising `claude plugin update contexer`. The same package-only-upgrade class exists for removed hook *entrypoints*: pre-#58 installs wired `claude.capture_task` (Claude home settings and Codex `hooks.json` — the identical command string) and `cursor.capture_task` hooks, which would raise `AttributeError` on every prompt once the package is upgraded. Those entrypoints therefore exist as **self-retiring no-op stubs**: being invoked is proof of a stale hook (nothing else ever calls them), so the stub returns the host's silent no-op AND removes its own hook group — `claude.capture_task` heals `~/.claude/settings.json` and delegates `~/.codex/hooks.json` to `codex.retire_capture_task` (each module edits only its own file); `cursor.capture_task` heals `~/.cursor/hooks.json`. This adds zero cost to healthy installs (no per-prompt config reads — the stub only runs when a stale hook fires, and after the first fire the hook is gone). Gemini needs no stub: its `capture_task` use was internal to `before_agent`, whose installed hook command never changed.

**During a session**, call `update_context` whenever you make a significant decision, establish a pattern, or document a constraint. This is mandatory — not optional. After you write or edit files, the next user prompt will inject a reminder via `additionalContext`, but you should call it proactively within the same turn, not wait for the next prompt.

Call `update_context` for any of these:
- A technology, library, or approach chosen over alternatives (subtype: `architecture`)
- A file structure, naming convention, or code organization pattern established (subtype: `pattern`)
- A rule stated by the user or inferred from their preferences: "always X", "never Y" (subtype: `constraint` or `convention`)
- A build, deploy, or tooling convention established (subtype: `convention`)
- Any decision that would surprise a future Claude session if it wasn't stored
- A synthesized understanding of how a subsystem works, produced while scanning the codebase to answer a question (subtype: `architecture`) — capture it in the same turn; the session may end with the answer.

Pass the full reasoning, not just the conclusion. Pass `subtype` so decisions are retrievable by type. The server's novelty filter discards duplicates silently, so err on the side of calling it.

**Retrieving context JIT**: call `get_context` **before reading files** for any question about architecture, design decisions, rationale, constraints, patterns, or conventions. Fall back to reading files only when context is missing or the question is about current code state (exact syntax, current values). Use `query` for keyword search or `entry_type` to retrieve a specific subtype: `get_context(entry_type="constraint")` returns only constraints (up to 25). Use `limit` to override the display cap. When results are truncated, the output includes a `"showing N of M"` note so you know more exist.

## Commit-time guard (`contexer guard`)

A git `pre-commit` hook — install with `contexer guard --install-hook` (never wired automatically by `contexer install`) — that checks staged files against stored decisions when you commit. Two tiers, both implemented in `contexer/guard_engine.py` (grep `_GUARD_`; `store.py` re-exports the public entrypoints lazily as a compatibility facade — see the module bullet above) and dispatched from `cli.py`'s `guard()`/`_guard_*` family: **Tier 1 (advisory, non-blocking, always exit 0)** pairs a staged file against an `approved` decision whose provenance is trusted (`_guard_trusted`; `_GUARD_TRUSTED_SOURCES = {human, scan, bootstrap, plan}` — never `ai`/`memory`, so an unreviewed guess never nags at commit time; `plan` is trusted too because a plan-sourced decision that survived reconciliation AND developer approval is more vetted than `scan`, and the status check still keeps an unapproved plan suggestion untrusted; ALSO trusted regardless of source: `entry.get("approved_by") == "human"` — a decision a developer EXPLICITLY approved (`_apply_approval`'s approve/edit paths, per-id only — bulk approval was REMOVED precisely because clearing a list wholesale is not the deliberate, decision-by-decision gesture this trust model assumes, and the review queue is exactly where a mis-captured decision lands) is trusted even when its revision `source` stays `ai`/`memory`; an auto-approved entry no human ever reviewed — scan/bootstrap/memory born-approved routes, legacy migration, or an `ai` capture whose content merely matches a scan-fact pattern — never sets `approved_by` and stays untrusted (issue #180)) via `_guard_pairs`: either the file is in the decision's `source_files` (repo-store decisions only — global-store decisions carry no `source_files` and pair via artifact match only), or a path/module-shaped artifact pulled from the decision's content matches the staged path through `_artifact_path_match` (exact relpath, a dotted-module → path mapping, or a `/`-bounded multi-segment suffix — a bare basename can never match, by construction: a slashless non-module artifact falls through before reaching the suffix branch). Provenance is read from the current revision's `source`; a falsy `source` (legacy entries that predate provenance tracking) falls back to the decision's `created_by` for this trust check ONLY — a **read-time** fallback, not a migration that rewrites storage: `share.py`'s `_wire_source` deliberately preserves a stored `source: None` end-to-end (the cloud stores NULL = honest unknown provenance), so back-stamping it in storage would fabricate a false provenance on the share wire the moment that entry is pushed. The fallback therefore lives in `_guard_trusted` itself, at the one point that actually needs a trust verdict, and nowhere else. **Scoped ruling (#176): synthesis is derivation, not fabrication.** This "never fabricate" invariant covers only entries whose STORED revisions carry an explicit falsy `source` — those stay `None` end-to-end. It does not reach `_migrate_decision`'s synthesis path: when a legacy entry never had revision objects at all, deriving that revision's `source` from the entry's `created_by` is the truest available provenance, since nothing revision-level ever existed to preserve. Noise control layers two sidecars under `STORE_DIR` before the surfaced list is capped at `_GUARD_MAX_ADVISORIES`=5: a permanent per-(decision, file) dismiss set (`.guard_dismissed_<slug>.json`, driven by `--dismiss <hash|n>`, hashed via `_guard_hash` = sha1(decision_id+"\n"+relpath)[:12] — keyed on decision+file only, never content or line, so an ordinary edit never resurrects a dismissed pair) and a content-keyed throttle (`.guard_advised_<slug>.json`, `{hash: content_sha1}`, capped at `_GUARD_THROTTLE_CAP`=500) that only re-advises a pair once its file's staged content actually changes. **Tier 2 (blocking, exit 1)** fires only for a decision explicitly armed via `arm_guard` (CLI: `guard arm <id> --regex '<pattern>' [--flags i] [--paths <glob>] [--message <hint>]` or `--check secret`) — arming requires the decision to already be `approved` (an unreviewed decision can't be armed) and the check to be machine-checkable (`_validate_guard_check`: regex must compile, only the `i` flag is accepted, `secret` takes no pattern — an invalid request raises `ValueError` at arm time, not commit time); approval is re-checked at RUN time by `_armed_rules`, never trusted from arm time, so a decision later `ignored` stops firing with no explicit disarm needed. **Invariant: the run path never blocks a commit on its own failure.** `guard_staged` (the single entrypoint, store-READ-ONLY — never calls `_save`/`_save_global`) wraps its entire body: Tier-2 violations run first under a `_GUARD_TIME_BUDGET`=2.0s wall-clock deadline checked between files/rules (Python's `re` has no per-call timeout, so one catastrophically backtracking regex can still overrun mid-match — the documented residual risk), and ANY exception or budget overrun returns `{"error": True}` with both lists empty rather than raising or half-blocking; `_guard_run` (the CLI entrypoint, deliberately NOT wrapped by `_run_guarded`) turns that into one stderr line and `sys.exit(0)`. `CONTEXER_GUARD=0` short-circuits before any work is done, in both the CLI and `guard_staged` itself. A merge in progress skips Tier-1 pairing but not Tier-2 (its violations already ran). `guard --install-hook` embeds the resolved binary's absolute path (`shutil.which("contexer")`, else `sys.argv[0]`) in a fenced block in `.git/hooks/pre-commit` (existence-guarded, so an uninstalled/upgraded binary no-ops instead of breaking the commit) and refuses — with guidance — when `core.hooksPath` is set or the existing hook was generated by the pre-commit framework (use `.pre-commit-hooks.yaml` at the repo root instead, id `contexer-guard`); `--uninstall-hook` strips exactly that fenced block, byte-preserving any foreign content.

**Approval-time anchoring.** `approve_decision(repo_path, entry_id, action, content="", *, source_files=None)` (in `store.py` — approval machinery, not guard engine) takes a keyword-only `source_files`: when non-empty and the resolved action is `approve` or `edit`, it anchors the entry via `_anchor_sources` (`source_files` + `anchor_commit` = current HEAD) once the approval actually applies — a Suggested Update's own stashed `source_files` anchors through `_promote_proposal` instead, so `approve_decision` skips the redundant re-anchor call in that case. Approval is treated as a human revalidation of the content: approve/edit is only ever legal on a decision still awaiting review (a brand-new `pending_approval` entry, or a live decision's Suggested Update) — `_apply_approval` rejects approve/edit outright on an already-active decision with no pending proposal, so there is no "re-approve" of a settled decision. On the two transitions where approve/edit IS legal, an entry that is *already* anchored gets `anchor_commit` refreshed to current HEAD regardless of whether `source_files` was passed this call, clearing any stale flag. `source_files` here is **single-id only**: `approve_decision` raises `ValueError` when `entry_id` is a comma-list or `"all"`/`"*"`, or when `action` isn't `approve`/`edit`. There is no bulk path at all any more: `store.approve_decisions` was deleted and `server.approve_decision` returns a refusal (`_BULK_REFUSAL`) for `"all"`/`"*"`/comma-lists, so every approval is one reviewed id. This is what makes the `contexer guard`/staleness pairing above possible without a separate capture-time `source_files` call: a decision approved with `source_files=["src/app.py"]` is immediately guard-pairable and staleness-trackable, the same as one anchored at capture time via `update_context`.

**Anchor accrual (issue #175).** An unanchored decision is not invisible to Tier 1 — `_guard_pairs` pairs on `source_files` **or** on a path/module artifact mined from the decision's own content — but it is invisible to **staleness** (`_staleness_note` needs `source_files` + `anchor_commit`), and it can only ever pair on whatever files it happens to name in its own prose. Anchoring after the fact is what closes both gaps: it makes the pairing explicit rather than incidental (reason `source_files match` instead of `path artifact ...`, and files the text never mentions become pairable) and it turns on staleness tracking for that decision. Two converging paths do it, one for the existing corpus (stock) and one for new captures going forward (flow), and both funnel through the SAME write primitive, `_anchor_sources`:

- **Stock: assisted backfill.** `guard_engine.anchor_candidates_for_backfill(repo_path)` is read-only: for every decision that is BOTH `_guard_trusted` AND currently unanchored, it mines the decision's OWN content for path/module-shaped artifacts (the same `_guard_content_artifacts` extraction Tier-1 pairing uses), maps any dotted module onto its file spelling(s), and keeps only candidates that actually `exist` in the working tree right now (no rename detection in v1 — a renamed file yields no candidate for that artifact rather than guessing). **What it buys, precisely:** because candidates come from the SAME extraction `_guard_pairs` already pairs on, a backfilled decision was ALREADY producing its Tier-1 advisory before the backfill (reason `path artifact ...`) — backfill adds no new advisories. What it adds is **staleness anchoring** (`source_files` + `anchor_commit`, which `_staleness_note` requires and content artifacts can never supply) and a firmer pairing reason (`source_files match`), plus the `[E]dit` path's ability to anchor files the decision's prose never named. `test_backfilled_decision_pairs_when_file_staged` pins exactly that BEFORE/AFTER pair of reasons. The CLI, `contexer guard anchors [--list]` (`cli.py`'s `_guard_anchors`), is its interactive counterpart: `--list` prints the candidate table and mutates nothing (also the non-TTY/agent-facing surface — the `[Y]/[E]/[S]/[Q]` loop refuses outright when stdin isn't a TTY); a ratified run applies every selection in ONE batch via `store.apply_backfill_anchors(repo_path, {decision_id: [file, ...]})` — one load+lock+save for the whole run, not one write per decision — which re-checks "not already anchored" at write time too (a concurrent capture/approval/backfill could have anchored it between the CLI's read and this write), so "never overwrite an existing anchor" holds even under a race. Two guards on that loop: a **Ctrl-C/EOF at either prompt aborts the whole run and writes nothing** — not even selections ratified before the interrupt (a plain `[Q]`uit still writes them, which is what the prompt promises); and `--list` is the ONLY accepted argument — anything else exits 1, so a read-only-sounding `--dry-run` can never fall through into the write flow.
- **Flow: capture-time candidates.** `store.update_decision` no longer requires the model to name `source_files` for a new capture to eventually anchor. When a captured entry lands `pending_approval` (status-gated on the ACTUAL resulting status, not on `created_by` alone — self-enforcing against future `created_by` values) and did NOT come with `source_files` and isn't scan/bootstrap/memory-sourced (those never touched a specific file THIS session, so the edited-files signal wouldn't correlate), the repo's recently-edited files (`store._read_edited_files`, fed by `record_edited_file` — see `PostToolUse` above; only edits inside the 30-minute freshness window) are stashed on the entry as `anchor_candidates` — a field the guard's pairing engine (`_guard_pairs`) never reads, so a candidate can NEVER pair as a Tier-1 advisory before a human blesses it. `format_pending_review` surfaces the stash as a `would anchor: <files>` line beneath the rendered decision (both the brand-new-entry and the Suggested-Update branch), so the developer reviewing it sees what will happen on approval before it happens — the informed-signature rule below. The same accrual runs on `capture_user_constraint`'s **deictic** path (the one that lands `pending_approval`, `created_by="human"`): that provenance is guard-TRUSTED the instant it is approved, making those entries the highest-value candidate carriers of all — a clean directive, born `approved`, is excluded by the identical status gate, since it can never see the pending→approved transition that blesses candidates. `contexer review`/`review_pending` never anchor by themselves; only `approve_decision`'s pending→approved (or proposal-approval) transition does, via `_apply_approval`, which blesses `anchor_candidates` into a real `source_files` anchor through `_anchor_sources` and clears the candidate field — precedence is caller-passed `source_files` (approval's own explicit kwarg) > a Suggested Update's own stashed `source_files` > `anchor_candidates`, each branch skipping the ones below it once it fires, so a caller-supplied anchor is never silently overridden by a stale candidate guess. A `clear_anchors` proposal (anchors.py's retirement) vetoes the whole ladder: it deliberately leaves the entry unanchored, so the candidates are dropped rather than blessed.

**The informed-signature rule, stated once:** no anchor ever becomes guard input without a human having seen the file(s) it names at the moment they signed off - a backfill candidate is shown and ratified per-decision in the CLI loop before `apply_backfill_anchors` writes it, and a capture-time candidate is rendered as `would anchor:` in the same review surface (`format_pending_review`) the developer is already reading before they call `approve_decision`. Neither path ever anchors a `pending_approval` decision on its own; a candidate sits inert until that human signature arrives. **One read of `anchor_candidates` lives OUTSIDE the guard**, and stays outside it: `_share_projection` falls back to the candidates when `source_files` is empty, so a decision shared before its local approval reaches Teams with the files it is actually about rather than none - a `pending_approval` decision IS shareable (`_shareable_entries` excludes only `ignored`). It is deliberately one-directional (it reads candidates, it never writes `source_files`, so the guard's Tier-1 pairing input still only ever contains human-blessed anchors), and safe on the wire because contexer-teams renders received paths as claimed, unverified metadata - the trust level a candidate actually has. What that argument does NOT buy is local silence: sharing is outward and hard to undo, so `format_share_preview` marks such a line `(unconfirmed - this session's edits, not yet approved)` via the projection's extra `source_files_unconfirmed` key, keeping the confirm surface as honest as the `would anchor:` lines everywhere else.

**Anchor truncation is recorded, not silent.** `_anchor_sources` is the ONE truncation point for anchors (`apply_backfill_anchors` delegates to it, and `anchors.py`'s own `[:_MAX_SOURCE_FILES]` slices a list this function already capped, so it can never fire), and a decision that genuinely governs more than `_MAX_SOURCE_FILES`=10 files keeps the first 10 with the rest gone for good. It therefore stamps `source_files_total` when - and only when - it actually truncated, popping it otherwise so a later re-anchor to fewer files can't leave a stale count behind; `cli._review_metadata` and `format_share_preview` render it as `(first 10 of 40)`, so the developer can narrow the anchor themselves instead of never learning it was partial. Raising the cap is deliberately NOT the fix: 10 is also the server's `INPUT_LIMITS.sourceFiles` bound (raising locally first would re-create the `-32602` outbox poisoning the wire gate exists to prevent), and `anchors._ANCHOR_GIT_BUDGET` is *derived* from it (`_RENAME_CHAIN_MAX * 2 * _MAX_SOURCE_FILES + 1`), so a 10x cap is a 10x git-subprocess budget at session start under the store lock. The real answer for a subsystem-wide decision is a directory/prefix anchor rather than 100 paths, tracked in #224.

**`source_files` on the wire (issue #174 Task 5).** `remote._WIRE_SOURCE_FILES` gates whether anchors egress at all. It shipped `False` because the contexer-teams push schema is server-controlled and an unknown field poisons the outbox with permanent validation failures (this happened for real with `source="plan"`: -32602 on every retry, 192 attempts); it is now `True`, contexer-teams having accepted the field on both `push_decision` and `push_decisions` (server commit `e1a2189`, snake_case on the wire - note the same schema spells `decisionId` in camelCase, so the field name is not guessable). Deliberately a constant and not a config flag: a toggle could be flipped on against an old server and reintroduce the failure mode. The gate is read at CALL time inside `_wire_args`, never captured by a caller, so an entry queued to the outbox under one setting drains under whatever the constant is AT DRAIN TIME - in both directions. `_wire_args` also CLAMPS the field to the server's own bounds (`_WIRE_SOURCE_FILES_MAX_ITEMS`=10 / `_MAX_LEN`=300, after the redaction scrub so a redaction-lengthened path is measured at its wire length, omitting the key entirely rather than sending `[]`, which would CLEAR the column via `excluded.source_files` on re-push). The count was already capped at capture; the LENGTH never was, and the singular `push_decision` rejects over-bounds at its zod boundary, which is the poisoning case itself. **The bound is ONE definition (`remote.bound_source_files`) applied at TWO layers, the same shape redaction already has, and both are load-bearing:** `store._share_projection` applies it so the confirm-preview and the durable outbox carry exactly what will be sent (without it the preview advertises a path the wire then silently drops, at the surface a developer approves an outward push from - caught in review on #225), and `_wire_args` applies it again as the hard guarantee, since it is the only chokepoint EVERY push funnels through: a legacy outbox row queued before this existed, or a direct `push_decision` caller, never passed through a projection at all. Bounding once at the chokepoint is a guarantee; bounding at each capture site would be a promise several writers have to keep. A drop at either layer surfaces through the same `(sending N of M)` preview line capture-time truncation already uses, so it needs no second notice.

## Design constraints

- **Silent operation is essential.** Tools must not produce noise — `update_context` silently discards filtered (non-novel) content without logging. This governs *capture and filtering* noise specifically; it does not forbid every user-facing message. Two deliberate, developer-ratified exceptions: the rationale hook's recall notice (above) — a short, structured line naming what Contexer fetched, so retrieval is observable rather than spooky — and `capture_lint`'s bounce message, a model-facing corrective ack (like `constraint_ack`) that tells the calling model to restate a narrative-shaped capture in the same turn; silently discarding those would lose the decision instead of fixing its shape.
- **Secrets never egress (capture stays faithful).** `redact.py` scrubs only where a decision leaves the machine — `remote._wire_args` (the wire guarantee) and `store._share_projection` (preview/outbox parity), surfaced by the `(N secrets redacted before sending)` preview banner. Capture is deliberately **not** redacted: the local store is a verbatim record, and silently rewriting captured decisions would corrupt the product's core value (scrubbing `0600` local files also buys little against a reader who already has `~/.aws`/`.env`). Redaction is default-on (`config.redact_secrets`), deterministic, idempotent, and fail-soft (a config error keeps it ON). Do not add an outbound path that bypasses `_wire_args` without extending redaction to it.
- **No abstraction beyond what exists.** The module structure (`server.py` / `store.py` / `cli.py` / `adapters/`) is intentional. Do not add classes, config files, or layers unless the spec changes. **Adding support for a NEW AI-ASSISTANT TARGET = one new module in `adapters/`; no other files change** - that clause is about tool targets specifically, and is the one case where a whole feature genuinely fits in a single new file because `adapters/__init__.py`'s registry is the only seam it needs. It is **not** a rule that every change must land in one file. A behaviour that is inherently cross-cutting touches every module that owns a piece of it, and confining it to one would mean either reaching into another module's files or duplicating its logic - both worse than the spread. Two shipped examples: the account-switch cache invalidation of #232 has its trigger in `auth.py`, its pull caches in `team_context.py` and its marker log in `share.py`, because each module owns the file it deletes; and `share --global` (#239) needs a selector in `store.py` (which owns `_global.json`) and a push path in `share.py` (which owns the wire and outbox). The test that separates the two cases is ownership, not file count: if each touched module is doing something only it can do, the change is correctly shaped. Adding a *layer* - an interface with one implementation, a config file for a constant, a factory for one product - is what this constraint actually forbids, at any file count.
- **`update_context` is called by Claude Code, not the developer.** Claude Code nominates content; the server filters. The filtering criterion is novelty — >70% token overlap with any existing decision is rejected as a duplicate, not an LLM call.
- **Git hooks and CLI commits are out of scope for capture.** The MCP tool call path is the only capture mechanism — the commit-time guard's git hook (see above) reads and checks already-stored, already-approved decisions; it never captures a new one.
