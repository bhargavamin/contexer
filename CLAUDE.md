# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Install dependencies
uv sync

# Run the server (stdio transport — for manual testing)
uv run python server.py

# Smoke-test the server responds to MCP initialize
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"test","version":"0"}}}' | uv run python server.py
```

## Architecture

A small package (`contexer/`), intentionally minimal:

- **`contexer/server.py`** — MCP server entry point. Defines tools (`capture_user_constraint`, `update_context`, `approve_decision`, `review_pending`, `get_context`, `get_context_for_prompt`, `bootstrap_context`, `list_shareable`, `share_decision`, `update_global_context`, `get_global_context`) using `FastMCP`. Generates a `SESSION_ID` (UUID) at process start shared across all tool calls in a session. Delegates all logic to `store.py`. **Pending-review UX is non-blocking:** `update_context` capturing an AI-inferred constraint / L3 architecture decision returns a *"pending review — not yet trusted, does not block your work"* notice (never a "wait for the developer" prompt); the identified list with content is pulled on demand via `review_pending` (the in-session twin of `contexer review`), and SessionStart injects only a **count** (not per-decision content) to keep startup light. **`share_decision` is confirmed-by-default:** an outward push previews what would leave the machine (`confirm=false`, a pure local read, only when a team endpoint is configured) and requires `confirm=true` to send; a developer can opt out with `skip_confirm = true` in `config.toml`. When the developer hasn't named a decision, `list_shareable` returns an identified list to pick from, and `share_decision` accepts a comma-separated **multi-select** (`"id1,id2"`) so a whole selection previews + pushes in one call. The CLI mirror is `contexer share` with no args → a numbered interactive multi-select picker.
- **`contexer/store.py`** — All read/write and filtering logic. `_passes_filter` is the core gate: content is stored only if it is novel (token-overlap check — >70% overlap with existing decisions = duplicate). Storage is capped at `MAX_ENTRIES = 500` per repo. Display is separately capped: `_UNFILTERED_DISPLAY = 10` for overview calls, `_FILTERED_DISPLAY = 25` for query/type-filtered calls. Bootstrap is insight-aware: `_detect_insight(repo_path)` infers the user's familiarity (`high`/`medium`/`low` + decisive flag) from git signals — commit authorship by `user.email`, first-commit authorship, fresh-clone reflog entries. Detection order is load-bearing: the empty-email check must run before any `--author` query (an empty author pattern matches every commit). `bootstrap_scan(repo_path, insight)` filters gap questions by each gap's `min_insight`; empty `insight` auto-detects. Non-decisive detection makes the offer ask the user directly. Known limitation: commit count is repo-wide, so a few commits in one corner of a monorepo read as insight into the whole repo.
- **`contexer/adapters/`** — one module per AI-assistant target. `base.py` holds shared config-file helpers (`_load`/`_save`/marker checks). `claude.py`, `cursor.py`, `codex.py`, and `gemini.py` each own that tool's MCP registration, hook wiring, install/uninstall/status, and provider-specific hook output. `__init__.py` is the registry (`detect()` / `select()`). Gemini stores MCP and hook configuration together in `~/.gemini/settings.json`; it uses `SessionStart`, `BeforeAgent`, `AfterTool(write_file|replace)`, `PreCompress`, and `SessionEnd`. Because `PreCompress` is asynchronous and Gemini has no `PostCompress`, `gemini.py` sets flags and re-injects stored context at the next `BeforeAgent` event.
- **`contexer/memory_sync.py`** — imports Claude Code's memory-tool facts (`~/.claude/projects/<slug>/memory/*.md`) into the store, so decisions a session persisted to the file-based memory tool (instead of calling `update_context`) still reach Contexer. This is a *coexistence* path, not a competitor for capture: rather than fight an authority contest hook-injected reminders always lose against another tool's system-prompt memory workflow, Contexer becomes a deterministic sync target. No model in the loop — parses each fact's YAML frontmatter (`description`/`type`/`originSessionId`) + body, splits multi-section docs on `##` headings into one entry each (never a raw blob), assigns a subtype by keyword rules (ordered `convention` > `constraint` > `pattern` > `architecture`, with a frontmatter-`type` backstop — `feedback`→convention, `project`→architecture — and an architecture default, so *every* import is queryable via `get_context(entry_type=...)`), and upserts the whole dir in one load+save via `store.upsert_memory_batch`, keyed on a stable `memory_key` (source file + `##` section; repeated headings are disambiguated so they don't collide) so a fact reworded on disk updates its entry *in place* rather than silently dropping the edit (<30% change) or accumulating a near-duplicate (>30% change). First-time creation still passes the >70% novelty filter, so a memory fact that merely restates an existing decision is recorded as a recurrence, not double-stored across the two systems. Provenance: `session_id` = the fact's `originSessionId`. Fail-soft per file — a malformed memory file is skipped, never raised. The module is neutral (takes a dir path); `adapters/claude.py` owns the Claude-specific `_memory_dir(repo_path)` slug derivation (`re.sub(r"[^a-zA-Z0-9]", "-", repo_path)` — the one fragile coupling point, marked in code: if Claude Code changes its project-dir encoding, sync fails *safe* (finds nothing, never wrong data) but can go quietly dead) and `sync_memory(repo_path)`, which skips the whole import when a content fingerprint (`~/.contexer/.memory_synced_<slug>`) is unchanged.
- **`contexer/cli.py`** — the `contexer` console script: bare invocation runs the MCP server; subcommands `install [--target claude|cursor|codex|gemini|all]` / `uninstall [--purge]` / `reinstall` / `status` / `version` / `help` manage tool configs. `install` auto-detects present tools (`~/.claude` → Claude Code, `~/.cursor` → Cursor, `~/.codex` → Codex, `~/.gemini` → Gemini CLI) and falls back to Claude Code when none is detected; `--target` overrides.
- **`server.py`** (repo root) — back-compat shim importing `contexer.server`; keeps `uv run python server.py` working.
- **`requirements.txt`** — Kept for reference; `pyproject.toml` is the authoritative dependency spec managed by `uv`.

## Storage

Context is stored at `~/.contexer/<repo_slug>.json` - one file per repo, plus `_global.json` for cross-repo decisions. The slug is the repo path with non-alphanumeric characters replaced by underscores. Each file holds a flat list of entries. Writes are atomic (unique temp file + `os.replace`, mode 0o600) so readers never see a torn file; corrupt files are read as empty rather than crashing.

### Decision / Revision model (Git-like: storage preserves history, replay = current)

A decision is the logical engineering decision; a **revision** is one immutable version of it. Storage preserves every revision forever; replay exposes only the current approved one (like Git keeping every commit but cloning HEAD). This separation is what lets engineering history accumulate without ever growing the prompt or letting stale/pending values leak into a session.

The model is **embedded**, not normalized into a second collection: each decision entry owns its revisions inline (`revisions[]`) with an explicit `current_revision_id` pointer. This is the correct serialization for strict 1-to-many ownership (a revision belongs to exactly one decision, is never shared, never queried independently) and keeps the flat-list-per-repo storage and atomic whole-file write intact. The heavy query-side concerns (timeline, diff, audit, analytics, team approval, shared semantic search) live **upstream** in the remote teams MCP that decisions forward to (`push_decision`) - this OSS local store is a capture client + cache + outbox, so duplicating a relational/vector engine locally would be wasted. The embedded JSON maps 1:1 onto upstream `decisions` + `revisions` (+ a future `revision_embeddings` index) tables when that day comes, so no schema migration is needed to add those.

**Decision entry** carries: `id` (= decision_id), `type` (`task` | `decision`), `subtype` (`architecture` | `constraint` | `pattern` | `convention` - maps to the upstream 3-value `type` enum, with `pattern`→`architecture` on forward), `status` (`approved` | `suggested` | `pending_approval` | `ignored`), `current_revision_id` (the active revision - precedence is the pointer, **never** timestamps), `session_id`, `session_ids` (all sessions that have seen it), `timestamp` (Created At - immutable), `updated_at` (bumped when the current revision changes), `occurrence_count`, `created_by`, `revisions[]` (canonical list of all revisions incl. current), and optionally `proposed_revision` (a pending Suggested Update - never replayed until approved) and `memory_key`. The decision also keeps `content` / `revision` (current `version_number`) / `confidence` / `confidence_factors` as a **synced HEAD-cache** of the current revision (`_sync_decision_cache`) so the many read sites stay O(1); the revisions are the source of truth, the cache is rewritten from them on every change.

**Revision object** (`_new_revision`): `revision_id`, `decision_id`, `version_number` (1-based), `content`, `confidence_score`, `evidence` (factor list), `created_at`, `approved_at`, `source` (provenance: `ai` | `human` | `scan` | `bootstrap` | `memory`). Revisions are immutable once superseded (the new-decision pre-approval edit amends v1 in place, since there is no prior version to preserve yet).

**Accessors / lifecycle:** `_current_revision(entry)` / `_current_content(entry)` resolve the pointer (fallback: last revision); `_append_revision(entry, content, source, approved_at)` creates the next version, advances `current_revision_id`, snapshots confidence onto the revision, and resyncs the cache; this is the single path used by trivial in-place updates, `_promote_proposal` (approve a Suggested Update), and memory-sync changes. Approving a brand-new `pending_approval` decision blesses revision 1 in place (no new version). **Migration is transparent and idempotent** (`_migrate_decision`, run from `_load`): a legacy entry (old `content`/`revision` head + historical-only `revisions[]` snapshots) is rebuilt into full revision objects + a `current_revision_id` on first load; persisted on next save; fail-safe (a corrupt file still reads as empty).

**Which repo a tool call targets** is resolved by `store._resolve_repo(repo_path)` with this precedence: (1) an explicit, sane `repo_path` argument; (2) `_SESSION_REPO` — the repo bound to the running MCP-server process, captured once at startup from its own cwd's git root via `server.main` → `set_session_repo(_git_root(os.getcwd()))`; (3) the shared `~/.contexer/.current_repo` pointer as a last resort. The per-process binding (2) exists because `.current_repo` is a single global file every assistant hook overwrites — a different tool or session could clobber it and send decisions to the wrong store file. `_is_sane_repo` rejects the home dir and tool config dirs (`~/.claude`, `~/.cursor`, `~/.codex`, `~/.gemini`, `~/.contexer`, `~/.config`) on every read and write, so a poisoned pointer can never select a config-dir store file (it also rejects the filesystem root). **Hooks additionally fall back to their own cwd** (`store._hook_cwd_repo`, applied in `session_start_payload`, `bootstrap_prompt_payload`, and the per-prompt Claude entrypoints): hosts run hooks with cwd = the project directory, and non-git projects are first-class stores keyed by absolute path, so an empty git-root from the hook's shell must not erase the session's identity - the 0.16.1 bug was SessionStart claiming "no context stored" in a non-git dir whose store existed, while the MCP tools (explicit `repo_path`) found it fine. The fallback is `_is_sane_repo`-guarded (a session opened in the home dir keeps the normal chain) and is deliberately NOT the retired `|| pwd` shell fallback: the shared pointer is only written from `session_start_payload` after the same sanity check, mirroring the git-repo case. `_resolve_repo` itself is unchanged - adding a cwd fallback there would misresolve for MCP servers whose cwd is not the project (Cursor launches its server outside the workspace).

## MCP integration

`contexer install` registers the server in `~/.claude.json` under `mcpServers`, pointing at the installed console script:

```json
{
  "contexer": {
    "type": "stdio",
    "command": "/Users/<you>/.local/bin/contexer"
  }
}
```

(A from-source dev install via `scripts/install.sh` wires `uv run --directory <clone> python server.py` instead.)

For Cursor, the equivalents are `~/.cursor/mcp.json` (MCP server registration) and `~/.cursor/hooks.json` (hook wiring), managed by `contexer/adapters/cursor.py`. The MCP server entry in `mcp.json` uses the same `contexer` command; hooks use Cursor's `sessionStart` and `beforeSubmitPrompt` event names.

For Codex, the MCP server is registered in `~/.codex/config.toml` (TOML) as `[mcp_servers.contexer]` with `command = "<contexer-bin>"`, and hooks live in `~/.codex/hooks.json` (JSON, same schema and event names as Claude's `settings.json` `hooks` block), both managed by `contexer/adapters/codex.py`. The `config.toml` edit is surgical text manipulation (validated with `tomllib` before writing) so only the contexer stanza is touched — `codex.py` adds no TOML-writer dependency.

For Gemini CLI, both the MCP server and managed hooks live in `~/.gemini/settings.json`, managed by `contexer/adapters/gemini.py`. Installation preserves unrelated keys, servers, and hook groups.

## Session behaviour (hooks)

`~/.claude/settings.json` wires up hooks globally (applies to every repo):

- **`SessionStart`** — first runs `claude.sync_memory` to import any memory-tool facts (crash-recovery net: catches facts whose previous session ended without a clean `SessionEnd` flush), then injects all *approved* conventions and constraints directly as project rules; injects a count pointer for deferred architecture/pattern decisions (fetched JIT via `get_context`); injects a **count-only** pointer for decisions awaiting review (never their content — pulled on demand via `review_pending`); injects a bootstrap offer if no context exists. Resume-aware and compaction-aware via the `source` field read from hook stdin (`source_from_hook_stdin`): on `resume` with context, skips re-injection entirely (the conversation already contains it); on `resume` without context, injects transcript-mining instructions instead of the menu; on `compact` it takes the normal path and silently re-injects the full context (this is what reloads context after compaction — there is no separate `PostCompact` hook) (mine decisions from the visible conversation + store scan facts, all in the first turn — no human round-trip) and writes `~/.contexer/.resume_mining` so the UserPromptSubmit bootstrap fallback stays silent (the flag is consumed on first prompt; non-resume session starts clear stale flags).
- **`PostToolUse` (Write|Edit, silent flag)** - fires after every `Write` or `Edit` tool call. Touches `~/.contexer/.pending_capture` and returns `{}`. Completely silent - no UI output. This is the single deterministic "files changed this turn" signal; it is consumed by the next `UserPromptSubmit` (anchor) reminder.
- **`.pending_review` (deterministic mid-session nudge).** Unlike `.pending_capture` (written by a hook), the **per-repo** `~/.contexer/.pending_review_<slug>` flag is written by the **store**: `store.update_decision` touches it at the two spots that create a state awaiting the developer — a new `pending_approval` entry (gated on status) and a freshly-attached `proposed_revision` — after `_save`, inside the store lock (`store._touch_pending_review(repo_path)`). Per-repo (not global) so a pending decision in repo A never nudges a session in repo B. The per-prompt consumer is `store.pending_review_nudge(repo_path)`: it fires the count-less "offer to `review_pending`, then `approve_decision`" nudge **only** when this repo has a freshly-set flag AND still has decisions pending (`get_pending_decisions`) — so a flag left by an already-approved decision, or by another repo, never yields a false nudge — then clears the flag (fire-once; a new pending decision re-arms it). So decisions captured mid-session resurface at the next natural turn instead of waiting for the next SessionStart. Consumers per adapter: **Claude/Codex** call the Python entrypoint `claude.review_nudge` from a UserPromptSubmit hook (Python, not shell, so it can compute the slug and verify the store; Codex reuses `claude.review_nudge` verbatim and lists it in `_EVENT_MARKERS` since it has no sentinel); **Gemini** calls `store.pending_review_nudge` in `before_agent`, independent of the compaction-reload branch (a reload re-injects `get_context`, which *excludes* pending decisions, so the nudge must still fire); **Cursor** can't inject per-prompt context (`beforeSubmitPrompt` returns `{continue}`), so its reminder rides the always-apply `.mdc` rule body instead.
- **No `Stop` hook.** An end-of-turn `Stop` hook that prompted the model (via `additionalContext`) to capture/review decisions was evaluated and removed: it added latency and tokens and depended on model behavior, while delivering nothing the deterministic `PostToolUse` flag + next-prompt anchor reminder doesn't already deliver at a non-interrupting moment. `claude.install`/`codex.install` actively strip a previously-installed Contexer `Stop` hook (matched on `.pending_capture`) while leaving any foreign `Stop` hook intact; the `Stop` marker stays in the uninstall tables for this cleanup. Decision *updates* are surfaced deterministically (the `proposed_revision` Pending Update + `contexer review`), not by mid-turn prompting.
- **`UserPromptSubmit` (anchor, command, every prompt)** — writes the git root to `~/.contexer/.current_repo`, but only when actually inside a git work tree (no `|| pwd` fallback — that could poison the pointer with a non-repo dir). Also checks for `~/.contexer/.pending_capture`: if present, deletes it and injects `additionalContext` reminding Claude to call `update_context` for decisions from the previous turn. Silent to the user — only Claude sees the injected context.
- **`UserPromptSubmit` (bootstrap, command, once)** — calls `store.get_bootstrap_context_prompt` on the first prompt; injects the bootstrap offer if no context exists (fallback for when SessionStart is skipped).
- **`UserPromptSubmit` (constraint, command, every prompt)** — calls `claude.capture_constraint` with the prompt text. Detects prescriptive directives (`always X`, `never Y`, `from now on Z`) and stores them as `decision` entries automatically — no Claude involvement needed. Silent no-op for all other prompts. To avoid crowding the store, `_is_prescriptive_constraint` rejects anything that isn't a clean standalone directive: pasted blobs over `_MAX_DIRECTIVE_LEN` (300) chars, fenced code dumps, and tool/system-injected text (`<task-notification>`, `<system-reminder>`, Contexer's own injected context) — these merely *contain* directive words and are never genuine user rules.
- **`UserPromptSubmit` (rationale, command, every prompt)** — calls `claude.rationale` with the prompt text; auto-injects matching decisions when the prompt contains rationale keywords (why, reason, rationale, decided, etc.). Silent no-op for all other prompts.
- **`UserPromptSubmit` (team poll, command, every prompt)** — calls `claude.team_poll(repo, raw, consumer)` (C7 delta-poll; `consumer` defaults to `"claude"`, Codex passes `"codex"`). **Non-blocking by design: the prompt path never performs network I/O.** Delivery is a **per-repo sync log + per-consumer high-water mark** (replacing the old single `.team_pending_<slug>.json` file, which a single consumer would claim, starving any other session on the repo): `_sync` appends `{seq, ids}` to a `sync_log` inside the cache file whenever it merges new/updated team rows (`seq` is a stored monotonic counter, never wall-clock — deterministic, clock-skew-immune; the log is capped at the last 50 batches, oldest dropped — a consumer further behind than the cap just misses old *banners*, the rows stay reachable via `get_context`). Each consumer keeps its own marker `~/.contexer/.team_seen_<slug>_<consumer>.json`; `team_context.poll_nonblocking(repo, consumer)` returns the rows from every log batch with `seq >` that marker (deduped by id, current version resolved from the cache), advances the marker, and — at most once per 15s — spawns a detached refresher process (`python -m contexer.team_context <repo>`) whose synced batch surfaces on the *following* prompt. So a Claude and a Codex session on the same repo each receive every newly-synced batch exactly once, independently. A brand-new or corrupt marker initializes to the current log head (caught-up, injects nothing that once) rather than 0, because SessionStart already renders the existing backlog — the delta-poll must only surface batches logged *after* the session started. The throttle stamp is written *before* spawning so a crashing refresher can never cause a spawn storm; a leftover legacy pending file is deleted on first poll. All read paths are fail-soft (corrupt marker/log degrades to an empty injection, never raises). Trade-off (deliberate): one prompt of extra staleness vs. the synchronous poll, in exchange for a hard guarantee that a slow or hanging cloud (worst case previously: the full transport timeout, ~10s) can never stall prompt submission. The synchronous `team_context.poll()` remains for callers that want blocking semantics.
- **`PreCompact`** — runs `claude.sync_memory` to flush memory-tool facts before the context window collapses, then injects a systemMessage reminding Claude to call `update_context` for any unsaved decisions.
- **No `PostCompact` hook.** After compaction Claude Code fires `SessionStart` again with `source="compact"`, and that event silently re-injects the full context via `additionalContext` (the normal `session_start_payload` path) — so post-compaction reload is already owned, seamlessly, exactly like a fresh session start. A `PostCompact` hook was tried and removed: `PostCompact` supports no `additionalContext` and its `systemMessage` is user-facing only (the model never sees it), so it reloaded nothing and merely dumped the entire stored context into the transcript as visible noise on every `/compact`. `claude.install` now actively strips a previously-installed Contexer `PostCompact` hook (matched on `get_post_compact_context` / the sentinel) while leaving any foreign `PostCompact` hook intact; the `PostCompact` markers stay in the uninstall table for this cleanup. (The neutral `store.post_compact_payload` / `get_post_compact_context` helpers are retained for the Codex adapter and Gemini's `BeforeAgent` re-injection, which do inject on their own event models.)
- **`SessionEnd`** — runs `claude.sync_memory` to flush memory-tool facts on clean exit. The earlier decision to reject `SessionEnd` hooks was about *capture that needs the model to act* (a `SessionEnd` hook can't make Claude call a tool); this is a deterministic file import that needs no model, so it is valid here. These three triggers (`SessionStart`, `PreCompact`, `SessionEnd`) are the memory-sync surface; the import itself is idempotent, so running it at several of them is cheap.
- **Legacy repo-settings cleanup (upgrade hygiene).** The pre-CLI from-source installer (June 2026) wrote hooks into the *repo's* `.claude/settings.json` — including an `mcp_tool` hook calling the since-removed `capture_context` tool ("Unknown tool: capture_context" on every prompt) and a dead-clone `uv run --directory` SessionStart hook (a second, contradictory "no context stored yet" startup message next to the real global one). Modern installs only manage `~/.claude/settings.json`, so upgrades used to leave those behind. `claude.clean_legacy_repo_settings(repo)` strips hook groups that are recognizably ours (`_LEGACY_REPO_HOOK_MARKERS` match or an `mcp_tool` hook targeting the `contexer` server) and preserves everything foreign; it is called from `sync_memory` (so a plain package upgrade self-heals each repo the user opens a session in — `sync_memory` is the one adapter entrypoint every already-installed SessionStart hook calls, no reinstall needed) and from `install`/`uninstall` for the cwd's git root. `install` also prunes the stale `mcp__contexer__capture_context` allow entry, retires the legacy unconditional every-prompt reminder echo from home settings, and warns (cannot fix — plugin caches belong to Claude Code) when an installed Contexer *plugin* still ships the removed `capture_context` hook, advising `claude plugin update contexer`. The same package-only-upgrade class exists for removed hook *entrypoints*: pre-#58 installs wired `claude.capture_task` (Claude home settings and Codex `hooks.json` — the identical command string) and `cursor.capture_task` hooks, which would raise `AttributeError` on every prompt once the package is upgraded. Those entrypoints therefore exist as **self-retiring no-op stubs**: being invoked is proof of a stale hook (nothing else ever calls them), so the stub returns the host's silent no-op AND removes its own hook group — `claude.capture_task` heals `~/.claude/settings.json` and delegates `~/.codex/hooks.json` to `codex.retire_capture_task` (each module edits only its own file); `cursor.capture_task` heals `~/.cursor/hooks.json`. This adds zero cost to healthy installs (no per-prompt config reads — the stub only runs when a stale hook fires, and after the first fire the hook is gone). Gemini needs no stub: its `capture_task` use was internal to `before_agent`, whose installed hook command never changed.

**During a session**, call `update_context` whenever you make a significant decision, establish a pattern, or document a constraint. This is mandatory — not optional. After you write or edit files, the next user prompt will inject a reminder via `additionalContext`, but you should call it proactively within the same turn, not wait for the next prompt.

Call `update_context` for any of these:
- A technology, library, or approach chosen over alternatives (subtype: `architecture`)
- A file structure, naming convention, or code organization pattern established (subtype: `pattern`)
- A rule stated by the user or inferred from their preferences: "always X", "never Y" (subtype: `constraint` or `convention`)
- A build, deploy, or tooling convention established (subtype: `convention`)
- Any decision that would surprise a future Claude session if it wasn't stored

Pass the full reasoning, not just the conclusion. Pass `subtype` so decisions are retrievable by type. The server's novelty filter discards duplicates silently, so err on the side of calling it.

**Retrieving context JIT**: call `get_context` **before reading files** for any question about architecture, design decisions, rationale, constraints, patterns, or conventions. Fall back to reading files only when context is missing or the question is about current code state (exact syntax, current values). Use `query` for keyword search or `entry_type` to retrieve a specific subtype: `get_context(entry_type="constraint")` returns only constraints (up to 25). Use `limit` to override the display cap. When results are truncated, the output includes a `"showing N of M"` note so you know more exist.

## Design constraints

- **Silent operation is essential.** Tools must not produce noise — `update_context` silently discards filtered content without logging.
- **No abstraction beyond what exists.** The module structure (`server.py` / `store.py` / `cli.py` / `adapters/`) is intentional. Do not add classes, config files, or layers unless the spec changes. Adding support for a new tool = one new module in `adapters/`; no other files change.
- **`update_context` is called by Claude Code, not the developer.** Claude Code nominates content; the server filters. The filtering criterion is novelty — >70% token overlap with any existing decision is rejected as a duplicate, not an LLM call.
- **Git hooks and CLI commits are out of scope.** The MCP tool call path is the only capture mechanism.
